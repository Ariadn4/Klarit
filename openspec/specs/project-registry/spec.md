## Requirements
### Requirement: 导入项目

用户 SHALL 能通过选择一个本地目录把项目导入 Klarit。一次导入 MUST 建立或扩充一个由**一个或多个成员仓**组成的项目：

- 选中的目录是单个 git 仓（或 gitless 目录）时，以该目录的文件夹名作为项目默认名，作为成员数为 1 的项目登记。
- 选中的目录自身不是 git、其直接子目录中含多个 git 仓时，系统 MUST **直接**把这些子仓组成一个多仓项目，**不再**弹出确认提示或要求用户二次确认（见 `multi-repo-project`）。

系统 MUST 以可读名称命名项目（单仓取仓库目录文件夹名；多仓取容器目录文件夹名作默认名，可编辑）。同一成员仓（按其持久身份判定）重复导入 MUST 不产生重复登记，而是复用既有成员条目并更新其记录路径；重复导入同一组成员仓 MUST 凭**成员身份**（`.klarit/project-id`）复用既有多仓项目（保持其项目 id 不变）而非新建——这同时实现换机器/同步后凭成员身份复原分组。

#### Scenario: 选择目录导入新项目
- **WHEN** 用户在导入流程中选择一个尚未导入的单个 git 仓库或 gitless 目录
- **THEN** 系统以该目录的文件夹名作为项目名，作为成员数为 1 的项目加入注册表

#### Scenario: 重复导入同一成员仓不重复登记
- **WHEN** 用户导入一个其持久身份已存在于注册表中的仓（如换了路径的同一仓库）
- **THEN** 系统复用既有成员条目而非新建，并更新其记录的最新路径

#### Scenario: 容器目录含多子仓直接组建多仓项目
- **WHEN** 用户选择的目录自身不是 git、其下含多个 git 子仓
- **THEN** 系统直接把这些子仓组成一个多仓项目并完成登记，不弹任何确认提示

#### Scenario: 重复导入同一组成员凭身份复用既有多仓项目
- **WHEN** 用户再次导入一个其子仓已作为某多仓项目登记过的容器目录（即便容器绝对路径已变）
- **THEN** 系统凭各子仓的 `.klarit/project-id` 认出它们属于既有项目，复用该项目（项目 id 不变），刷新各成员路径，不新建重复项目

### Requirement: 持久项目身份

每个入 git 的项目 SHALL 拥有一个持久且唯一的身份标识，写入项目内的 `.klarit/project-id`（随项目目录与 git 一起走）。注册表中的项目身份与卡片/状态数据 MUST 按此 ID 关联而非按路径，从而在移动目录、换机器、使用多个 worktree 时都不断链。

#### Scenario: 首次绑定生成身份文件
- **WHEN** 一个有 git 的项目被导入且尚无 `.klarit/project-id`
- **THEN** 系统生成唯一 ID 写入 `.klarit/project-id`，并以该 ID 在注册表中登记项目

#### Scenario: 移动目录后仍识别为同一项目
- **WHEN** 一个已绑定身份的项目被移动到新路径后再次被打开或导入
- **THEN** 系统通过 `.klarit/project-id` 识别为同一项目，复用其注册条目并更新记录路径

#### Scenario: 多 worktree 指向同一身份
- **WHEN** 同一仓库的另一个 worktree 被导入（其 `.klarit/project-id` 与主工作树一致）
- **THEN** 系统将其识别为同一项目身份，而非新建独立项目

### Requirement: git 检测与绑定

导入或打开项目时，系统 SHALL 检测该目录是否处于 git 仓库内；一旦查到 git 即 MUST 立即绑定，记录其主分支名以及（若存在）远程地址。系统 MUST 正确处理无 git、有 git 但未配置远程、有 git 且已推远程等多种情况，且不得因为缺少远程而拒绝绑定。

#### Scenario: 有 git 且已推远程
- **WHEN** 导入的项目处于 git 仓库中且配置了远程
- **THEN** 系统记录其主分支名与远程地址，并完成身份绑定

#### Scenario: 有 git 但未配置远程
- **WHEN** 导入的项目有 git 但尚未配置任何远程
- **THEN** 系统仍完成绑定并记录主分支名，远程记为缺省，不因无远程而失败

#### Scenario: 导入时无 git
- **WHEN** 导入的目录不在任何 git 仓库内
- **THEN** 系统仍把项目登记进注册表（以路径为基础标识），不创建 `.klarit/project-id`，并标记为「无 git」

### Requirement: git 出现后自动补绑

对于导入时尚无 git 的项目，当其目录之后变为 git 仓库（例如用户执行了 `git init`）时，系统 SHALL 在再次检测到 git 时立即补绑：生成并写入 `.klarit/project-id`、记录主分支与远程，并把注册表中原以路径标识的条目升级为以持久身份标识。

#### Scenario: 后续 git init 触发补绑
- **WHEN** 一个先前以「无 git」登记的项目，其目录此后被检测到已成为 git 仓库
- **THEN** 系统立即写入 `.klarit/project-id`、记录主分支与远程，并把该注册条目升级为按持久身份关联

### Requirement: 项目目录由成员仓路径派生

项目的**项目目录**（侧边栏文件树视图的根，见 `app-shell-sidebar`）SHALL 由其成员仓的最近已知路径**派生**，而非另存一个绝对路径：单仓项目取其唯一成员的路径；多仓项目取各成员仓的公共父目录。因绝对路径在云同步、换机器、换盘符时必然失效，项目目录 MUST NOT 作为持久身份被存储；成员仓路径按各自 `.klarit/project-id` 在重新导入时刷新，项目目录据此自动归位。（gitless 纯目录项目无持久身份，是天然 path-bound 的退化情形，换机器需重新导入。）

#### Scenario: 单仓项目目录取成员路径
- **WHEN** 系统需要确定一个单仓项目的项目目录
- **THEN** 取其唯一成员仓的当前记录路径作为项目目录

#### Scenario: 多仓项目目录取成员公共父目录
- **WHEN** 系统需要确定一个多仓项目的项目目录
- **THEN** 取各成员仓当前记录路径的公共父目录作为项目目录

#### Scenario: 换机器重新导入后项目目录自动归位
- **WHEN** 用户在新机器上重新导入某多仓项目的容器，其各子仓凭 `.klarit/project-id` 被识别为原成员并更新到新机器上的路径
- **THEN** 系统据成员的新路径派生出新机器上的项目目录，文件树根随之归位，无需用户另行设置路径

### Requirement: 项目激活工作流

每个项目 SHALL 记录其**激活工作流 id**，作为项目管理数据持久化于注册表（`userData`，不入 git），按项目身份关联而非路径——移动目录、换机器、多 worktree 都不断链。系统 MUST 提供读取与设置某项目激活工作流的能力，并经 IPC 暴露。未设置激活工作流的项目（如新导入）MUST 以「未激活」状态返回，不致错误。

#### Scenario: 设置并读回激活工作流
- **WHEN** 为某项目设置激活工作流 id 后再读取该项目
- **THEN** 系统返回先前设置的激活工作流 id

#### Scenario: 新项目无激活工作流
- **WHEN** 读取一个尚未设置激活工作流的项目
- **THEN** 系统以「未激活」状态返回，不报错

#### Scenario: 激活指针随身份不断链
- **WHEN** 一个已设置激活工作流的项目被移动目录后重新打开
- **THEN** 系统按持久身份识别为同一项目，其激活工作流 id 保持不变

### Requirement: 删除工作流时清理激活引用

当某工作流被删除（见 `workflow-library`）时，系统 SHALL 清理所有指向它的项目激活指针：被影响项目的激活工作流 MUST 被清除为「未激活」（或由调用方改投到另一工作流），删除完成后不得有任何项目仍指向已删除的工作流 id。

#### Scenario: 删除后无悬挂激活引用
- **WHEN** 一个被某项目激活的工作流被删除
- **THEN** 该项目的激活工作流被清为「未激活」，注册表中不残留指向已删除 id 的引用
