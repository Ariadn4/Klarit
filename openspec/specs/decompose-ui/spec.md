# decompose-ui Specification

## Purpose
新建需求分解的交互界面：看板「待办」列底部的「新建需求」入口（呈「+ 创建」按钮，按流程相位承载全程状态）、无蒙层可最小化的「描述想法」窗（附件按钮/粘贴/拖入均把路径插入正文）、处理态改由「待办」列「+ 创建」按钮承载全程（呈「建卡中」、处理窗只「收起」一个按钮、不中断分解，不再在主面板右下角设独立「建卡中」浮标）、以及「审阅候选任务」窗（分类徽章+标题+markdown 渲染描述、点卡进详情、仅标题与描述可改）。三窗均不加蒙层、仅用语义令牌、深浅双主题。
## Requirements
### Requirement: 新建需求入口

渲染层 SHALL 在项目窗口主面板的**看板「待办」列底部**提供「新建需求」入口,呈现为一个「**+ 创建**」按钮。该按钮承担新建需求流程的**全程状态**,按当前相位改变形态:

- **空闲(idle)**:显示「**+ 创建**」,点击打开「描述想法」窗(现状不变)。
- **描述中(describing,已收起)**:反映「编辑中」态,点击重开「描述想法」窗。
- **处理中(processing)**:显示带处理中图标(转圈)的「**建卡中**」,点击重开处理窗;此态 MUST NOT 发起新的分解或新的描述窗(见「处理态隐藏与『+ 创建』按钮承载建卡状态」)。
- **审阅中(reviewing,已收起)**:显示待审阅状态(含候选张数,如「N 张候选待审阅」),点击重开「审阅候选任务」窗。

任一**非空闲**相位点击该按钮 MUST 重开对应浮窗,而非另起一次分解(复用既有「再次点击新建需求即重开」语义)。该位置为新建需求入口与全程状态的**唯一落点**(取代此前主面板右下角的独立「建卡中」指示)。该入口 MUST 在当前窗口未绑定任何项目时给出明确空态(无处归属需求,见 `global-agent`),不报错。看板列骨架本身由 `requirement-kanban-board` 定义。按钮样式 MUST 遵循品牌规范(`docs/brand`)与 `index.css` 的 `@theme` 设计令牌、支持深浅双主题、仅用语义令牌。

#### Scenario: 空闲态待办列底部渲染「+ 创建」入口
- **WHEN** 主面板渲染看板「待办」列且新建需求流程处于空闲态
- **THEN** 该列底部出现「+ 创建」新建需求入口

#### Scenario: 点击新建需求打开描述想法窗
- **WHEN** 用户在已绑定项目的窗口点击处于空闲态的「+ 创建」
- **THEN** 打开「描述想法」窗

#### Scenario: 处理态按钮呈现「建卡中」
- **WHEN** 新建需求流程处于处理中(processing)
- **THEN** 「待办」列底部的按钮呈现带处理中图标的「建卡中」态,而非「+ 创建」

#### Scenario: 处理态点击按钮重开处理窗
- **WHEN** 处理进行中用户点击呈「建卡中」态的按钮
- **THEN** 重开处理窗并提示「正在处理需求」,不发起第二次分解、不弹新的描述窗

#### Scenario: 审阅收起后按钮呈现待审阅状态
- **WHEN** 用户在「审阅候选任务」窗点「收起」、审阅态浮窗已隐藏
- **THEN** 「待办」列底部的按钮呈现待审阅状态(含候选张数),点击它重开「审阅候选任务」窗

#### Scenario: 未绑定项目时的空态
- **WHEN** 当前窗口未绑定任何项目,用户点击空闲态「+ 创建」
- **THEN** 给出明确空态提示,不打开描述想法窗、不报错

### Requirement: 描述想法窗

「描述想法」窗 SHALL 含：一个**「附件」按钮**、一个**多行描述输入**、底部「取消 / 提交」按钮，及一段提示文案「请描述想法（可一次写下多条）；可 Ctrl+V 粘贴截图、拖入文件插入其路径」。该窗 MUST **不加蒙层**（无 scrim 遮罩），且可最小化/关闭。**附件统一以路径形式即时插入正文**（而非单列附件区）：

- 点击「附件」按钮 MUST 打开**系统文件选择器**（可多选），所选文件的路径插入正文。
- **Ctrl+V 粘贴截图** MUST 把该图落盘到受管目录后，将其路径插入正文。
- **拖入文件** MUST 取其本地路径插入正文。

点击「提交」MUST 携带描述发起分解（见 `requirement-decomposition`）；点击「取消」MUST 关闭窗、不发起分解。窗体样式 MUST 遵循品牌规范（`docs/brand`）与 `index.css` 的 `@theme` 设计令牌、支持深浅双主题、仅用语义令牌。

#### Scenario: 描述想法窗的构成
- **WHEN** 描述想法窗打开
- **THEN** 展示「附件」按钮、多行描述输入、取消/提交按钮与提示文案，且不带蒙层

#### Scenario: 附件按钮打开系统选择器并把路径插入正文
- **WHEN** 用户点击「附件」按钮并在系统文件选择器中选中一个或多个文件
- **THEN** 所选文件的路径被插入到正文描述中

#### Scenario: 粘贴截图落盘后路径插入正文
- **WHEN** 用户在描述想法窗内 Ctrl+V 粘贴一张截图
- **THEN** 该截图落盘到受管目录，其路径被插入到正文描述中

#### Scenario: 拖入文件插入路径
- **WHEN** 用户把一个文件拖入描述想法窗
- **THEN** 该文件的本地路径被插入到正文描述中

#### Scenario: 提交发起分解
- **WHEN** 用户点击「提交」
- **THEN** 系统携带描述发起分解，进入处理态

#### Scenario: 取消不发起分解
- **WHEN** 用户点击「取消」
- **THEN** 描述想法窗关闭，不发起分解

### Requirement: 处理态隐藏与「+ 创建」按钮承载建卡状态

提交后 AI 处理期间,描述想法窗 SHALL **隐藏**(不停留遮挡界面),建卡状态 SHALL 由「待办」列底部的「**+ 创建**」按钮承载——该按钮呈现带处理中图标的「建卡中」态(见「新建需求入口」)。系统 MUST NOT 在主面板右下角(或其它全局位置)另设独立的「建卡中」浮动指示。处理期间用户**再次点击该按钮**(此时呈「建卡中」态)MUST 重新弹出处理窗并提示「正在处理需求」(而非另起一次新的分解或新的描述窗)。处理窗 MUST **只含一个「收起」按钮**(收回,按钮继续显示「建卡中」),**不含关闭(×)**——收起不中断分解、不清空,「建卡中」态 MUST 一直存在于按钮上直至处理完成。处理完成后 MUST 自动弹出「审阅候选任务」窗、按钮的「建卡中」态消除。按钮状态样式 MUST 遵循品牌规范与设计令牌、深浅双主题、仅用语义令牌。

#### Scenario: 处理时隐藏并由按钮承载建卡中
- **WHEN** 用户提交描述、AI 开始处理
- **THEN** 描述想法窗隐藏,「待办」列底部「+ 创建」按钮呈现「建卡中」处理态,主面板右下角无独立「建卡中」指示

#### Scenario: 处理中再点按钮显示正在处理
- **WHEN** 处理进行中用户再次点击呈「建卡中」态的按钮
- **THEN** 重新弹出处理窗并提示「正在处理需求」,不发起第二次分解、不弹新的描述窗

#### Scenario: 处理窗只「收起」不关闭、建卡中持续
- **WHEN** 用户在处理窗点「收起」
- **THEN** 处理窗收回、分解不中断,按钮「建卡中」态仍在,直至处理完成

#### Scenario: 处理完成弹出审阅窗
- **WHEN** 分解处理完成、产出候选卡
- **THEN** 自动弹出「审阅候选任务」窗,按钮「建卡中」态消除

### Requirement: 审阅候选任务窗

「审阅候选任务」窗 SHALL 列出每张候选卡,每张展示:**分类徽章**(`epic`/`feature`/`bug`,徽章文案如 EPIC/FEAT/BUG)、**标题**、**描述(markdown 渲染、非源码)**。点击某张卡 MUST 进入**任务详情**展示该卡细节;详情中**允许用户修改标题与描述**,`typeId`/预取名只读。

**跨卡依赖门的呈现与编辑**:因 `blocked_by` 是 `todo-auto-scheduler` 的**调度硬门**(连错一条边会让卡静默不排),任务详情 SHALL **显式呈现**该候选卡的跨卡依赖边(`blocked_by`/`blocks`),每条标出**被指向卡的当前状态**(如「在跑」/「未开始」/「已完成」),而非只渲染一行 `kind→target` 原文。用户 MAY 在详情里**删除**一条依赖门,并 MAY 新增一条 `blocked_by` 指向全盘中的某张现有卡;所加/所留的边 MUST 过 `requirement-card-model` 的共享边谓词——一条 `blocks` 指向在跑卡 MUST 被拒并给可读原因。层级关系(`parent`/`child`)与预取名保持只读。

**详情视图的返回与页脚**:详情视图的返回入口 MUST 位于**窗口标题栏**,以**统一的 chevron 返回图标**(不使用 `←` 等箭头字符——全 app 返回一律用 chevron,对齐品牌规范「详情返回」)呈现,点击返回候选列表。详情视图 MUST **不渲染**「取消 / 创建任务」页脚——「创建任务」只在**候选列表视图**可点,用户须先返回列表才能创建(避免在单卡编辑态误触发整批落库)。

**列表视图的页脚**:候选列表视图窗底含「取消 / 创建任务」按钮:点击「取消」MUST 关闭窗、丢弃候选;点击「创建任务」MUST 把(含用户编辑后的)候选卡经**统一创建接缝**落库到当前项目(见 `requirement-card-store`)。该窗 MUST **不加蒙层**,样式 MUST 遵循品牌规范与设计令牌、深浅双主题、仅用语义令牌。

#### Scenario: 列出候选卡
- **WHEN** 审阅候选任务窗打开(列表视图)
- **THEN** 每张候选卡展示分类徽章、标题与渲染后的 markdown 描述,窗底含「取消 / 创建任务」,窗体不带蒙层

#### Scenario: 点击卡进详情、标题栏 chevron 返回
- **WHEN** 用户点击某张候选卡进入任务详情
- **THEN** 展示该卡细节,窗口标题栏左侧出现 chevron 返回图标(非 `←`);点击它返回候选列表

#### Scenario: 详情呈现跨卡依赖门与目标状态
- **WHEN** 一张候选卡带 `blocked_by`/`blocks` 指向现有卡,用户进入其任务详情
- **THEN** 详情显式列出这些依赖门,每条标出被指向卡的当前状态(如「在跑」),而非只渲染一行 `kind→target` 原文

#### Scenario: 可删除一条跨卡依赖门
- **WHEN** 用户在任务详情里删除某条 `blocked_by` 门
- **THEN** 该候选卡的对应关系边被移除,创建时不再携带该门

#### Scenario: 详情里加 blocks 指向在跑卡被拒
- **WHEN** 用户在任务详情里试图给候选卡加一条 `blocks` 指向一张在跑卡
- **THEN** 经共享边谓词判非法、给出可读原因,该边不被加入

#### Scenario: 详情视图不渲染创建/取消页脚
- **WHEN** 用户处于某张候选卡的任务详情视图
- **THEN** 窗底 MUST NOT 出现「取消」「创建任务」按钮;须返回候选列表视图后「创建任务」方可点击

#### Scenario: 仅可改标题、描述与跨卡门
- **WHEN** 用户在任务详情里编辑
- **THEN** 标题、描述与跨卡依赖门(`blocked_by`/`blocks`)可改,`typeId`/预取名/层级关系为只读

#### Scenario: 描述以 markdown 渲染
- **WHEN** 候选卡描述含 markdown 标记
- **THEN** 窗内以渲染后的样式呈现,而非展示 markdown 源码

#### Scenario: 列表视图创建任务落库
- **WHEN** 用户在候选列表视图点击「创建任务」
- **THEN** 系统把含编辑的候选卡经统一创建接缝落库到当前项目,再刷新看板、收起流程

#### Scenario: 取消丢弃候选
- **WHEN** 用户在候选列表视图点击「取消」
- **THEN** 关闭窗、丢弃全部候选,不落库
