# engine-execution Specification

## Purpose
定义工作流的运行引擎：以 runId 标识的运行与断点持久化、节点执行的阶段状态机、幂等 ensure 引擎执行器（8 个操作）、失败四归宿与统一前进式决策回路（i18n key、人工门复用、接 agent 的 sourceKind 口子）、一次性触发且可取消可恢复的 IPC 契约，以及非引擎执行者的跳过约定。
## Requirements
### Requirement: 运行的标识、请求与持久化

引擎的一次执行称为一个**运行(run)**,SHALL 以一个 `runId` 唯一标识。运行由一个**运行请求**触发,请求至少含:目标工作流 id、目标仓库上下文,并 MAY 携带一个可选 **`cardId`**——把该运行**关联到一张需求卡**(见 `requirement-card-store`)。带 `cardId` 时,运行的**涉及仓集合来自该卡的 `repos`**(需求与成员仓多对多);运行 SHALL 以卡预取名(slug)作**所有被命中成员仓的同名工作分支名**。运行 MUST 为涉及仓集合中**每个成员仓各构造一套执行上下文**(各绑该成员的仓路径、逐仓解析的基分支),在一个运行内对成员仓**扇出**执行——**一卡对应一个运行**(对齐卡侧单一 `activeRunId` 与运行侧单一 `cardId`),不为多仓拆成多个运行。单仓卡(`repos` 单元素)是成员数为 1 的退化情形,行为与今日单仓一致。

当运行请求**要求避撞**时(`avoidBranchConflict`——**卡派生的运行请求默认开启**,直接触发的运行缺省关闭),分支名 MUST 在运行**触发(start)时一次性解析**出一个在**所有涉及仓都空闲**的名字:自卡 slug 起,若该名在**任一**涉及仓已存在同名本地分支、**或**其在任一涉及仓派生出的 worktree 路径已被占用,则**所有涉及仓一起**递增尾号(`x`→`x-2`→`x-3`…)另取下一档,逐档对全体涉及仓复检,直到找到一个在**每个涉及仓的本地分支与 worktree 路径两个维度上都空闲**的名字;解析结果 SHALL **一次性烙入 `request.branch`**。涉及仓始终**共用同一个**分支名——不做逐仓分别递增(保「卡 slug = 各仓同名分支」不变量)。此解析 MUST 只在 start 发生**一次**且只读探测(不写 git):`deriveMembers` 等派生 MUST 保持纯函数,恢复(resume)时**沿用已烙入的分支名**,MUST NOT 在恢复时重跑撞名检测(否则会从运行自己已建的 worktree 上递增走开、造成孤儿)。start 之后若外部插入同名分支,由既有幂等认领(见「引擎执行器」`create-branch`)兜底,不重解析。**未要求避撞**的运行沿用既有幂等认领语义——遇同名分支即认领(noop),不改名。

运行的状态(断点)MUST 按运行**独立持久化**到用户数据目录(`userData/engine-runs/<runId>.json`),其 `request.cardId` 随之持久化,作运行 → 卡的**正向链**;卡侧以 `activeRunId` 记反向链。断点 MUST 额外持久化**每个成员仓的派生上下文**(分支/worktree 路径/逐仓基分支)与**上游节点结构化输出**,以保证恢复稳定。运行模型本身(阶段状态机、决策回路、恢复)MUST NOT 因绑卡或多仓而改变——`cardId` 仍为可选关联字段,不带 `cardId` 的运行(如旧数据)按无关联、单仓上下文处理。

> 说明:运行断点本期仍物理存于 `engine-runs`(运行机制单一来源,`resumeAll` 依赖之),逻辑上经 `cardId`/`activeRunId` 双向链归属于卡。

#### Scenario: 触发运行得到 runId
- **WHEN** 以一个合法运行请求触发引擎
- **THEN** 引擎分配并返回一个 `runId`,并为该运行落一份持久化断点(含每成员派生上下文)

#### Scenario: 运行状态可按 runId 查询
- **WHEN** 以某 `runId` 查询运行状态
- **THEN** 返回该运行的当前节点、阶段、运行态与(若有)待决策;未知 runId 返回空而非抛错

#### Scenario: 运行请求可关联需求卡并按卡涉及仓扇出
- **WHEN** 以一个携带 `cardId`、其卡 `repos` 含成员 A、B 的运行请求触发引擎
- **THEN** 单个运行为 A、B 各建执行上下文,断点记下 `request.cardId` 与每成员派生上下文,可据此反查所属卡

#### Scenario: 建分支撞名时全仓统一递增避撞（opt-in）
- **WHEN** 触发一个 `avoidBranchConflict` 开启、slug 为 `x`、涉及仓 A、B 的运行,其中 B 已存在本地分支 `x`(或 B 的 `x` 派生 worktree 路径已被占用)
- **THEN** start 解析出下一档 `x-2`(A、B **一起**用 `x-2`,不是只 B 递增),烙入 `request.branch`;A、B 的 worktree 路径均据 `x-2` 派生

#### Scenario: 未要求避撞的运行遇同名分支沿用幂等认领
- **WHEN** 触发一个 `avoidBranchConflict` 关闭(缺省)、分支为 `x` 的运行,而 `x` 已存在
- **THEN** 不改名(`request.branch` 仍为 `x`),由既有幂等认领处理(create-branch 报 noop),保直接触发运行的既有语义

#### Scenario: 冲突判定含分支与 worktree 路径两维
- **WHEN** slug `x` 的分支在所有涉及仓都不存在,但其在某涉及仓派生的 worktree 路径已被占用
- **THEN** `x` 判为不可用,全仓递增到 `x-2`(直到某档在每个涉及仓分支与路径两维都空闲)

#### Scenario: 恢复时沿用已烙入分支名不再递增
- **WHEN** 一个已把 `request.branch` 解析为 `x-2` 并建出 worktree 的运行随应用重开、触发恢复,`deriveMembers` 重跑
- **THEN** 派生沿用已烙入的 `x-2`(尽管此刻 `x-2` 分支/worktree 已由本运行自己占用),不再重跑撞名检测、不递增到 `x-3`

#### Scenario: 旧断点无 cardId 仍可读
- **WHEN** 引擎加载一份不含 `cardId` 的旧断点
- **THEN** 正常读取并续跑,视为无卡关联、单仓上下文,不报错(向后兼容)

#### Scenario: 单仓卡退化等价
- **WHEN** 绑卡运行的卡 `repos` 仅一个仓且工作流节点均未声明 target
- **THEN** 运行行为与今日单仓一致(派生单套分支/worktree/base,作用于唯一成员);无撞名时分支名即原 slug 不变

### Requirement: 节点执行的阶段状态机

引擎执行一个节点 SHALL 走一台**阶段状态机**:`executing`(跑执行者)→ 依序 `gate 0`、`gate 1`…`gate n`(逐道检查)→ `done`(推进到下一节点)。引擎 MUST 在**每个阶段边界**持久化断点(记录当前节点与所处阶段)。`done` 即推进到工作流节点列表的下一个节点;末节点 `done` 即运行完成。

#### Scenario: 无门节点走 executing 直达 done
- **WHEN** 执行一个无门把的引擎节点
- **THEN** 经 `executing` 阶段后直接进 `done` 并推进到下一节点,期间在阶段边界写过断点

#### Scenario: 有门节点逐道过门
- **WHEN** 执行一个含若干门把的节点,且各门把依次通过
- **THEN** 阶段依 `executing → gate 0 → … → gate n → done` 推进,每道门把通过后断点前移到下一阶段

### Requirement: 运行态与「永不静默卡住」

运行 SHALL 处于三种状态之一:`running`(推进中)、`waiting-decision`(被一个待决策阻塞)、`paused`(被用户暂停)。引擎 MUST NOT 让运行因错误进入任何**不可见、无出路**的停滞:任何使运行无法继续的情形,MUST 表现为 `waiting-decision`(携带可操作的固定选项)或 `paused`,二者皆为**可见、可操作**的状态。

#### Scenario: 终局失败进入可见的等待决策而非死挂
- **WHEN** 某节点遇到无法自动恢复的终局失败
- **THEN** 运行进入 `waiting-decision` 并携带固定选项,而非停在一个无状态、无按钮的卡死

#### Scenario: 暂停是可见状态
- **WHEN** 用户暂停一个运行
- **THEN** 运行在下一个阶段边界进入 `paused` 并持久化断点,可被恢复

### Requirement: 断点恢复与开机自动续跑

恢复 SHALL 依断点跳到 `(当前节点, 阶段)` 并**续跑当前阶段**,而非从节点开头重来。重跑当前阶段 MUST 安全:`executing` 阶段重跑引擎操作因其幂等而收敛;**`agent` 节点的 `executing` 恢复 MUST 走续接**（见 `agent-execution`「续接阶梯」：优先原生 `--resume` 接盘上会话、否则喂回历史重建），而非丢弃半路进度从头新拉;门把阶段恢复时**已通过的门把跳过**、从停住那道续。应用启动时,引擎 SHALL 扫描持久化运行,把处于 `running` 的自动续跑(对齐「关软件自动暂停、重开自动恢复」),含续接崩溃/关软件时半路的 agent 节点。

#### Scenario: 中途中断后从断点续而非重来
- **WHEN** 一个运行在某节点的某阶段被中断(关应用/崩溃),其后引擎重新加载该运行
- **THEN** 运行从该 `(节点, 阶段)` 续跑,已完成的上游节点与已过的门把不重做

#### Scenario: 崩溃半路的 agent 节点按续接恢复
- **WHEN** 应用在某 agent 节点执行中崩溃/关闭，重启后引擎恢复该 `running` 运行
- **THEN** 引擎对该 agent 节点走续接阶梯（优先原生 `--resume`）接上半路会话，而非从头重跑丢失进度

#### Scenario: 开机自动恢复进行中的运行
- **WHEN** 应用启动且存在持久化的 `running` 运行
- **THEN** 引擎自动续跑它们,无需渲染层触发

#### Scenario: 门把进度按已过道数恢复
- **WHEN** 一个运行停在 `gate k`(0..k-1 已过),随后恢复
- **THEN** 从第 k 道门把续跑,0..k-1 不重跑

### Requirement: 引擎执行器——幂等的 ensure 操作

`engine` 执行者的每个操作 SHALL 实现为一个**幂等调谐器**:先**探测** git/fs 实际状态,已达目标即 no-op,否则补齐(reconcile-by-probe)。引擎为运行的**每个成员仓**各构造一套 ensure 上下文(各绑该成员的仓路径、逐仓解析的基分支);执行一个引擎节点时,SHALL 先按节点 `target`(见 `repo-targeting`)解析出成员仓子集,再对子集中每个成员各执行一次对应操作。引擎 MUST 支持以下操作,各以「确保某状态成立」语义实现,且对「目标已达 / 目标未达 / 存在半成品残留」三态都安全收敛:

- `create-branch`:确保分支(=卡 slug)存在于该成员仓自身主线为基的期望基点。
- `open-worktree`:确保该分支在期望路径有 worktree(残留半成品先 prune/repair)。
- `link-env`:确保关联环境的 junction 存在且指向正确(指向错则清后重链);亦用于联调——把兄弟成员仓 worktree 链进 hub worktree。
- `merge-branch`:确保来源已并入目标(在途合并先 abort);空/已合并分支报 no-op;冲突为终局失败。
- `push-branch`:确保远端分支已是本地 HEAD;非快进/无远端为终局失败;对空分支可 skip 以免建垃圾远端分支。
- `remove-worktree`:确保该 worktree 不存在——删前**无条件防御性解链**(见 `git-write-operations`)。
- `delete-branch`:确保本地分支不存在——若仍被 worktree 检出则**级联**先移除该 worktree;采用安全删,未合并为终局失败(由此天然回收未被改动成员仓的空分支、保护有真实工作的分支)。
- `delete-remote-branch`:确保远端分支不存在。

#### Scenario: 重复执行同一操作收敛为 no-op
- **WHEN** 对同一目标连续执行同一 ensure 操作两次
- **THEN** 第二次探测到目标已达、不重复施加副作用,git/fs 状态不变,均标记成功

#### Scenario: 半成品残留被调谐
- **WHEN** 执行 `open-worktree` 而该路径存在一个被中断留下的半成品/失效 worktree 注册
- **THEN** 操作先清理残留(prune/repair)再补齐,最终达成期望 worktree

#### Scenario: 删分支级联清理检出它的 worktree
- **WHEN** 执行 `delete-branch` 而该分支仍被某 worktree 检出
- **THEN** 操作先对该 worktree 执行 `remove-worktree`(含防御性解链),再删分支

#### Scenario: 逐仓解析各自主线为基
- **WHEN** `create-branch` 命中成员 A(主线 master)与 B(主线 main)
- **THEN** A 的分支基于 master、B 的分支基于 main,各以自身主线为基点

#### Scenario: 未被改动成员仓的空分支被安全删回收
- **WHEN** 某成员仓的卡分支无新提交(未被改动),运行到 `delete-branch` 节点
- **THEN** 安全删 `git branch -d` 成功删除该空/已合并分支;若另一成员有未合并真实提交则其安全删被拒、分支受保护

### Requirement: 失败的四种归宿

引擎处理一个操作的结果 SHALL 只有四种归宿,**绝不停在不可见、无继续路径的死结**:

1. **成功** → 推进下一阶段。
2. **自动处理**:瞬时失败(目录占用、网络抖动、锁等)**有限次**自动重试;某些环境性缺失(关联目标不存在、删云端分支失败)直接**跳过**并记提示。所有重试 MUST 有限次。
3. **交给 agent 自愈**:技术性失败路由给 agent。**引擎节点的合并冲突、命令节点主命令非零退出、命令节点客观门报错** MUST 先经**临时 heal agent** 自愈(见 `node-failure-heal`)——拉起临时读写 agent 在卡工作区改/解、引擎确定性提交并幂等重跑验证,**限次**,超限才回落第 4 类的既有人工决策;**agent 节点**的技术失败仍走 agent 节点自愈(续接原 agent,见 `agent-execution`)。**engine 节点的客观门报错**因无代码可改,不走此类、直接第 4 类。
4. **人工拍板**:涉及**意图取舍 / 破坏性 / 凭据环境**的停顿,以及第 3 类**自愈超限**的回落 → 抛一个**人工决策**、运行进入 `waiting-decision`。

引擎 SHALL **优先自动、其次 agent、最后才打扰人**:只有第 4 类才抛人工决策。

#### Scenario: 瞬时失败有限次自动重试
- **WHEN** 某操作遇到瞬时失败(如 worktree 目录被文件句柄短暂占用)
- **THEN** 引擎按上限自动重试;在限内成功则继续,超限则转为人工决策

#### Scenario: 环境性缺失自动跳过不打扰
- **WHEN** 关联环境目标不存在,或删云端分支因不存在/无权限失败
- **THEN** 引擎自动跳过该步并记一条提示,不抛任何决策、运行继续

#### Scenario: 合并冲突先交 agent 自愈
- **WHEN** 引擎 `merge-branch` 节点遇到合并冲突,且 heal 可用、未超限
- **THEN** 引擎先拉临时 heal agent 尝试自愈(第 3 类),仅在超限时才回落人工决策

#### Scenario: 意图/破坏性失败抛人工决策
- **WHEN** 某操作遇到需人拍板的停顿(如删未合并分支、push 非快进、push 无远端)
- **THEN** 引擎抛出对应人工决策,运行进入 `waiting-decision`,不静默

### Requirement: 统一决策的结构与回应

引擎抛出的决策 SHALL 为一个**统一结构**,失败决策与人工门共用:含 `source`、**来源类型** `sourceKind`(`engine` 或 `agent`)、**背景说明**、一组**前进式选项**(各带 `id`、一句话 `label`、可选 `detail`、可选 `recommended`)、可选 `multi`(单选/多选)、可选 `input`(填空,如「远端仓库地址」)。

**选项一律前进式**:每个选项都使运行继续(继续/跳过本节点/重做/换法),决策 MUST NOT 含「中止」「暂不处理」这类使运行卡死、无继续路径的选项。

**除人工评审门外的决策 SHALL 恒带一个自由输入框**(不另设「继续问 AI」按钮——追问即在该框输入);**人工评审门**(`manualReview`)本能力内 MUST **不**渲染自由输入框(其驳回需要「退回哪个节点」的只读回退判定 + 内容驱动回退,该基建本能力不实现)。用户 SHALL **选一个选项、和/或在自由输入框写内容,再提交才正式生效**。提交后:**只选内置选项、无自由文本** → 引擎按选项语义续跑;**含自由文本** → 转交 AI 处理,按有无当前 agent 路由:

- **当前有 agent 在跑本节点**(agent 节点提问/自愈超限,含正在跑的 heal agent)→ 把选中项/自由文本经**续接注入当前 agent**。
- **当前无 agent**(engine/command 失败决策、客观校验门失败决策)→ **新起一个读写处置 agent**(复用 agent 执行器、cwd = 卡工作区):喂「失败背景 + 用户自由输入」,令其**能改就改**(不自己提交,引擎提交后重跑该操作验证)、**不能改就经握手解释并把处置建议作为新选项交回用户**。

本能力产生的失败决策 `sourceKind` **恒为 `engine`**。引擎决策**不写指导文案**(如何配凭据等"指导"是 agent 的职责)。

用户回应 SHALL 为 `{ optionId? | optionIds? | text? }`;引擎按回应续跑(跳过/强制/重试/换参/先合并再删/按填入的地址配置远端/把自由文本注入当前 agent 或新起处置 agent 等),并清除该待决策。

#### Scenario: 失败决策为统一结构且选项全前进式带自由输入
- **WHEN** 引擎为某需人拍板的失败抛决策
- **THEN** 决策含 `sourceKind`、背景、一组前进式选项与**一个自由输入框**,**不含**「中止」类死结选项

#### Scenario: 人工评审门不渲染自由输入框
- **WHEN** 引擎为一道人工评审门抛决策
- **THEN** 该决策只含「通过」类前进式选项,**不**渲染自由输入框(其驳回回退判定本能力不实现)

#### Scenario: 纯选项回应按语义续跑
- **WHEN** 用户对一个待决策只选某选项、未写自由文本(如删未合并分支选「先合并再删」)
- **THEN** 引擎按该选项语义继续(先合并再删),并清除待决策

#### Scenario: 有当前 agent 时自由文本注入当前 agent
- **WHEN** 一个决策当前有 agent 在跑本节点,用户写了自由文本并提交
- **THEN** 引擎把选中项/自由文本经续接注入当前 agent 续跑,而非丢弃

#### Scenario: 无当前 agent 时自由文本新起读写处置 agent
- **WHEN** 一个 engine/command 失败决策(无当前 agent)被写入自由文本并提交
- **THEN** 引擎新起一个读写处置 agent(cwd = 卡工作区),喂「失败背景 + 用户自由输入」,令其改代码(引擎提交后重跑验证)或经握手解释并把建议作为新选项交回

#### Scenario: 需填信息的决策携带填空
- **WHEN** push 因无远端失败
- **THEN** 决策携带一个 `input`(标签「远端仓库地址」)与「跳过推送」选项;用户填入地址回应后,引擎配置远端并重推,或选跳过则继续

### Requirement: 人工评审门复用决策回路

**人工评审**门把 SHALL 复用统一决策结构(`sourceKind: 'engine'`):进入该门把时,引擎抛一个决策,运行进入 `waiting-decision`。该决策 MUST 携带**唯一前进选项 `通过`** 与**自由输入框**;选「通过」且未写自由输入则过门进下一阶段。它与失败决策共享同一运行态、同一断点恢复、同一回应入口。

**驳回走内容驱动回退**:**自由输入框即驳回入口**——用户在框里写下不满意的点并提交时,引擎 MUST NOT 过门,而是转入内容驱动回退(拉起只读回退判定 agent → 回退确认 → 重入目标节点前向修复),详见 `content-driven-rollback` 能力。不另设「驳回」按钮(框空时提交禁用,天然保证驳回必带理由)。

#### Scenario: 人工门抛决策并据通过过门
- **WHEN** 执行到一个人工评审门把
- **THEN** 运行进入 `waiting-decision` 并携带唯一 `通过` 选项与自由输入框;用户选「通过」(未写输入)则过门推进

#### Scenario: 写下驳回意见转入内容驱动回退
- **WHEN** 用户在人工评审门自由输入框写下意见并提交
- **THEN** 引擎不过门,转入内容驱动回退

### Requirement: 一次性触发且可取消可恢复的 IPC 契约

引擎 SHALL 经 IPC 暴露:`start(运行请求) → { runId }`(**触发一次、立即返回**,不让渲染层 await 整个运行)、`pause(runId)`、`resume(runId)`、`decide(runId, { optionId? | optionIds? | text? })`、`getRunState(runId)`,以及一个 `progress` **事件通道**(推送节点/阶段进入退出、操作输出、需要决策等事件)。运行生命周期 MUST 由主进程(引擎)持有;渲染层只触发与观察,**关闭窗口 MUST NOT 终止或丢失运行**。

#### Scenario: 触发后立即返回且运行独立存活
- **WHEN** 渲染层调用 `start` 触发一个运行
- **THEN** 立即得到 `runId`,运行在主进程独立推进;期间关闭并重开窗口,运行不丢失,可经 `getRunState` 重新观察

#### Scenario: 经事件通道观察进度
- **WHEN** 一个运行推进(进入/退出节点与阶段、产生操作输出、抛决策)
- **THEN** 渲染层经 `progress` 事件通道收到对应事件

#### Scenario: 暂停与恢复经 IPC 控制
- **WHEN** 渲染层调用 `pause` 再 `resume` 某运行
- **THEN** 运行在阶段边界进入 `paused` 后又从断点续跑

### Requirement: 非引擎执行者在本能力内被跳过

引擎执行循环 SHALL 识别全部四类执行者(`agent`/`engine`/`command`/`subworkflow`)。`engine`、`command` 与 **`agent`** **真正执行**——`agent` 节点委派 `agent-execution` 能力落地（无头 adapter 拉起、握手、续接、自愈、越界检测 + 每节点提交、同节点多仓由一个 agent 跨仓承担）。**仅 `subworkflow` 仍未落地**:遇到 `subworkflow` 节点,引擎 MUST 发一条「执行器未落地、跳过」的进度事件并直接过到该节点 `done` 阶段,**不报错、不卡住**。这使含占位 subworkflow 节点的工作流仍能端到端跑完。

#### Scenario: agent 节点真正执行而非跳过
- **WHEN** 工作流含一个 `agent` 节点
- **THEN** 引擎调用 agent 执行器（在成员仓 worktree 无头拉起 agent CLI 干活），据握手/门/越界结果推进或自愈，而非发「跳过」事件

#### Scenario: 占位 subworkflow 节点被跳过而非阻断
- **WHEN** 工作流含一个 `subworkflow` 节点
- **THEN** 引擎发「跳过」进度事件并推进到下一节点,运行不因此报错或停滞

#### Scenario: command 节点不再被跳过
- **WHEN** 工作流含一个 `command` 节点
- **THEN** 引擎真正执行其命令(而非发「跳过」事件),并据执行结果推进或抛决策

### Requirement: 命令节点的执行

一个 `command` 执行者 SHALL 声明**一条或多条命令**(`commands: CommandSpec[]`,每条 `{ label?, command, check?, timeoutSec? }`)。引擎执行该 `command` 节点的 `executing` 阶段时 SHALL 经**可取消的命令运行器**(见 `command-execution`)在**节点 worktree**(`worktreePath`,无则回落主仓 `repoPath`)下**并发**跑其全部命令,各自流式捕获输出与退出码。每条命令**各自**:走各自的前置检查护栏(`check`)、各自的超时(`timeoutSec`)、各自可被中途打断,并把输出流式发入**各自的前台桶**(见「命令输出按命令/后台任务分桶缓冲且可回看」——键含命令序号,互不混)。

`executing` 阶段的处置为:**全部命令自然退出 0** → 该阶段成功(进而进入门把或 `done`);**任一命令非零退出或超时** → 引擎 SHALL 杀掉本节点其余仍在跑的命令,并按「命令节点失败的归宿」/「每条命令的可选超时」抛该命令的失败/超时决策(决策标明是哪条命令,不显示退出码);**被取消**按「executing 阶段可被中途打断」处理。单命令节点(`commands` 恰一条)是本要求的退化,行为与单命令等同。

#### Scenario: 单命令节点成功推进
- **WHEN** 执行一个无门、`commands` 恰一条的 `command` 节点,其命令退出码为 0
- **THEN** 该节点经 `executing` 进入 `done` 并推进到下一节点

#### Scenario: 多命令并发各自分桶
- **WHEN** 执行一个 `commands` 为两条的 `command` 节点,两条命令同时产出输出
- **THEN** 两条命令并发执行,各自输出进各自的前台桶(键含命令序号),读一桶不含另一条命令的输出

#### Scenario: 全部命令退出 0 才算节点成功
- **WHEN** 一个多命令节点的全部命令都以退出码 0 结束
- **THEN** 该 `executing` 阶段成功,进入门把或 `done`

#### Scenario: 一条命令失败则收其余并抛决策
- **WHEN** 一个多命令节点里某条命令非零退出(或超时)
- **THEN** 引擎杀掉本节点其余仍在跑的命令,抛该命令的失败(或超时)前进式决策(标明是哪条命令、不显示退出码),运行进入 `waiting-decision`

#### Scenario: 命令在节点 worktree 下执行
- **WHEN** 引擎执行一个 `command` 节点
- **THEN** 其各条命令的工作目录为该运行的 worktree 路径(无则回落主仓路径)

### Requirement: 命令节点的前置检查护栏

`command` 执行者 MAY 携带一条可选**前置检查命令**(`check`)。引擎执行该 `command` 节点的 `executing` 阶段时 SHALL:若声明了 `check`,**先**跑 `check`——其退出码为 0(视为「目标已完成」)则**跳过主命令**、该阶段直接成功(reconcile-by-probe,不重复执行);`check` 非零(视为「尚未完成」)才跑主命令。未声明 `check` 时直接跑主命令(默认每次重跑)。

此护栏使中断恢复**无需询问用户**:恢复时引擎照常重跑 `executing`——带 `check` 的命令(如数据库迁移、版本号自增)因前置探测而幂等收敛、不重复执行;不带 `check` 的命令(如测试、构建)重跑本就无害。引擎 MUST NOT 为命令的重跑向用户抛「重跑还是跳过」之类的判断决策。

#### Scenario: 前置检查通过则跳过主命令
- **WHEN** 一个 `command` 节点声明了 `check`,执行时 `check` 退出码为 0
- **THEN** 引擎跳过主命令、该 `executing` 阶段直接成功,不重复执行主命令

#### Scenario: 前置检查不通过才执行主命令
- **WHEN** 一个 `command` 节点声明了 `check`,执行时 `check` 退出码非零
- **THEN** 引擎执行主命令,并据其退出码推进或处理失败

#### Scenario: 未声明前置检查则默认重跑
- **WHEN** 一个未声明 `check` 的 `command` 节点被(首次或恢复后)执行
- **THEN** 引擎直接执行其主命令,不抛任何「是否重跑」的决策

#### Scenario: 中断恢复经前置检查自动收敛
- **WHEN** 一个声明了 `check` 的 `command` 节点在执行后被中断,其后引擎恢复并重跑该 `executing`,且此时 `check` 已通过
- **THEN** 引擎据 `check` 跳过主命令、自动收敛,不重复执行、不询问用户

### Requirement: 命令节点失败的归宿

当 `command` 节点的主命令**非零退出**(技术性失败,如测试未过/构建失败)时,引擎 SHALL **先经临时 heal agent 自愈**(见 `node-failure-heal`):拉临时读写 agent 在命令的工作区改代码、引擎提交后**重跑该命令**验证,退 0 即收敛、继续。**限次**;超限 SHALL 回落到一个**人工前进式决策**(`sourceKind: 'engine'`),携带 `重试 / 跳过本节点` 这类前进式选项,运行进入 `waiting-decision`;命令、退出码与输出 MAY 进决策的 `raw` 字段供开发/测试排查(正式 UI 不渲染)。非零退出 **MUST NOT** 被当作瞬时失败而自动重试。

#### Scenario: 命令非零退出先 heal
- **WHEN** 一个 `command` 节点的主命令以非零退出码结束,且 heal 可用、未超限
- **THEN** 引擎拉临时 heal agent 改代码并重跑该命令验证,而非直接抛决策

#### Scenario: 命令 heal 超限抛前进式决策
- **WHEN** 命令主命令非零退出的 heal 达到重试上限仍未过
- **THEN** 引擎抛一个含 `重试 / 跳过本节点` 的前进式决策,运行进入 `waiting-decision`,不静默卡住、不自动重试

#### Scenario: 决策续跑按选项语义
- **WHEN** 用户对命令失败决策选「重试」或「跳过本节点」
- **THEN** 引擎据选项重跑该节点或跳过推进,并清除待决策

### Requirement: executing 阶段可被中途打断

对**可被中途打断**的执行者(`command`),引擎 SHALL 支持在其 `executing` 阶段进行中**真正打断**正在运行的子进程(杀整棵进程树)。暂停一个运行时,若其当前 `executing` 阶段有命令在跑,引擎 MUST 终止该命令,并在阶段边界把断点落在 `executing`、运行态置 `paused`。被打断(`killed`)**不**被当作命令失败,**不**抛失败决策。恢复时从 `executing` 续跑(对带 `check` 的命令经前置检查收敛,对其余命令重跑)。

#### Scenario: 暂停杀掉正在跑的命令
- **WHEN** 一个运行的 `command` 节点命令正在执行时用户暂停该运行
- **THEN** 引擎终止该命令(及其子孙进程),断点落在 `executing`、运行态为 `paused`,且不抛失败决策

#### Scenario: 被打断后恢复续跑
- **WHEN** 一个在 `executing` 被暂停打断的命令运行随后被恢复
- **THEN** 引擎从 `executing` 续跑该节点(带前置检查者据检查收敛、其余重跑)

### Requirement: 客观门把执行真实命令

客观(自动校验)门把的评估 SHALL **真正执行**其校验命令(而非恒通过的桩):校验为 `inline` 时直接跑其裸命令字符串;为 `ref` 时解析规则库 `objective-check` 条目得到命令再跑。命令在节点 worktree(`worktreePath` 真存在则用它,否则回落 `repoPath`)下经可取消运行器执行;退出码为 0 即该门**通过**(并清零该门的重试计数)、进下一道。门未通过时按「客观门失败的自动重试与升级」处理。`ref` 引用的条目在本机缺失时 MUST 按缺失上报、不崩。

#### Scenario: inline 门命令通过则过门
- **WHEN** 一道 `inline` 客观门把的命令退出码为 0
- **THEN** 该门通过,阶段推进到下一道门(或 `done`),该门重试计数清零

#### Scenario: ref 门解析规则库条目后执行
- **WHEN** 一道 `ref` 客观门把引用一个存在的 `objective-check` 条目
- **THEN** 引擎解析该条目得到命令并执行,据退出码过门或进入重试/升级

#### Scenario: ref 条目缺失按缺失上报
- **WHEN** 一道 `ref` 客观门把引用的规则库条目在本机不存在
- **THEN** 引擎按缺失上报(进度事件/决策),不抛未捕获异常、不静默卡住

### Requirement: 客观门失败按原因与节点类型分流

客观门未通过时,引擎 SHALL 按**失败原因**与**当前节点执行者类型**分流处理,对齐失败四归宿:

- **门报错(非零退出)且节点为 `command`**:MUST **先经临时 heal agent 自愈**(见 `node-failure-heal`)——拉临时读写 agent 在节点工作区改代码、引擎提交后**重跑该门**验证;**限次**;超限再抛人工决策。
- **门报错(非零退出)且节点为 `engine`**:确定性操作无代码可改,MUST **直接抛人工决策**(不自动重跑、不 heal)。
- **门报错(非零退出)且节点为 `agent`**:MUST 触发 **agent 节点自愈**——**续接原 agent**(见 `agent-execution`「续接阶梯」)、注入「哪道门为何没过」详情令其重做,有限次(≤3);仍不过再抛 `sourceKind='agent'` 人工决策。`subworkflow` 节点门报错仍作占位(自动重跑整个节点有限次后抛决策),其执行本能力内被跳过、门暂不触发。
- **门超时(任何节点类型)**:多为抖动/慢,**自动只重跑该客观门**有限次(≤3),仍不过再抛人工决策。

自动重跑/heal 的次数与历史 MUST 按**「该运行在该门把」**(heal 则按 `(节点,成员仓)`)累计并**持久化到断点**(关闭重开后计数不丢);门**通过**时清零。

决策 MUST NOT 向用户显示**退出码**(属开发排查信息,仅进 `raw`);MUST 改以**检查命令自身的输出**作为用户可读的失败**原因**(`reason`)呈现。决策选项至少含 `重跑此检查 / 重跑本节点 / 跳过此检查`;因超时多次升级时 MAY 附带重试历史(每次原因与重跑粒度,不含退出码)。

#### Scenario: 命令节点门报错先 heal
- **WHEN** 一道客观门把命令非零退出,且其节点执行者为 `command`,heal 未达上限
- **THEN** 引擎先拉临时 heal agent 改代码并重跑该门,超限才抛人工决策

#### Scenario: 引擎节点的门报错直接交用户
- **WHEN** 一道客观门把命令非零退出,且其节点执行者为 `engine`
- **THEN** 引擎不自动重跑、不 heal,直接抛人工决策(运行进入 `waiting-decision`),决策以检查输出为可读原因、不显示退出码

#### Scenario: agent 节点门报错触发续接自愈
- **WHEN** 一道客观门把命令非零退出,且其节点执行者为 `agent`,重试未达上限
- **THEN** 引擎续接原 agent、注入该门失败详情令其重做(而非新拉临时 agent),累加一次记录、不抛决策;达上限抛 `sourceKind='agent'` 人工决策

#### Scenario: 门超时自动重跑该门有限次后升级
- **WHEN** 一道客观门把命令超时且该门重试未达上限
- **THEN** 引擎自动只重跑该客观门、累加一次「超时/门」记录、不抛决策;达上限仍超时则抛人工决策

#### Scenario: 计数关闭重开后仍准、通过即清零
- **WHEN** 一个运行在某门超时/heal 重试若干次后被关闭并恢复,随后该门最终通过
- **THEN** 恢复后重试计数延续(不因重启清零),门通过后该门计数与历史清零

### Requirement: 人工门动作按钮以独立后台进程执行

人工评审门声明的**动作按钮**被触发(`runGateAction(runId, actionIndex)`)时,引擎 SHALL 把该动作的命令**登记为该运行的一条后台命令**并按后台命令语义执行:铸一个 `bgId`、以该动作文案为 label 登记(命令、所属节点、可选超时随之),流式输出经 `op-chunk` **带上该 `bgId`**(归入桶 `bg:<bgId>`)、命令进程句柄进该运行的后台活进程表。触发 SHALL **立即返回该动作的 `bgId`**(不 await 命令跑完——动作多为不退出的 dev server),该动作进程 MUST 可经既有**中止指定后台命令**入口(按 `bgId`)独立停止。

动作进程的生命周期取**后台命令**语义:run 走到终局(`done`/`aborted`)时随后台一并被杀并清记录;关软件时杀活进程。但动作是**用户手动触发的旁路进程**,MUST NOT 随开机恢复(`resumeAll`)自动拉起——重开后由用户手动再触发。

同一个动作按钮(以 `(节点, 动作索引)` 为身份)在同一时刻 MUST 至多有一条活进程:该动作已有活进程时再次触发 SHALL 先停旧再起新(不叠加 spawn),使其运行态可派生、按钮可呈现为「中止」。该动作的 `bgId` MUST **按按钮身份稳定**(启动→中止→再启动复用同一 `bgId`,即复用同一格输出、不攒新窗口);再启动时其输出桶 MUST 被**清空**,使复用的输出格只呈现本次输出、不残留上次(崩溃/中止)的旧内容。

引擎 MUST 保证以上各情形不留孤儿进程,且触发/中止某动作 MUST NOT 影响同节点其它动作或命令。

#### Scenario: 动作按钮触发起独立后台进程
- **WHEN** 用户触发一道人工评审门的某个动作按钮
- **THEN** 引擎为其铸 `bgId`、登记为后台命令、流式输出带该 `bgId` 归入 `bg:<bgId>` 桶,并立即返回该 `bgId`(不等命令结束)

#### Scenario: 两个动作各自独立且可分别中止
- **WHEN** 用户先后触发两个动作按钮(如启动后端、启动前端),两条命令同时在跑
- **THEN** 两条命令各进各自 `bg:<bgId>` 桶、各持独立中止句柄;中止其一(按 `bgId`)不影响另一条,不留孤儿进程

#### Scenario: 重复触发同一动作是先停后起、复用同一格
- **WHEN** 一个动作按钮已有活进程时用户再次触发同一动作
- **THEN** 引擎先停掉该动作的旧进程再起新进程,同一时刻该动作至多一条活进程(不叠 spawn);新进程复用同一 `bgId`(同一格输出),其输出桶被清空后只含本次输出、不残留上次内容

#### Scenario: run 终局收掉动作进程
- **WHEN** 一个有活动作进程的运行走到 `done` 或 `aborted`
- **THEN** 该动作进程随后台命令一并被杀、记录清空,不留孤儿

#### Scenario: 关软件后动作不自动拉起
- **WHEN** 一个有活动作进程的运行随应用关闭后重开
- **THEN** 动作进程在关闭时已被杀,重开后**不**随 `resumeAll` 自动拉起,由用户手动再触发

### Requirement: 命令节点的手动推进与后台化

command 节点在其命令运行期间(`executing` 进行中),引擎 SHALL 提供两个**手动推进**入口,使长驻命令不阻塞运行:**中止并进入下一节点**(杀掉本节点**尚在跑的全部命令**的整棵进程树后推进)、**进入下一节点(转后台)**(**不杀**本节点尚在跑的命令、将它们**各自**移入按运行维护的**后台命令登记**——每条各得一个 `bgId`、各自携带其转后台前的前台输出——后推进)。两者都使运行推进到下一节点并**跳过本节点剩余门把**。多命令节点转后台时,其尚在跑的每条命令**各成一条独立后台命令**(各自 bgId/桶/中止)。

被转入后台的命令 MUST **继续流式输出**(经 `op-chunk`,归各自 `bg:<bgId>` 桶),且引擎 MUST 提供**列出**某运行的后台命令与**中止**指定后台命令的入口。后台命令以一份**可重启记录**(命令、所属节点、标识)**持久化于断点**,使其生命周期如下:

- **被用户中止 / 其所属运行抵达终局(`done`/`aborted`)**:杀掉进程树**并清除记录**(不再重启)。
- **暂停**:杀掉后台进程树(暂停即一切静止)、但**保留记录**;**恢复**时按记录**重新拉起**。
- **应用退出**(关软件 = 自动暂停):杀掉进程树**保留记录**,重开时按记录恢复。
- **超时跟随到后台**:若该命令声明了超时,转后台后该超时**仍生效**——后台进程到点 MUST 被杀掉(并摘除记录);因其为旁路进程,**不**抛运行级决策。暂停恢复/重开重启时按记录**重新计时**。

引擎 MUST 保证以上各情形都不留孤儿进程。手动推进(中止或转后台)**不**被当作命令失败,**不**抛失败决策。

#### Scenario: 中止并进入下一节点
- **WHEN** 一个 command 节点命令运行时用户选择「中止并进入下一节点」
- **THEN** 引擎杀掉本节点尚在跑的全部命令(及其子孙进程)并推进到下一节点,跳过本节点剩余门把,不抛失败决策

#### Scenario: 多命令转后台各成独立后台命令
- **WHEN** 一个有两条尚在跑命令的 command 节点被用户选择「进入下一节点(转后台)」
- **THEN** 引擎不杀这两条命令、将它们各自移入后台命令登记(各得独立 bgId/桶/中止,各携带其转后台前的前台输出)并推进到下一节点;两条命令继续运行与各自流式输出

#### Scenario: 后台命令可列出、可中止、退出时不留孤儿
- **WHEN** 某运行有后台命令,用户中止其一(或应用退出)
- **THEN** 该后台命令的整棵进程树被杀掉、从登记移除;应用退出时所有后台命令被杀掉,不留孤儿进程

#### Scenario: 工作流完成时后台命令被同步收尾
- **WHEN** 一个运行抵达终局(`done`/`aborted`)而仍有后台命令
- **THEN** 引擎同步杀掉该运行的全部后台命令(连进程树)并清除其记录,不遗留

#### Scenario: 暂停杀后台并保留记录、恢复重新拉起
- **WHEN** 一个运行有后台命令,随后被暂停
- **THEN** 后台进程被杀掉(一切静止)、但其可重启记录保留;随后恢复时引擎按记录重新拉起这些后台命令

#### Scenario: 后台命令记录持久化、关软件重开可恢复
- **WHEN** 一个有后台命令的运行随应用退出(关软件 = 自动暂停)后,应用重开并恢复该运行
- **THEN** 引擎据持久化的后台记录重新拉起这些后台命令(进程不留孤儿、记录不丢失)

#### Scenario: 后台命令到超时被杀
- **WHEN** 一个声明了超时的命令被转入后台,且其后台进程运行超过该超时
- **THEN** 引擎杀掉该后台进程并摘除其记录,不抛运行级决策

### Requirement: 每条命令的可选超时

引擎执行的**每一条命令**(命令节点主命令、客观门把命令、人工门把动作命令)SHALL 各自支持一个**可选超时**(`timeoutSec`);超时为**每条命令独立**的属性(同一节点的主命令与客观门可设不同时限),未声明即**无超时**(全局默认无超时)。当一条命令运行超过其 `timeoutSec` 时,引擎 MUST 杀掉其整棵进程树并按**失败**处理(非用户主动暂停,故不落 `paused`):命令节点主命令超时 → 抛前进式「命令超时」决策(`重试 / 跳过本节点`);客观门超时 → 抛前进式「检查超时」决策(`重试 / 跳过此检查`);门把动作超时 → 仅终止该动作并回显「已超时」,不抛运行级决策。`npm start` 等长驻命令通过**不声明** `timeoutSec` 即不被超时。

#### Scenario: 命令节点主命令超时抛决策
- **WHEN** 一个声明了 `timeoutSec` 的命令节点主命令运行超过该时限
- **THEN** 引擎杀其进程树并抛前进式「命令超时」决策,运行进入 `waiting-decision`(不落 `paused`)

#### Scenario: 客观门命令超时抛决策
- **WHEN** 一道声明了 `timeoutSec` 的客观门把命令运行超过该时限
- **THEN** 引擎杀其进程树并抛前进式「检查超时」决策

#### Scenario: 未声明超时的长驻命令不被超时
- **WHEN** 一条未声明 `timeoutSec` 的命令(如长驻服务)持续运行
- **THEN** 引擎不因时间而终止它(仅可被 `pause`/动作停止显式打断)

### Requirement: 流式输出进度事件

引擎在执行命令(命令节点、客观门、动作按钮)产生输出时 SHALL 经 `progress` 事件通道发**流式输出事件**(`op-chunk`),承载运行 id、节点 id、来源流(stdout/stderr)与增量文本块,使消费方可实时回显长命令或永不退出命令的输出。终态摘要(退出码/归宿)仍由既有 `op-output` 事件承载。

#### Scenario: 命令输出经流式事件实时推送
- **WHEN** 一条命令在执行中持续输出
- **THEN** 引擎以增量 `op-chunk` 事件推送其 stdout/stderr,消费方无需等命令结束即可回显

#### Scenario: 终态摘要仍由 op-output 承载
- **WHEN** 一条命令结束
- **THEN** 引擎发一条 `op-output` 终态摘要(含归宿/退出码),与流式 `op-chunk` 并存

### Requirement: 运行触发非阻塞且暂停可即时打断

引擎的 `start`/`resume`/`decide` SHALL **不等待整个运行跑完**:持久化(初始/更新)断点后在后台驱动运行,并**立即**给出一个**运行标识**(`runId`)与一个**到停点即兑现的 awaitable**(下记 `settled`)——`settled` 在运行进入停点(`done` / `waiting-decision` / `paused` / `aborted`)时兑现为彼时的断点。**不想等结果**的调用方(IPC/渲染层)取 `runId` 即返回、MUST NOT 等待 `settled`(经事件通道与 `getRunState` 观察后续);**需要结果**的调用方(如测试)await `settled` 拿到停点断点。`settled` MUST NOT 经 IPC 跨进程传递(IPC 只回当前断点)。

运行生命周期由主进程持有,长命令运行不阻塞渲染层调用、关闭窗口不产生孤儿调用。`pause` MUST 能**即时**作用于一个正在驱动中的运行(包括打断其 `executing` 阶段在跑的命令),而非等到当前长操作自然结束;引擎 MUST 保证暂停态不被后台驱动循环回写覆盖。

#### Scenario: 触发长命令运行后立即返回
- **WHEN** 渲染层(经 IPC)`start` 一个含长命令节点的运行
- **THEN** 立即返回当前断点(运行态为 `running`),不等待运行跑完;运行在主进程后台推进,期间关窗不产生挂起的孤儿调用

#### Scenario: 需要结果的调用方等到停点
- **WHEN** 一个调用方 `start`/`resume`/`decide` 后 await 其 `settled`
- **THEN** `settled` 在运行进入下一个停点(done/waiting-decision/paused/aborted)时兑现为彼时的断点

#### Scenario: 暂停即时打断长命令
- **WHEN** 一个运行正在 `executing` 跑一条长命令时调用 `pause`
- **THEN** 该命令被即时打断,运行在阶段边界落 `paused` 并持久化,该暂停态不被后台驱动覆盖回 `running`

### Requirement: 命令输出按命令/后台任务分桶缓冲且可回看

引擎 SHALL 在流式推送命令输出(`op-chunk`,见「流式输出进度事件」)之外,把命令输出**按桶累积缓冲**并持久化于该运行,使其可在事件流过之后**回看**(含关闭重开后):

- **前台节点命令**:一个 command 节点的**每条命令各一桶**,键为 `node:<nodeId>:<命令序号>`(单命令节点即其唯一命令一桶);
- **每个后台命令**各一桶,键为其 `bgId`(`background[].bgId` 已是天然分桶键);**人工门动作按钮触发的命令亦为后台命令**,同样各占一桶(`bg:<bgId>`),MUST NOT 归入前台节点桶。

**通用契约**:一个节点在同一时刻**并发运行的多条命令**(前台各命令、转后台命令、门动作进程等),MUST 各进各自的桶、各持独立中止句柄——任一条的输出或中止 MUST NOT 影响另一条。缓冲 MUST 与运行生命周期对齐:同一运行的不同桶**互相隔离**;运行进入终局后缓冲 MAY 保留以供回看,按容量策略回收。引擎 SHALL 提供按桶键读取已缓冲输出的入口,供消费方(卡详情面板)分流展示。

一条命令**转后台后,其后续输出 MUST 归入该后台命令的桶**(`bg:<bgId>`),不再进前台命令桶——否则后台命令输出视图会恒为空。**转后台时,该命令转后台前已产出的前台输出 MUST 一并并入 bg 桶**,使后台输出视图呈现从头到尾的完整输出(而非只有转后台之后的部分)。

后台命令的登记变化事件(`background`)MUST 能区分终止原因:用户中止(`stopped`)、自行退出(`exited`)、**超时被杀(`timeout`)**——使消费方能对"计时中止"给出明确终态、而非与自然退出混同。

#### Scenario: 前台多命令各自分桶隔离
- **WHEN** 一个 command 节点有两条前台命令同时产出输出
- **THEN** 两条命令各进 `node:<nodeId>:0` / `node:<nodeId>:1` 桶,读一桶只得该命令输出,互不混入

#### Scenario: 前台与后台命令输出分桶隔离
- **WHEN** 一个运行有前台节点命令与一个以上后台命令(含动作进程)同时产出输出
- **THEN** 各命令的输出进各自的桶,读取某桶只得该命令的输出,互不混入

#### Scenario: 同节点并发多命令各自分桶且可独立中止
- **WHEN** 同一节点上有两条以上并发命令(前台多命令、或两个动作按钮进程)同时在跑
- **THEN** 每条各占一桶、各持独立中止句柄,中止其一不影响另一条,读一桶不含另一条输出

#### Scenario: 转后台后输出归后台桶
- **WHEN** 一条正在前台执行的命令被转入后台,其后续继续产出输出
- **THEN** 转后台后的输出进该后台命令的桶(`bg:<bgId>`),后台命令输出视图可读到(非空)

#### Scenario: 转后台带走转后台前的前台输出
- **WHEN** 一条命令在前台已产出若干输出后被转入后台
- **THEN** 转后台前的前台输出被并入该后台命令的桶,后台输出视图从头呈现完整输出(不丢转后台前的部分)

#### Scenario: 后台命令超时被杀发可区分的 timeout 事件
- **WHEN** 一个带超时的后台命令到点被引擎杀掉
- **THEN** 引擎发 `background` 事件 `status: 'timeout'`(与用户中止 `stopped`、自然退出 `exited` 相区分),不留孤儿进程

#### Scenario: 输出可在流过之后回看
- **WHEN** 一条命令的输出已流式推送完毕,消费方此后请求该命令的已缓冲输出
- **THEN** 引擎返回该命令累积的输出(不止实时片段)

#### Scenario: 关闭重开后缓冲仍可读
- **WHEN** 一个产生过命令输出的运行随应用关闭后重开
- **THEN** 引擎据持久化缓冲仍能按桶键返回运行期内已缓冲的输出

### Requirement: 断点记录节点路径(子工作流穿透留口)

运行断点 SHALL 可选地记录一条**节点路径** `nodePath`——从顶层节点指向当前实际执行的最内层节点的序列,用于将来子工作流(subworkflow)运行时"以内部节点而非顶层节点"呈现当前位置。本能力 `subworkflow` 执行被跳过,故 `nodePath` 恒只含顶层当前节点一项(或缺省,等价于 `[currentNodeId]`);消费方(看板圆点)读其末项作当前节点名。该字段为数据留口,MUST NOT 改变本能力的执行/恢复行为。

#### Scenario: 本期节点路径只含顶层
- **WHEN** 引擎执行一个非子工作流节点并写断点
- **THEN** `nodePath` 缺省或恒只含当前顶层节点;消费方读末项即得当前节点 id

#### Scenario: 字段为留口不影响恢复
- **WHEN** 引擎加载并恢复一份带或不带 `nodePath` 的断点
- **THEN** 恢复行为与本字段无关(按 `currentNodeId` 与 `phase` 续跑),`nodePath` 仅供展示

### Requirement: 后台命令结束不回退主流程断点

后台命令结束(自行退出 / 超时被杀)时,引擎摘除其可重启记录 MUST 作用于**当前持久化断点**,而非某个在转后台时捕获的、可能已过期的断点引用。因为主流程可能已越过一个 `decide`/`resume` 边界推进到更后的节点(新断点),若回写捕获的旧断点会把 `currentNodeId` 覆盖回旧节点,造成运行"莫名跳回上一步"。故后台命令的结束处理 MUST 读当前断点、仅从中移除自己的记录再保存。

#### Scenario: 后台命令超时结束不覆盖已推进的断点
- **WHEN** 一条命令转后台(带超时)后,主流程经人工门 `decide` 推进到更后的节点,期间该后台命令超时被杀
- **THEN** 运行断点仍停在已推进到的节点(不被后台命令的结束处理回写覆盖回转后台时的旧节点)

### Requirement: 默认全建后未用成员仓的回收

当 `create-branch`/`open-worktree` 以 `target=all`(解析为卡 `repos` 全集)在涉及仓建分支后,未被改动的成员仓 SHALL 通过既有节点自然回收,**无需新增 GC 操作**:`merge-branch` 对其空分支报 no-op,`delete-branch` 经安全删将其回收。GC 路径上的 worktree 移除 SHALL 沿用「绝不无脑 --force」红线——成员仓 worktree 含未提交改动时 MUST 拒绝删除并表现为可见停点,绝不静默抹掉未提交工作。

#### Scenario: 前后端都改时两仓分支都保留合并
- **WHEN** 卡涉及仓 A、B 且两仓都有真实提交,走到 merge/delete 节点
- **THEN** 两仓各 merge 回各自主线;两仓分支均非空,安全删按生命周期在合并后回收

#### Scenario: 仅后端被改时前端空分支自然回收
- **WHEN** 卡涉及仓 A、B 但仅 B 有提交,走到 merge/delete 节点
- **THEN** A 的空分支 merge 报 no-op、随后被安全删回收;B 正常合并

#### Scenario: 空分支但 worktree 脏时拒删抛给人
- **WHEN** 某成员空分支但其 worktree 含未提交改动,GC 尝试移除该 worktree
- **THEN** 移除被拒(非 force),运行进入可见停点而非抹掉未提交改动



### Requirement: decide 路由识别评审门驳回

`decide()` MUST 识别「决策 `source` 以 `:manual-gate` 结尾 + 回应含自由输入」这一分支,把它路由到内容驱动回退(拉起只读回退判定 agent),而非按内置前进选项语义(通过/跳过/重试)直接续跑。此路由与既有的「执行阶段失败 + 自由输入 → 处置 agent」「agent 运行时提问 → 续接当前 agent」并列,互不干扰。

#### Scenario: 评审门自由输入路由到判定 agent
- **WHEN** `decide()` 收到 `source` 以 `:manual-gate` 结尾且带 `text` 的回应
- **THEN** 引擎拉起只读回退判定 agent,而非直接过门或跳过

#### Scenario: 非评审门决策路由不受影响
- **WHEN** `decide()` 收到执行阶段失败或 agent 提问来源的自由输入
- **THEN** 仍按既有路由(处置 agent / 续接当前 agent)处理,不误入回退判定

### Requirement: 断点记录最远进展节点与回退判定记账

`RunBreakpoint` MUST 新增 `furthestNodeId` 字段,记录本运行推进到过的最远节点;回退到更早节点后该字段保留,供重入续接注入告知进度。回退判定 agent 的运行状态 MUST 以区别于普通 heal 的记账键(如 `<nodeId>:rollback-judge`)持久化进断点,关软件重开仍可查。

#### Scenario: 前向推进时更新最远进展节点
- **WHEN** 运行推进到一个比 `furthestNodeId` 更靠后的节点
- **THEN** 断点更新 `furthestNodeId` 为该节点

#### Scenario: 回退后最远进展节点保留
- **WHEN** 引擎重入到更早的节点 K
- **THEN** `furthestNodeId` 仍指向回退前的最远节点,不被 K 覆盖

### Requirement: 确认后重入执行

用户确认回退目标节点 K 后,`decide()`(或其调用的重入过程)MUST 把 `currentNodeId` 拨回 K、`phase` 设 `executing`,保留 K..N 各节点的会话续接 token(重锚其越界/提交基线以便前向提交叠加),续接 K 的执行者并注入修复前向上下文,再 `drive()` 前向重流。此过程 MUST NOT 触及 git 写侧的 `reset`。

#### Scenario: 确认回退拨回当前节点并前向重流
- **WHEN** 用户在回退确认决策里选定目标节点 K
- **THEN** 引擎设 `currentNodeId=K`、`phase=executing`,续接 K 的执行者后 `drive()` 前向重流,期间不执行 `git reset`
