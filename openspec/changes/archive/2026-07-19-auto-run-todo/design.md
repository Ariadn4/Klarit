## Context

Klarit 让 vibe coder 只管需求与优先级,执行交给它编排。但今天"执行"只有手动一条路:卡详情 header 的 `▶` 一次拉起一个运行(`requirement-card-detail` 的运行主控 → `requirement-card-store` 的 `deriveRunRequest` → `engine.start` → 卡↔运行双向链)。待办列堆多了就得人肉挨个点。

现状关键事实(定这个设计的边界):
- **全库无任何并发/队列/调度概念**——运行是"人点 → start 一个",`engine.start` 立即返回、后台 `launch` 驱动,谁也不限制同时几个。
- **一卡一分支一运行**:卡的 `proposedName` 即分支名;卡声明它碰哪些**成员仓 `repos: string[]`**。不同卡是不同分支,但**可共享同一个物理仓**——都 merge 回该仓主线时改到同一批文件就冲突。这是"冲突"唯一有意义的度量面。
- **运行终局已被感知**:引擎每次状态变化 `emit`,`index.ts` 的回调据此 `reconcileCardForRun`(`done` → 卡「已完成」)。这就是排程要搭的现成钩子。
- **开机 `resumeAll` 并行恢复**所有 `running` 断点——重启瞬间活跃数可能就 >3。
- 卡有 `blocked_by`/`blocks`/`coupled_with` 关系边(`requirement-card-model`)。

约束(项目宪法):测试先行、针对公共 API 覆盖行为(不为可测性导出私有);动态文档只记最新现状;颜色只用语义令牌(本 change 基本无 UI)。

## Goals / Non-Goals

**Goals:**
- 待办列有资格的 leaf 卡**自动排队跑**,人不必挨个点;**自动并发上限 3**,槽没满贪心补满。
- **只有运行 `done` 与卡进待办**触发补位,并发数稳定收敛、不抖动。
- 候选多于空槽时,**先免费粗筛(共享仓)、再一次 agent 调用**按"与在跑任务的冲突 + 所选集合内部冲突"最小化选一批。
- **手动运行不受节流**、可超上限;排程绝不为让位中止任何运行;容忍开机既成超额。
- 不碰引擎内部:纯复用现成启动接缝 + `emit` 钩子。

**Non-Goals:**
- `abort`/`paused`/`waiting-decision` **不触发**填槽(只 `done`,见 D2)。
- **无"暂缓/草稿"口子**:隐式判定下待办即自动,想挡只能 `blocked_by` 或不进待办(见 D5)。
- 上限 3 不可配置;不接 webhook;不做优先级手调;不跨项目排程。
- 不做冲突的确定性静态分析——repo 粗筛是**充分**证明"不冲突",agent 细判是**预测**、非硬保证(见 D3)。
- 不改引擎 `drive`、不新增引擎能力、不新造事件总线。

## Decisions

### D1 排程住在主进程,挂现有 `emit` + 落库接缝,不放渲染层
排程要感知运行终局、要能 `engine.start`、要读卡库全貌——都在主进程。做成 `src/main/auto-scheduler.ts` 一个常驻回路,对外暴露一个 `evaluate()`。触发它的两类事件:
- **运行 `done`**:搭进 `index.ts` 现有引擎 `emit` 回调(与 `reconcileCardForRun` 同处),`state==='done'` 后调 `evaluate()`。`blocked_by` 的 blocker 完成也是一次 `done` → 自然使被阻塞卡变得有资格,无需单独的"解阻塞"事件。
- **卡进入待办**:卡落库/关系变更接缝后调 `evaluate()`——手动新建(`cardsCreate`)、外部候选落库(`submitDecomposedCandidates`)、关系增删(可能去掉一个 `blocked_by`)。
渲染层不参与排程决策(不轮询、不持有并发状态),只照常经既有 IPC/事件看到卡进入「进行中」。

### D2 补位触发 = `done` ∪ 卡进待办 ∪ **删卡**;`pause`/`waiting-decision` 仍占槽不补
补位触发是"释放了槽位"或"新增了候选"的事件:运行 `done`(释放槽)、卡进待办(新增候选)、**删卡**(删在跑卡→级联中止→释放槽)。而 `paused`/`waiting-decision` 的运行**仍算活跃、仍占一个槽**(它没结束),不触发补位——一个卡在等决策的运行会一直占着 1/3,直到它 `done` 或被删除。
**删卡为何触发**(dogfood 修正):初版把"运行变 `aborted` 不触发"一刀切,导致**删除一个在跑任务腾出槽位后、待办队列不继续**——体验上"卡住了"。修正:UI 里中止一个运行的唯一途径就是**删卡**(`cardsRemove` 级联 `engine.abort`),而删卡是用户显式的"这张不要了、继续排队"意图,**理应补位**。故在 `cardsRemove` 处理器删卡后显式 `scheduleEvaluate`。这与"暂停/等待决策仍占槽不补"不矛盾——那些运行还在、没释放槽;删卡真正释放了槽。(引擎 `aborted` **state 事件本身**仍不触发,避免非删卡路径的抖动;触发点是删卡这个**动作**。)

### D3 冲突处理 = 确定性的共享成员仓判断(无 agent、即时)
**决定移除冲突排序 agent**(初版设计里的 `conflict-rank-producer`),改为纯确定性、即时的规则:
- 以**成员仓重叠**判冲突:候选 `repos` 与"当前在跑卡集合 `repos` 并集"**交集为空** → 分支落在不同物理仓、merge 不可能互撞;有交集 → 视为与在跑共享仓。
- 选取顺序:**与在跑不共享仓者优先**(按入列顺序)→ 再接**共享仓者**(按入列顺序)→ 填满空槽取前 K。多仓下把并行错开到不同仓;单仓下所有卡共享唯一仓,自然退化为**纯按序填槽**。

**为什么移除 agent**(dogfood 暴露):默认 agent 是 claude-code/opus,跑一整轮排序要**几十秒**;单仓下粗筛永远命中、**每次多候选竞争都走 agent**,于是用户"盯着空槽等几十秒"、体感"卡死"。而 agent 的增量价值仅是**文件级**冲突预测(还是预测、非精确)。权衡下:**用户明确要求砍掉 agent、只保留共享仓这一即时判据、其余按序**。文件级智能排序留作未来可选增强(那时再引入注入式产出者,且必须非阻塞)。这也顺带删掉 `conflict-rank-producer.ts` 与在跑卡 `diff 摘要`采集(`card-run-diff.ts`)——它们只为喂 agent 而存在。

### D5 资格隐式、无开关;缺"暂缓"口子是接受的取舍
用户选"靠现有信号隐式判定",不加每卡开关也不加全局总开关。于是**有资格 ⇔ leaf ∧ 在待办(`未开始`∧无 `activeRunId`)∧ 所有 `blocked_by` 目标已「已完成」∧ 派生成功**。含义:一张满足条件的待办卡**必然**会被自动拉起。想把一张卡放进待办却暂时别跑,现有信号里**没有**"暂缓"——只能给它挂个 `blocked_by`,或干脆先别拖进待办。已与用户确认接受"待办即自动"语义;若日后要"暂缓",再引入一个现有信号承载(不在本期)。

### D6 看板实时反映自动启动(异步起卡的显式刷新)
dogfood 暴露:**异步**自动启动的卡不上板——排程在 `evaluate()`(create/`done` 触发)里 `cardStore.update` 置卡「进行中」,但渲染层没重载。原因:渲染层刷卡状态只在①它自己发起动作后(手动 `runCard`/创建流程 `await load()`)②引擎 `state` 事件回推 `load()`;而引擎运行事件里 `node-enter` 只回灌**断点**、不刷**卡状态**,初始 `running` 态又无独立 `state` 变更事件 → **异步起卡后没有任何一次 `load()`**,`cardColumn` 见卡状态仍「未开始」→ 误判入「待办」(实际在跑,CDP 直连渲染层已证 `listCards()` 返回"进行中")。
**修复**:`startCardRun`(手动/自动共用接缝)置卡链后,主进程向所有窗口广播 `cards:changed`,渲染层订阅即 `load()`——与「窗口绑定后通知渲染层」同一套路。并给渲染层 `load()` 加**单调序号防竞态**(并发起多张时,较早发起、较晚返回的陈旧 `load` 不覆盖较新态)。

### D7 并发计数的单一真相来源 + 评估串行化(防竞态)
- **活跃数**取引擎在册运行(`engine` 的 active 运行集合 / 据卡 `activeRunId` 反查),不自己另记一份可能漂移的计数。含**所有**在跑运行(手动+自动、含 paused/waiting-decision 占槽的)。
- **`evaluate()` 串行化**:多个 `done`/落库事件可能几乎同时到达,若并发进入评估会重复选中同一张卡、`engine.start` 两次。用一把"评估中"锁(或把评估请求串成队列)保证**同一时刻至多一个评估在跑**,且评估内对已被本轮选中的卡即时并入"在跑集合",防同卡双启。
- **既成超额容忍**:开机 `resumeAll` 恢复出 >3 个 running 时,`evaluate()` 见活跃≥3 就单纯不填槽,**不中止**任何运行,待自然回落 <3 再补。

## Risks / Open Questions

- **等待决策占槽饿死**:一个长期卡在 `waiting-decision` 的自动运行会一直占 1/3 槽,若三个都卡住,自动并行归零直到人处理。属预期(它们确实没结束),但若实际体验差,可考虑"等待决策不计入自动占槽"——本期先按"占槽"做,留观察。
- **冲突判据的粗粒度**:共享成员仓是"可能冲突"的充分判据、非精确——单仓下所有卡都判"共享",退化为按序;文件级实际是否冲突不判(留未来可选增强)。可接受:未判出的文件级冲突最坏只是并行的两张 merge 时冲突,由既有引擎失败决策兜底,不产生错误。
- **触发点覆盖**:要确保所有"使卡变得有资格"的接缝都触发 `evaluate()`(新建、候选落库、关系增删、blocker 完成)。blocker 完成经 `done` 覆盖;关系增删需在其写接缝显式触发——实现时以测试钉住。

## Migration
纯增量,无数据迁移。手动运行路径与既有双向链、开机恢复、列派生均不变;旧项目加载即获得自动排程,无需任何转换。
