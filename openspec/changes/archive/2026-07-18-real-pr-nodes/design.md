## Context

Klarit 的引擎把需求从「准备 → 实现 → 交付」推下去,交付段现有两条内置工作流都由 **Klarit 自己 `merge-branch`** 本地合并。所谓「PR 模式」只是 push + 一道本地人工门,并不在托管平台上真的开 PR。

真 PR 的现实机制(与用户逐轮敲定):A push 分支 → 在平台上开 PR/MR → **评审与合并都发生在平台上** → 合并后本地还剩「删分支 / 删 worktree」这些**平台够不着的**收尾;且 **PR 被打回改代码是常态**——反馈要能退回改、更新 PR、再等合并。于是引擎需要:①一个「开 PR」的动作(各家平台异构);②一个「**等平台把 PR 合并、合了才收尾;不满意打回改**」的关口——这不是流水线节点,而是**一种新门类**(见 D4)。

约束(项目宪法):测试先行、针对公共 API 覆盖行为;节点名双语;动态文档只记最新现状;引擎操作集与门把模型是 `src/shared` 的单一来源,写工作流 skill 由它自动合成。

## Goals / Non-Goals

**Goals:**
- 让用户能走真 PR 流程:Klarit 帮开 PR、平台上评审合并、Klarit 察觉合并后收尾;**PR 被打回可退回改代码 → 更新 PR → 再等合并**。
- 把「开 PR」的**平台异构性**隔离进 agent,不在引擎里堆永远追不完的适配器。
- 让「核查已合并」**平台无关且零平台 CLI 依赖**。
- **给「等外部状态达成」一个正经的门类**(而非把它硬塞成节点),打回复用人工评审门现成的内容驱动回退,并为未来 webhook 留接入点。

**Non-Goals:**
- 不做各平台 CLI 的一键安装按钮(由 agent 自行判断)。
- **本期外部门只做「人触发再核查」,不接 webhook**(留接入点);外部核查只做 `pr-merged` 一种。
- 不做「调平台 API 拿确凿合并状态」确凿退路(后续增强)。
- 不改「引擎操作」这个名字。
- **不动普通引擎失败决策的既有路由、不删就地处置 agent**——打回是「门」的能力,不泛化到所有引擎决策(见 D6)。
- 不动既有两条内置工作流的行为。

## Decisions

### D1. 「引擎操作」升级为「平台预制节点」,内部实现可分流
**选择**:保持 `executor.kind = 'engine'` + `operation` 的对外形状不变,把「引擎操作」含义拓宽为「平台预制的现成节点」;引擎分派层(`runEngineOpForMember` 的 switch)按 `operation` 分流——多数 case 调 git-write 原语,`open-pr` 这个 case **拉起 agent**。
**理由**:UI、作者体验、读写、能力声明机制零改动,纯增量。
**弃选**:给 PR 单开一个 `executor.kind`——逼 UI/校验/skill/编辑器全特判,得不偿失。

### D2. `open-pr` 内部委派 agent,节点级、跨仓一次
**选择**:`open-pr` 实现为在引擎节点分派处把该节点**包装成等价 agent 节点**(合成 inline 指令),交 `runAgentNode` 执行——agent 复用既有多仓布局(主仓 cwd + 其余仓 `--add-dir`)**一次看到所有涉及仓**,为每个仓各开一个 PR、回报链接;幂等靠 agent「先查再开」。
**理由**:开 PR 依赖异构外部系统,硬编适配器是维护跑步机且永远不全;agent 天生擅长这种随机应变,还化解「gh 没装」。贴合「模糊活交给 agent,确定性管道交给引擎」。
**代价**:交出硬幂等(靠「先查再开」);依赖已配置 agent,无 agent 即终局失败。

### D3. 外部门 `pr-merged` 用纯 git 信号,平台无关、免 CLI
**选择**:核查用 `fetch --prune` + 「已并入基分支 或 上游 gone」判定(`checkBranchMerged`),只用 git、不调任何平台工具。**这段逻辑不再是一个引擎操作**,而是**外部门的过门条件**。
**理由**:git 信号天下统一,一套覆盖所有平台含自建;零平台 CLI/认证依赖。
**squash/rebase 的坑 → 缓解**:squash 后 feature 提交不作基分支祖先,「已并入」漏判;靠**「上游 gone」**兜(需平台开「合并后自动删分支」)。两信号都不满足则判未合并——最坏多点一次「开始收尾」,不会误放行。
**弃选**:调平台 API 拿确凿状态——平台特定、把 gh 依赖引回来;留后续增强。

### D4.（核心）「确认合并 + 收尾」是**外部门**,不是节点
**背景 / 当初为什么定成节点**:一开始我们一直在「引擎操作节点」这条轴上想(用户最早问的就是「能做成引擎操作节点吗」),于是把「等平台合并」当成流水线里一步、做成一个「只观察」的引擎节点 + 自造的挂起决策。结果「PR 被打回改」没法复用门的回退,只能去泛化引擎决策(那正是后来 dogfood 暴露的坑)。
**选择**:把它做成门把模型的**第三个 `kind`——`external`(外部门)**,挂在 `open-pr` 节点上。语义:
- **进门核查**外部状态(`verify: 'pr-merged'` → 跑 `checkBranchMerged`)。达成 → **过门**(推进到清理);未达成 → **挂起等待**,抛一个决策,恒含前进式「**开始收尾**」(点它=再核查一次);**将来可由 webhook 等外部信号触发同一再核查**(本期只人触发,留接入点)。
- **打回**:复用**人工评审门的自由输入 → 内容驱动回退**——写反馈即退回之前节点改代码,前向重流自然 re-push 更新 PR、回到本门再等合并。
**为什么门比节点顺**:①「等人/外部确认 + 不满意打回」本就是门的本行,做成门,打回**白捡**(不用碰引擎决策路由);②它是**第一个「等外界」的门**,独立命名给 webhook 正经接入点,也不把「等待/外部信号可解决」这层埋进 manual 门;③auto/manual 都是「当下判」,external 是「等外部达成」,三类性格清晰。
**弃选**:①保持节点 + 自造决策(就是被推翻的原方案);②做成 manual 门但不核查——丢了用户要的「真去查合没合」,且把「等外部/webhook」这层埋没。

### D5. 「真 PR」工作流不含 `merge-branch`
**选择**:交付段 `push-feature → open-pr〔外部门 pr-merged〕→ remove-worktree → delete-branch`,**没有 `merge-branch`**;云端分支交平台「自动删分支」清。
**理由**:合并发生在平台上,Klarit 不本地合并。分支配对约束满足(含 create-branch + delete-branch)。这与既有两条工作流最大的形状差异,正体现真 PR 本质。

### D6. 外部门复用人工评审门的回退;回退回落 origin-aware;**不**泛化到普通引擎决策
**选择**:外部门的**打回自由输入**走**与人工评审门同一条内容驱动回退**(`runRollbackJudge` → 回退确认 → `reenterFromRollback` 前向重流)。**发起入口**从「仅人工评审门」扩到「也含外部门」。
**回退回落 origin-aware**:回退子系统此前在「无判定 agent / 判无候选 / 用户取消」时硬编 `raiseManualGate`。改为按**发起回退的那道门**重抛——评审门→评审门,外部门→外部门。把 `raiseManualGate` 一般化为按当前门 `kind` 分派的 `raiseGate`。这是**门系统内部**的小一般化,不碰普通引擎失败决策。
**明确不做(修正我此前的 overreach)**:**不**把「所有引擎决策的自由文本」都改走回退、**不**删就地处置 agent。理由——普通引擎失败决策(命令失败、push 认证等)的反馈**有的就是本节点的活**,该就地改;强行都退回上一个节点会挑错节点、甚至转圈(死循环)。回退是「门」(评审门 / 外部门)的语义;处置 agent 继续管普通引擎失败。
**弃选**:泛化回退到所有引擎决策 + 删处置(用户已否:本节点该改的没法改、易死循环)。

## Risks / Trade-offs

- **[open-pr 幂等非硬保证]** agent 没先查就重复开 PR → **缓解**:指令明确「先查已存在 PR、有则不重开」;逐仓回报链接便于核对。
- **[squash 合并漏判已合并]** 纯 git「已并入」在 squash 下失效 → **缓解**:靠「上游 gone」+ 建议开「合并后自动删分支」;最坏多点一次,绝不误放行。
- **[依赖已配置 agent]** 无默认 agent 时 `open-pr` 跑不了 → **缓解**:终局失败给清楚提示;这类项目本不适合真 PR 自动化。
- **[新门类触及门把数据模型]** `external` 是 `WorkflowGateItem` 第三个 `kind`,动到校验/修复/迁移/skill/编辑器消费 → **缓解**:判别联合加一支,旧包无 `external` 门、迁移幂等;编辑器可后续再加下拉项(本期至少不崩)。
- **[打回复用回退,回退回落要 origin-aware]** 门系统 `raiseManualGate` 一般化为 `raiseGate` → **缓解**:改动限门系统内部;回归测试覆盖「评审门驳回→回退」既有链路 + 「外部门打回→回退」新链路 + 各回落点重抛正确的门。
- **[两个 PR-ish 工作流易混]** 「PR 模式」(本地门)与「真 PR」并存 → **缓解**:描述文案讲清定位;是否精简既有「PR 模式」留后续。
