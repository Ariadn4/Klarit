## ADDED Requirements

### Requirement: 人工驳回落地为内容驱动回退

失败矩阵中「人工驳回」一类(如「UI 重做」「换实现方法」)SHALL 由内容驱动回退承接,不再是留后续的空格:人工评审门驳回 → 只读回退判定 agent 溯源定位最早节点 → 用户确认目标节点 → 重入该节点前向修复。机制细节归 `content-driven-rollback` 能力;本能力据此把「人工驳回」纳入统一的失败处理版图。

#### Scenario: 人工驳回有明确出路
- **WHEN** 用户在人工评审门驳回
- **THEN** 引擎按内容驱动回退处理(判定 → 确认 → 重入修复),而非停在无出路的死结

### Requirement: 回退判定 agent 复用 heal 拉起形态但只读不提交

回退判定 agent SHALL 复用 heal agent 的拉起形态(经运行器无头拉起、写握手文件、全量留痕),但与写侧 heal agent 有三点确定性区别:

- **只读**:prompt 不给可写范围/产出;
- **不提交**:引擎对它**不跑越界检测、不做每节点提交**——它没有代码改动可提交;
- **产出是回退决策**:它的握手写的是回退目标节点与理由,真正的修复由被退回节点的执行者(有写)去干。

其记账键区别于普通 heal(如 `<nodeId>:rollback-judge`)。

#### Scenario: 判定 agent 走 heal 形态拉起
- **WHEN** 引擎为驳回拉起回退判定 agent
- **THEN** 复用 heal 的无头拉起 + 握手 + 留痕路径,记账键标明其为回退判定

#### Scenario: 判定 agent 不触发越界检测与提交
- **WHEN** 回退判定 agent 退出
- **THEN** 引擎不对其运行执行越界检测或每节点提交,只读取其握手里的回退决策
