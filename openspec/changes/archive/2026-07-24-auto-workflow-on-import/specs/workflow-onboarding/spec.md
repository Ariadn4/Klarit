## ADDED Requirements

### Requirement: 首次导入后按判据为项目落定一份工作流

首次导入(**非 reused**)一个项目、且该项目的文档语义分析**已完成**(默认 agent 已腾出档期)后,系统 SHALL 跑一次工作流 onboarding 判据,并**保证判据结束时项目已有一份活动工作流**(默认或经用户采用的提案),绝不让首次导入的项目停在「无工作流」态。判据对同一项目**至多跑一次**,`reused` 导入(重开已知项目)SHALL 跳过、不覆盖用户已有 `activeWorkflowId`。

判据分支:

- **有 agent 习惯痕迹 且 有能跑的默认 agent** → 系统 SHALL 无头触发 author 以系统合成意图产出一份工作流提案,并主动弹给用户预览/采用。
- **否则**(无痕迹 / 空新项目 / 未设默认 agent 或其不在已检测 agent 中) → 系统 SHALL 直接把内置默认工作流(本地直合)派为该项目活动工作流。

#### Scenario: 老项目有习惯 + 有 agent → 自动 author 提案

- **WHEN** 首次导入的项目某成员仓带 agent 习惯痕迹,且已设一个已检测到的默认 agent,文档分析完成
- **THEN** 系统无头触发 author 产出工作流提案并主动弹出预览,不派纯默认作最终结果(默认仅作占位)

#### Scenario: 新空项目 → 派默认工作流

- **WHEN** 首次导入的项目无任何习惯痕迹
- **THEN** 系统直接派内置默认工作流(本地直合)为活动工作流,不触发 author

#### Scenario: 有习惯但没能跑的 agent → 派默认

- **WHEN** 项目有痕迹,但未设默认 agent(或默认 agent 未安装)
- **THEN** 系统派默认工作流(生成了也跑不动),不触发 author

#### Scenario: 重开已知项目 → 跳过判据

- **WHEN** 导入结果 `reused` 为真
- **THEN** 判据整体跳过,项目原有活动工作流不变

### Requirement: 排序理由是 agent 档期串行,不是数据依赖

工作流 onboarding 的触发时机 SHALL 是**主进程文档语义分析返回那一刻**(分析 agent 释放),而 MUST NOT 依赖用户在文档 onboarding dialog 里的保存动作。author agent 自行探查项目习惯,不依赖审批过的文档登记表/公约。系统 MUST NOT 让 author 与文档语义分析**并发**占用同一默认 agent——两者对同一 agent 档期 SHALL 串行。

#### Scenario: 分析一返回即触发,不等用户保存

- **WHEN** 文档语义分析在主进程返回,用户尚未在 onboarding dialog 点保存
- **THEN** 工作流 onboarding 判据即可开始(命中支的 author 在后台跑),不阻塞于用户操作

#### Scenario: 不与文档分析并发抢 agent

- **WHEN** 文档语义分析仍在进行
- **THEN** 系统不启动 author 任务,直到分析返回、agent 腾出

### Requirement: 习惯痕迹为轻量存在性门控,不抽取内容

系统 SHALL 提供一个**廉价的存在性探测**判断项目是否带 agent 习惯痕迹,只回答「有没有可学的东西」用于门控,MUST NOT 读取、解析或预抽取痕迹内容喂给 agent(深读与解读是 author agent 自身职责)。探测 SHALL 为**项目级**——只看各成员仓根目录、不碰用户 home(如 `~/.claude`)。标记集 SHALL 至少覆盖 `.claude/`、`CLAUDE.md`、`.cursor/`、`AGENTS.md`、`.codex`、`.github/`;**多仓任一成员仓命中**即算「有习惯」。

#### Scenario: 多仓任一命中即有习惯

- **WHEN** 多仓项目里只有一个成员仓有 `CLAUDE.md`
- **THEN** 探测返回「有习惯」

#### Scenario: 只看项目、不看 home

- **WHEN** 用户 home 有 `~/.claude` 但导入的项目本身无任何痕迹标记
- **THEN** 探测返回「无习惯」(项目级判定)

### Requirement: author 失败一律回落默认,不留半成品激活

当命中 author 支但产出不可用(agent 失败/超时,或 `WorkflowProposal.issues` 非空、存库入口被禁用)时,系统 SHALL 回落把默认工作流派为活动工作流,保证项目有可用工作流;失败 SHALL NOT 打断用户,至多轻提示。用户**弃用**或关闭提案预览时,系统 SHALL 保持已派的默认工作流作为活动工作流,MUST NOT 把未采用的提案激活。

#### Scenario: author 产出无骨架 → 回落默认

- **WHEN** author 返回的提案 `issues` 非空、不可存库
- **THEN** 系统派默认工作流为活动工作流,项目不停在无工作流态

#### Scenario: 用户弃用提案 → 停在默认

- **WHEN** 用户在预览浮层里弃用/关闭该提案
- **THEN** 活动工作流保持为默认工作流,提案不被激活

### Requirement: 提案主动露出——追加进全局对话 + 底栏进度 + 排队不叠加

工作流生成为**后台异步**,其过程 SHALL 在**底栏状态区**呈现进度(对齐文档扫描的状态呈现),不打断用户。得到可用提案后,系统 SHALL 把它**作为一条 agent 消息追加进本项目的全局对话**(而非弹孤立浮层),使用户可在对话里预览(复用「预览草稿」入口)并**用对话输入框反馈让 AI 改写**。露出 SHALL 经**全局模态协调器**排队:无全局模态在开 → 立即**打开/聚焦对话面板、选中并刷新该会话**;有模态在开(如文档 onboarding)→ 排队,待其关闭再打开,MUST NOT 叠加于既有模态之上。

全程项目已有占位默认工作流,用户不被阻塞;系统 MUST NOT 为「统一弹出」而等文档扫描与工作流生成都完成再一起露(会被较慢一方拖住)。因主进程后台追加消息、渲染层无自动刷新(无 `conversationChanged` 广播),系统 SHALL 补一条推送驱动渲染层重取并选中该会话。

#### Scenario: 提案作为 agent 消息进全局对话

- **WHEN** 自动 author 产出可用提案
- **THEN** 系统把它作为 agent 消息追加进本项目全局对话,消息带该提案、可在对话里预览与反馈改写,而非弹孤立浮层

#### Scenario: 无模态在开 → 打开对话面板并选中该会话

- **WHEN** 提案就绪且此刻无全局模态在开
- **THEN** 系统打开/聚焦对话面板、选中并刷新承载该提案的会话、滚到该消息

#### Scenario: 有模态在开 → 排队待关闭再打开

- **WHEN** 提案就绪但用户正开着另一个全局模态(如文档 onboarding)
- **THEN** 系统不叠加,而是排队;待该模态关闭后再打开对话面板

#### Scenario: 生成进度进底栏

- **WHEN** 工作流正在后台生成
- **THEN** 底栏状态区显示其进度,不打断用户当前操作

### Requirement: 自动生成的提案留可供调试的日志

自动 author 产出提案后,系统 SHALL 把该结果**记入可供开发者事后查看的日志**(至少含:目标项目、产出的 `WorkflowDefinition`(节点/门/执行者概览或全量)、校验 `issues`、以及失败时的原因),便于在不依赖用户逐节点截图的情况下复现与调试。日志 SHALL 落在主进程可写、开发者可读之处(如日志文件/结构化 log),不打扰普通用户。

#### Scenario: 产出提案即留日志

- **WHEN** 自动 author 产出一份提案(成功或失败)
- **THEN** 系统记录一条含目标项目、工作流定义概览与 issues(失败则含原因)的日志,供事后调试

### Requirement: 生成失败——原因上浮、自动重试一次、失败轻提示

自动 author 失败或空产出时,系统 SHALL:

- **上浮并区分失败原因**:author 入口 SHALL 返回足以区分失败种类的信息(agent 调用抛错 / 跑通但无工作流产出 / 产出校验不过),供日志按种类记录,MUST NOT 把不同失败一律抹成「返回 null」。
- **有界自动重试**:命中 author 支且首次失败时 SHALL **自动重试一次**;仍失败才回落默认工作流。重试 SHALL 有界(至多一次),避免系统性失败下无限重试。
- **失败轻提示**:最终失败/空产出时 SHALL 给用户一条**非阻断轻提示**(如底栏「未能生成定制工作流,已用默认」,自动消失),不得让进度指示一闪即无、用户无从知情。

#### Scenario: 失败区分种类记日志

- **WHEN** author 因 agent 抛错、或跑通无产出、或校验不过而失败
- **THEN** 日志按种类记录原因,而非一律「返回 null」

#### Scenario: 首次失败自动重试一次

- **WHEN** 命中 author 支且首次调用失败
- **THEN** 系统自动重试一次;再失败才回落默认工作流(重试至多一次)

#### Scenario: 最终失败给底栏轻提示

- **WHEN** author 重试后仍失败/空产出
- **THEN** 底栏给一条自动消失的轻提示(已用默认工作流),不打断用户

### Requirement: author 产出须过固化门 lint,不过则喂回警告让其修订

自动 author 产出一份可用提案后,投递前系统 SHALL 对其跑 `lintWorkflow`;若命中警告(如「固化步骤前缺人工验收」),系统 SHALL 把**该警告文字 + 上一版工作流定义**合成一段修订意图**喂回 author**,令其修正(如补上不可逆固化前的人工审批门)后重新产出;此**修订-复检**循环 SHALL **有界**(至多若干次)。有界内改到不再告警则投递该修正版;仍告警则投递最后一版(UI 软校验仍会提示),不阻断。此为「不可逆固化前必有人工审批」这一硬原则的自动执行——把软校验从"仅 UI 提示"升级为"author 的自检-自修信号"。

#### Scenario: 缺审批门 → 喂回警告、author 补上

- **WHEN** author 首版产出触发「固化前缺人工验收」lint 警告
- **THEN** 系统把警告 + 上版定义喂回 author,author 补上固化前的 manual 审批门,投递修正版(不再告警)

#### Scenario: 修订有界

- **WHEN** 喂回修订达到上界仍未消除警告
- **THEN** 系统投递最后一版(UI 软校验仍提示),不无限循环、不阻断

#### Scenario: 无 lint 警告则直接投递

- **WHEN** author 产出本就无 lint 警告
- **THEN** 不触发修订循环,直接投递

### Requirement: 缺固化前审批门时确定性自动补(不赌 LLM)

因实测表明 author 反复把「验收」做成 agent/命令节点而非 `manual` 门、连喂回修订多轮仍不改正,自动 author 产出投递前系统 SHALL **确定性地**保证「不可逆固化前有一道人工审批 `manual` 门」:若命中「固化步骤前缺人工验收」lint,系统 SHALL 在**第一个不可逆固化节点之前**插入一个带 `manual` 门的复核节点(机械修复,不依赖 LLM 再产出),使投递的工作流**必然**含该审批门、该 lint 不再命中。修复 SHALL **幂等**(已有合规审批门则不重复插),且产出仍为合法工作流。此为「重大步骤必须人工审批」硬原则的确定性执行。作用域限**自动 onboarding 路**;聊天写工作流路不强加(用户在聊天里显式控制门)。

#### Scenario: author 漏审批门 → 确定性补上再投递

- **WHEN** 自动 author 产出的工作流在不可逆固化前缺 `manual` 门(即便经修订循环仍缺)
- **THEN** 系统在第一个固化节点前确定性插入一个带 `manual` 门的复核节点,投递的工作流含该审批门、无「固化前缺人工验收」告警

#### Scenario: 已有审批门则不重复插

- **WHEN** author 产出已在固化前含 `manual` 门
- **THEN** 确定性修复为幂等 no-op,不重复插入

### Requirement: 内置默认工作流可被稳定引用

为让兜底/否则支能指名派发,系统 SHALL 以**稳定 id** 种子化内置主默认工作流(本地直合),种子幂等(重复启动不重复建)。工作流 onboarding 的默认派发 SHALL 通过该稳定 id 激活。

#### Scenario: 稳定 id 幂等种子

- **WHEN** 应用多次启动
- **THEN** 内置主默认工作流始终以同一稳定 id 存在,不产生重复副本

#### Scenario: 兜底按稳定 id 激活

- **WHEN** 判据落到默认支
- **THEN** 系统以稳定 id 对该项目 `setActiveWorkflow`,无需即时创建新工作流包
