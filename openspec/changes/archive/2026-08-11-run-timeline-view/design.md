# 设计：数据早就齐了，缺的只是落盘和一层分组

## 核心观察：不要发明新事件

做「运行时间线」最容易走偏的第一步，是给引擎加一套 `journal.log(...)` 调用——在各个执行路径里手插埋点。那会立刻产生两个问题：埋点必然漏（新加的执行路径忘了埋），以及埋点和 `EngineProgressEvent` 说的话会慢慢分叉。

但 `EngineProgressEvent` **本来就是完整的**：

| 事件 | 时间线上答的问题 |
|---|---|
| `node-enter` / `node-exit` | 走到哪个节点了、这节点花了多久 |
| `phase` | 节点内部走到哪一阶段 |
| `skip` | 为什么跳过了这节点 |
| `gate-retry` | 客观门重试了几次、为什么（`GateAttempt.cause`/`rerun`） |
| `background` | 哪些命令转了后台、结局是什么（stopped/exited/timeout） |
| `decision` | 什么时候停下来等人 |
| `state` | 运行整体状态迁移 |

所以 journal **不是新的埋点体系，是既有事件流的一个持久化消费者**：在引擎已有的 `emit` 处旁挂一次写入即可。推论——任何未来新增的 `EngineProgressEvent` 类型自动进时间线，不需要改 journal。

## 明确排除 `op-chunk`

`op-chunk` 是流式增量输出，量级比其余事件大几个数量级，而且**它已经有家了**：`output-buffer` 按 `chunkBucket(nodeId, {bgId, cmdIndex})` 存着，`requirement-card-detail` 的「命令输出按前台/各后台任务分流且可回看」已经能回看。

journal 里存桶名引用，时间线点开时去读那个桶。这样：

- journal 保持小（每个运行几十到几百条），可以整份读进内存做分组
- 输出只存一份，不会出现「桶里和 journal 里的输出对不上」

## 时间线的形状：按节点分组，不是流水账

原始事件是一条平坦的流。直接渲染成流水账（一行一个事件）对不读代码的用户毫无用处——他看到的是 200 行 `phase: executing`。

所以要一层**纯函数分组**：`groupByNode(events) → NodeSegment[]`，每段含节点 id、进入/退出时刻、耗时、终局（完成 / 跳过+原因 / 停在决策）、门重试摘要、后台任务列表、输出桶引用。

这个分组是纯函数、放 `src/shared/`，因为它同时要被时间线视图和（将来的）任何摘要消费。分组逻辑里有一处需要小心：**运行可能没有 `node-exit`**（跑到一半软件关了、或停在决策上）。这种段标记为「未结束」并用最后一个事件的时刻算「至今耗时」，不能当成缺数据丢掉。

内容驱动回退会让同一个节点**出现多段**（回退后重入）。分组必须按「进入次序」切段而不是按 nodeId 合并——用户需要看到「这节点跑了两遍」，合并掉就把回退这件事藏起来了。

## 为什么放卡详情而不是全局

时间线的读者永远是在问「**我这张卡**怎么样了」。放全局要先选运行，多一次导航还得知道 runId。放卡详情里，`activeRunId` 就是默认选中项，历史运行在同一页签里切换。

页签内容复用 `CommandOutputView` 渲染展开的输出桶——不另写一套输出渲染，否则两处的换行/ANSI/滚动行为会慢慢不一致。

## 边界

- **不做 token 用量采集**（用户拍板砍掉）。我们复用用户订阅跑无头 CLI，用量不等于花钱而是额度；「哪张卡把额度烧光了」这个痛感尚未验证，不值得为它在 adapter 层给每家 CLI 写一套解析。时间线本来就是主体，用量是搭车的。将来真痛了再单独提。
- 不做时间线导出/分享。
- 不给 journal 单独发明保留与清理策略——跟 `output-buffer` 现行口径走，两者本来就该同生共死（journal 引用桶，桶没了 journal 留着也没用）。
- 本 change 之前的运行没有 journal。时间线对它们显示「无记录」，不做任何回溯重建（原始事件早就没了，硬造只能造假）。
