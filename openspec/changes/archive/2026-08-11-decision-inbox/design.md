# 设计：收件箱是投影，不是第二个真相源

## 核心决策：投影而非存储

最容易做错的版本是「收件箱表」——决策产生时往一张表里插一条，回应时删掉。这会立刻产生**双写不一致**：引擎的 `pendingDecision` 和收件箱表各存一份，任何一条路径（开机 `resumeAll`、内容驱动回退、用户 `abort`、干预挂起）忘了同步表，收件箱就会留下点开发现「这卡没在等你」的幽灵条目。

所以收件箱**不存东西**：

```
真相源：RunBreakpoint.pendingDecision（已有，run-store 持久化）
        ↓ 派生
收件箱：进程内 Map<runId, InboxEntry>
        ↑ 增量：engine.onEngineProgress 的 decision / state 事件
        ↑ 重建：run-store.list().filter(bp => bp.pendingDecision)
```

推论：**收件箱永远不可能比引擎更旧或更新**。任何让 `pendingDecision` 变化的路径（包括我们还没想到的）都自动反映到收件箱，不需要在那些路径上加同步代码。

## 为什么要给断点加 `pendingSince`

投影唯一缺的信息是**时间**。`RunBreakpoint` 现在没有「这个决策什么时候产生的」，而收件箱要按「等最久的在上」排序，还要显示「等了 2 小时」——这正是让用户判断先看哪张卡的关键信息。

进程内记时间戳不够：软件重开后全量重建，所有条目的时间都变成"刚刚"，排序就废了。所以时间必须跟着断点持久化。

`pendingSince` 与 `pendingDecision` **同生共死**：置决策时写、清决策时清。二者要么都有要么都无，不引入第三种状态。

老断点没这个字段 → 回落用 run-store 的文件 mtime 排序。不完美（mtime 会被任何一次 save 刷新），但只影响老数据的排序，不影响正确性，不值得为它做迁移。

## 只导航，不回应

收件箱里**不放回应决策的按钮**。理由不是省事，是避免两套决策 UI：

`RunDecisionPanel` 已经承载了决策的全部复杂度——前进式选项、多选、填空、`sourceKind='agent'` 的自填选项、人工门的动作按钮（`runGateAction` 起后台进程 + 流式回显）、可打开的产出物 `outputs`、外部链接 `links`、客观门重试历史 `gateHistory`。在收件箱里再实现一遍必然是个残废版本，用户会撞见「这个决策在收件箱里点不了、得点开卡」的不一致。

所以收件箱的职责边界很窄：**告诉你哪些卡在等你、等了多久、大概等你干什么，然后把你送过去。**

## `gateKind`：两类，不细分

条目要回答「大概等我干什么」，但不该复述整个决策。从 `EngineDecision.source`（格式 `<nodeId>:<outcome>` 或 `<nodeId>:manual-gate`）派生两类：

- `review` —— source 后缀是 `manual-gate`：**等你验收**，是流程正常走到你面前
- `failure` —— 其余：**出岔子了要你选**，是异常升级

不细分到具体 outcome。用户在收件箱这一层只需要区分「顺利跑到要我看」和「卡住了要我救」，更细的进卡详情看。

## 通知：只为新增发，且只在没盯着的时候

系统通知的价值全在「你没在看的时候告诉你」，所以两个门控：

1. **仅新增条目**触发（条目消失不发；重建时的存量条目不发——否则每次开机糊一脸通知）
2. **仅应用窗口未聚焦**时发

第二条也顺带解决了自动排程的场景：用户在别处干活，三张卡在后台跑，跑到验收门时通知冒出来。这正是「只在需要你决策时打扰你」的字面实现。

## 多窗口

收件箱是**项目级**的，每个窗口绑一个项目（见 `workspace-windows`），所以投影按项目实例化，窗口只订阅自己项目的那份。两个窗口开同一项目时共享同一投影，各自渲染。

## 边界

- 不做跨项目聚合（"所有项目里有 5 件事等你"）。等单项目版本 dogfood 过再说。
- 不把「引擎正在自愈重试」列进来——那不需要用户决策，列进来就退化成活动流水，违背「只在需要决策时冒泡」。
- 不做已读/归档/延后。条目的生命周期完全由决策的生命周期决定，加任何独立状态都是在偷偷造第二个真相源。
