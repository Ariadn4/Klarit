## ADDED Requirements

### Requirement: 项目由一个或多个成员仓组成

一个项目 SHALL 由 1..N 个**成员仓**（git 代码仓）组成。每个成员仓 MUST 各自拥有持久身份（沿用 `.klarit/project-id` 与既有 git 检测/补绑逻辑）；项目层面的**成员分组**MUST 存于 Klarit 管理数据（userData），不入 git。单仓项目是成员数为 1 的退化情形，其行为与扩展前一致。

#### Scenario: 单仓项目作为成员数为 1 的情形
- **WHEN** 导入一个单独的 git 仓库为项目
- **THEN** 系统建立一个仅含该仓为唯一成员的项目，对外行为与单仓时代一致

#### Scenario: 成员仓各自持久绑定
- **WHEN** 一个多仓项目的某个成员仓有 git
- **THEN** 该成员仓按既有逻辑获得自己的 `.klarit/project-id` 与 git 信息，独立于其它成员仓

#### Scenario: 分组存于 userData 不入 git
- **WHEN** 系统记录某项目的成员仓集合
- **THEN** 该成员分组写入 userData 注册表，不写入任何成员仓的 git

### Requirement: 导入时检测嵌套子仓并提议组建多仓项目

当用户选择导入的目录**自身不是 git 仓库**、但其直接子目录中存在多个 git 仓时，系统 SHALL 检测出这些子仓并向用户提议把它们组成一个多仓项目。用户确认后 MUST 建立一个以这些子仓为成员的项目；用户拒绝时回退为按 gitless 容器登记。

#### Scenario: 容器目录含多个子仓
- **WHEN** 用户导入的目录自身无 git，其下含 `frontend/`、`backend/` 两个 git 仓
- **THEN** 系统提示发现 2 个子仓，并提议把它们组成一个多仓项目

#### Scenario: 确认后建立多仓项目
- **WHEN** 用户在上述提议中确认组建
- **THEN** 系统建立一个含 `frontend`、`backend` 两个成员仓的项目，各成员仓分别完成身份绑定

#### Scenario: 拒绝则按 gitless 容器登记
- **WHEN** 用户拒绝组建多仓项目
- **THEN** 系统按既有 gitless 行为把该容器目录登记为单个 gitless 项目

### Requirement: 成员仓的关联与解绑

成员关系是 Klarit 侧的分组元数据，磁盘内容才是事实来源——系统 MUST 对账而非掌管那些目录。具体规则如下：

- **成员仓即项目目录下的子仓**：成员仓由项目目录（容器）下的 git 子目录构成（如 `/A` 下的 `/A/front`、`/A/back`），由导入时检测自动纳入，无需手动添加。**不提供**手动关联任意路径独立仓的用户入口（保持模型简单：成员就是子目录）。
- **解绑**：用户 SHALL 能把某成员仓移出项目；解绑 MUST 只解除分组关系，**绝不**删除该仓的磁盘内容或其 `.klarit/project-id`。
- 项目解绑到 0 个成员仓时 MUST 不再作为有效项目展示。

#### Scenario: 成员仓来自项目子目录
- **WHEN** 用户导入 `/A`（自身非 git），其下含 `/A/front`、`/A/back` 两个 git 子仓
- **THEN** 系统把 `front`、`back` 作为成员仓自动纳入项目，无需任何手动关联操作

#### Scenario: 解绑不动磁盘
- **WHEN** 用户把某成员仓从项目中解绑
- **THEN** 系统仅解除该仓与项目的分组关系，不删除其文件，也不删除其 `.klarit/project-id`

### Requirement: 成员仓在磁盘上缺失时的处理

当某成员仓的记录路径在磁盘上已不存在（用户在 Klarit 之外删除或移动了该目录）时，系统 MUST NOT 崩溃或丢弃整个项目；该成员仓 SHALL 被标记为「缺失/不可用」展示，其它成员照常工作。系统 MUST NOT 因路径缺失就自动从分组中清除该成员（它可能只是被移走或在本机未检出）。用户 SHALL 能对缺失成员选择「重新定位」（指向新路径）或「从项目移除」（解绑）。若该成员仓凭其 `.klarit/project-id` 在别处被重新导入，系统 SHALL 自动复用并把分组里的它重新指向新路径。

#### Scenario: 成员目录被外部删除后不崩溃
- **WHEN** 某多仓项目的一个成员仓目录在 Klarit 之外被删除，用户随后打开/刷新该项目
- **THEN** 该成员仓显示为「缺失/不可用」，其它成员仓的文件树照常展示，项目不被丢弃

#### Scenario: 缺失不自动清除
- **WHEN** 一个成员仓的路径暂时不存在
- **THEN** 系统保留其在分组中的成员身份，不自动从项目中删除

#### Scenario: 用户对缺失成员重新定位或移除
- **WHEN** 用户对一个缺失成员选择「重新定位」并指向新路径，或选择「从项目移除」
- **THEN** 前者把该成员指向新路径并恢复可用；后者解绑该成员（不动任何磁盘内容）

#### Scenario: 成员被移走后在别处重新导入自动复位
- **WHEN** 一个原本缺失的成员仓凭其 `.klarit/project-id` 在新路径被重新导入
- **THEN** 系统识别为同一成员，自动把分组里的它重新指向新路径，无需手动重新关联

### Requirement: 多仓项目在侧边栏按成员仓分组展示

多仓项目的侧边栏 SHALL 以每个成员仓为顶层分组（显示仓名，有 git 时附当前分支），各成员仓的目录树挂在其分组之下。单仓项目 MUST 仍直接展示其目录树而不额外加分组层。

#### Scenario: 多仓项目分组展示
- **WHEN** 当前项目含多个成员仓且侧边栏展开
- **THEN** 侧边栏为每个成员仓显示一个顶层分组，展开分组可见该仓的目录树

#### Scenario: 单仓项目不加分组层
- **WHEN** 当前项目仅含一个成员仓
- **THEN** 侧边栏直接展示该仓目录树，不显示多余的分组层

### Requirement: 移动或换机器后凭各仓身份复原分组

当多仓项目的成员仓被移动路径、或在新机器上重新导入时，系统 SHALL 凭各成员仓的 `.klarit/project-id` 重新识别它们，并据 userData 中（含云同步而来）的成员分组复原项目。

#### Scenario: 成员仓移动路径后仍归属原项目
- **WHEN** 某多仓项目的一个成员仓被移动到新路径后再次被打开或导入
- **THEN** 系统通过其 `.klarit/project-id` 识别为同一成员仓，更新其记录路径而不脱离原项目

#### Scenario: 换机器后分组复原
- **WHEN** 在同步了 userData 的新机器上重新导入各成员仓
- **THEN** 系统按各仓 `project-id` 与已同步的成员分组，把它们复原到同一项目下
