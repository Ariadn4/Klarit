## Why

真实项目常常是多个代码仓的组合——最典型就是「前端仓 + 后端仓」属于同一个产品，本该当成**一个** Klarit 项目来管。当前模型是「一个项目 = 一个 git 身份」(`.klarit/project-id` 落在单一仓库根)，于是这种项目只能拆成两个独立项目来回切，或者把含多个子仓的容器目录误当成 gitless 项目、两个子仓的 git 都不绑定——既丢了「换机器不断链」的保证，也割裂了本属同一项目的需求管理。本 change 让一个项目能由多个代码仓组成。

## What Changes

- **项目模型扩展为「一组代码仓」**：一个项目含 1..N 个**成员仓**；单仓项目是「成员数为 1」的退化情形，行为与今天一致。
- **每个成员仓各自绑定持久身份**（沿用 `.klarit/project-id` 与既有 git 检测/补绑逻辑），项目层面的**成员分组**存在 userData（不入 git，随云同步）。
- **导入时检测嵌套子仓**：选中的目录自身不是 git、但其下含多个 git 子仓时，提议把这些子仓组成一个多仓项目；单仓导入流程不变。
- **成员仓增删**：可向已有项目添加 / 移除成员仓。
- **侧边栏按成员仓分组展示**：多仓项目的文件树以每个成员仓为顶层分组（仓名 + 分支），各自的目录树挂在其下；单仓项目展示不变。
- **移动 / 换机器后凭各仓 `project-id` 复原分组**：成员仓各自重新识别，分组关系从 userData 复原。
- **需求 ↔ 成员仓多对多**（数据层）：项目记录其成员仓集合，为「需求卡声明涉及哪些仓」预留结构；**不**在本 change 实现跨仓分支编排。

## Capabilities

### New Capabilities
- `multi-repo-project`: 多仓项目的分组模型——项目由 1..N 个成员仓组成、成员分组存 userData、导入时检测嵌套子仓并提议组建、成员仓增删、侧边栏按成员仓分组展示、移动/换机器后凭各仓 `project-id` 复原分组。

### Modified Capabilities
- `project-registry`: 「导入项目」要求扩展——一次导入可建立或扩充一个由一个或多个成员仓组成的项目（单仓行为不变；容器目录含多子仓时进入多仓组建）。
- `app-shell-sidebar`: 「当前项目目录文件树」要求扩展——多仓项目以每个成员仓为顶层分组分别展示其目录树（单仓展示不变）。

## Impact

- **数据模型**：注册表条目从「单仓项目」泛化为「项目 + 成员仓列表」；新增成员仓的轻量结构（各自的 `project-id` / 路径 / git 信息）。需提供从旧单仓条目到新结构的向后兼容读取（旧条目读作成员数为 1）。
- **主进程**：导入编排增加「容器目录嵌套子仓扫描」与成员分组的建立/复原；`WindowManager` 的文件监听从单根扩展到多根（每个成员仓一棵树）。
- **渲染层**：侧边栏文件树支持多个成员仓根分组；切换器仍按项目（分组）名展示。
- **持久化**：成员分组写入 userData 注册表；成员仓身份仍写各自的 `.klarit/project-id`。
- **明确不做**：跨成员仓的分支 / worktree 协同编排（一个需求同时改前后端两条分支的执行机制）属执行引擎范畴，待其落地的 change 处理；本 change 只到注册/身份/导入/侧边栏这一层。
- 文档：`docs/project-goals.md` 已先行补入「项目与代码仓」一节并修正存储/分支模型，本 change 与之对齐。
