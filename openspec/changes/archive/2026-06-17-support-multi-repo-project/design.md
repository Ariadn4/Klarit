## Context

`add-project-sidebar` 已落地「一个项目 = 一个 git 身份」的模型：注册表条目 `ProjectEntry` 直接代表一个仓，`.klarit/project-id` 是其持久身份，卡片/状态按此 ID 关联。`docs/project-goals.md` 现已补入「项目与代码仓」一节，把项目重新定义为「一组代码仓」。本 change 把代码模型对齐到这个定义：项目可由多个**成员仓**组成，常见场景是「前端仓 + 后端仓」。

约束沿用：成员仓身份仍走 `.klarit/project-id`（入各仓 git）；Klarit 管理状态（含成员分组）存 userData、不入 git、随云同步（goals 文档「产物存储」）。本 change 只到注册/身份/导入/侧边栏层，**不**触及跨仓分支编排（执行引擎尚未建）。

## Goals / Non-Goals

**Goals:**
- 注册表模型从「单仓项目」泛化为「项目 + 成员仓列表」，且向后兼容已归档的旧单仓条目。
- 导入容器目录时检测其下多个 git 子仓并提议组建多仓项目。
- 成员仓增删；移动/换机器后凭各仓 `project-id` 复原分组。
- 侧边栏对多仓项目按成员仓分组展示，单仓不变；每个成员仓各自文件监听。

**Non-Goals:**
- 跨成员仓的分支/worktree 协同编排（一个需求同时改前后端两条分支的执行机制）——留给执行引擎的 change。
- git submodule 的特殊处理——含 submodule 的外层仓仍按单个仓处理。
- 深层嵌套扫描——只扫容器目录的直接子目录（depth 1）。
- 「管理仓库…」完整界面——仍延续上一个 change 的延后状态，本 change 仅给成员增删一个轻量入口。

## Decisions

### D1：模型泛化为 `Project { members: RepoMember[] }`，旧条目载入时包一层
把今天的 `ProjectEntry`（仓级身份/路径/git）下沉为 `RepoMember`；新增 `Project { id(分组 id), displayName, derivedName, memberIds[] }` 或直接内联 `members: RepoMember[]`。注册表载入时，**旧的单仓条目自动读作「成员数为 1 的项目」**（分组 id 复用原 entry id，唯一成员就是它自己），保证已归档数据与现有 session 引用不失效。
- **为什么**：单仓是多仓的退化情形，统一模型避免双轨；包一层迁移让旧数据零改动可用。
- **替代**：给单仓和多仓各设一套类型——分叉严重、下游到处分支判断，否决。

### D2：分组归 userData 为准，成员仓只各存自己的 `project-id`
成员分组（哪几个 `project-id` 属于同一项目）只写 userData 注册表；不往成员仓里写「我属于哪个组」。换机器复原靠：各仓凭自己的 `project-id` 重新识别 + 已云同步的 userData 分组表。
- **为什么**：与 goals 文档一致——管理状态在 userData、随云同步；避免「往每个成员仓写组信息、且谁是 canonical」的难题。
- **替代/权衡**：可选地在每个成员仓写 `.klarit/project-group` 提示，让**没开云同步**的新机器也能自动重组——代价是写每个仓 + canonical 归属。本 change 不做，列入 Open Questions。

### D3：嵌套子仓检测只在「容器自身非 git」时触发，且只扫直接子目录
导入目录时先按既有逻辑探测它自身的 git；**仅当它自身不是 git 仓**，才扫其直接子目录（depth 1），对每个子目录探测 git，收集出 ≥2 个子仓时提议组建。
- **为什么**：容器自身是 git（monorepo）时就该按单仓走，不该拆；depth 1 避免大目录递归与误抓 `node_modules` 里的仓。扫描复用 `probeGit`。
- **风险见 R3**。

### D4：`WindowManager` 多根监听，变更带成员仓标识
窗口绑定的是项目（分组）。对多仓项目，为**每个成员仓**各起一个 chokidar 监听，推给渲染层的 `FileTreeChange` 附带 `memberId`（或成员根路径），渲染层据此定位要刷新的成员分组子树。
- **为什么**：每个成员仓是独立目录树，单根监听不够；带标识让前端精确更新对应分组。

### D5：侧边栏 `members.length>1` 才加分组层
渲染层：单成员→直接渲染既有 `FileTree`（零变化）；多成员→每个成员仓渲染一个可折叠 `RepoGroup`（仓名 + 分支）内嵌 `FileTree`。切换器仍展示项目 `displayName`。
- **为什么**：单仓体验不被多仓改动波及；分组层只在需要时出现。

### D6：以「对账磁盘」为主线，成员管理是分组意图的薄层
成员关系只是 userData 里的分组元数据，**磁盘是事实来源**。主线不是「让用户增删成员」，而是**每次打开/刷新时把分组与磁盘对账**：
- 容器下的子仓由导入及再检测自动纳入（含「容器下新增子仓→提议纳入」）。
- 手动操作只剩两件、都做成 `registry-core` 纯函数先测后写：`linkMember`（关联非嵌套的独立仓）与 `unlinkMember`（解绑）——**解绑只解分组，绝不碰磁盘与 `project-id`**；成员降到 0 则项目不再展示。
- UI 暂以侧边栏分组区的轻量入口承载（不依赖延后的「管理仓库…」界面）。

### D7：成员目录在磁盘缺失 → 标记缺失、不清除、可复位
用户常在 Klarit 之外删/移目录。对账时若某成员的记录路径不存在：
- **不崩、不丢项目**：该成员标记 `missing`，其它成员照常；`WindowManager` 给缺失成员**不起监听**、`listDir` 失败被吞为「缺失」而非异常。
- **不自动清除**：路径没了≠成员没了（可能被移走/本机未检出），保留分组身份。
- **可复位**：用户「重新定位」改路径，或「从项目移除」解绑；若该仓凭 `project-id` 在别处被重新导入，复用既有按-id-识别链路自动把成员重指到新路径。
- **为什么**：贸然按路径自动删成员，会在「移动目录」这种最常见操作里把分组弄断——与 goals 文档「按 id 不按路径」的整条主张冲突。缺失是一种**状态**，不是删除事件。

## Risks / Trade-offs

- **[R1] 旧单仓注册表/会话数据兼容** → 载入时把旧条目包成单成员项目（D1），并写迁移单测覆盖「旧 registry.json 读出后行为不变」。
- **[R2] 仅 userData 分组：未开云同步的新机器不自动重组** → 接受并在 UI 说明；重组在同步前需手动「添加成员仓」。可选 git 提示作为后续增强（Open Questions）。
- **[R3] 嵌套扫描的深度/性能/误抓** → 只扫 depth 1，且跳过 `node_modules`/`.git` 等忽略目录；发现层级更深的仓时 `log` 提示而非静默忽略。
- **[R4] 一个成员仓被加进两个项目** → 约束「一个成员仓至多属一个项目」；重复添加时提示移动或拒绝。列入 Open Questions 定最终交互。
- **[R5] 多仓项目命名** → 容器目录名作默认 `displayName`，可编辑；成员仓各留自己的派生名用于分组标题。
- **[R6] 用户在 Klarit 之外删/移成员目录** → 对账时标记 `missing` 而非清除（D7）；`listDir`/监听对缺失成员降级处理，不抛异常；缺失成员凭 `project-id` 在别处出现时自动复位。需专门的「成员缺失」测试与 e2e。

## Migration Plan

新增能力，无破坏性数据变更（旧数据自动适配）。落地顺序：
1. 泛化注册表类型 + 旧条目载入迁移（纯逻辑，先测后写）。
2. `registry-core`：建组 / 成员增删 / 重组（凭 `project-id`）纯函数 + 测试。
3. 导入编排：容器嵌套子仓检测 + 组建流程（main，复用 `probeGit`）。
4. `WindowManager`：多根监听 + 变更带成员标识。
5. 渲染层：`RepoGroup` 分组渲染 + 成员增删入口；切换器不变。
6. e2e：导入含 2 子仓的容器→组建多仓项目→侧边栏两个分组→关闭重开复原。

回滚：纯新增，回滚即移除多仓相关代码；旧单仓数据与行为不依赖本 change。

## Open Questions

- 是否额外往每个成员仓写 `.klarit/project-group` 提示，以支持未开云同步的新机器自动重组？（倾向：本期不写，仅 userData；视用户反馈再说。）
- 成员增删的 UI 落点——侧边栏轻量入口，还是并入将来的「管理仓库…」界面？（倾向：先放侧边栏分组区。）
- 一个成员仓能否同时属于多个项目？（倾向：至多一个，重复添加给出移动/拒绝提示。）
- 多仓项目里某成员仓是 gitless（还没 git）时，分组成员如何稳定标识——暂用路径，git 出现后补绑并替换为 `project-id`（复用既有补绑链路）。
