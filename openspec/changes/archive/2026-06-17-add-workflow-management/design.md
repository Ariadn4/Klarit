## Context

Klarit 当前已有：项目注册表（`registry.json` @ userData，按持久身份关联）、app 级设置（`settings.json`，目前仅语言）、侧边栏视图、IPC 契约（`KlaritApi`）。持久化统一走 `src/main/store.ts` 的 `readJson`/`writeJson`。渲染层设置 UI 在 `Settings.tsx`，目前只有语言切换。

本变更要把「工作流」从无到有立成一等持久对象，并在设置面板加项目级管理入口。`docs/project-goals.md` 已规定工作流的完整结构（阶段/节点/执行者/产出/可写范围/门/溯源）。本次只落**定义 + 库 + 编辑 + 项目激活**，**不落执行引擎**，不落可视化 DAG。

约束：YAML 是对外开放的导入/导出格式（project-goals「导入格式 v1 必须开放」）；卡片/管理状态存 userData、不入 git；UI 遵守品牌规范与 `@theme` 令牌；测试先行。

## Goals / Non-Goals

**Goals:**
- 工作流定义的数据模型 + 校验，在 `src/shared/types.ts` 定义、main 与 renderer 共享。
- 工作流以包目录 `userData/workflows/<id>/`（`workflow.yaml` + skill 文件）持久化，读写往返一致、损坏不崩、整包可移植。
- 工作流库服务：列出/新建/克隆/删除/导入/导出 + 首启默认种子，经 IPC 暴露。
- 项目记录激活工作流 id；读取/设置；删除工作流时清理悬挂引用。
- 设置面板新增「项目设置」区：激活选择器 + 库管理 + 表单式编辑器（节点列表可拖拽排序）。

**Non-Goals:**
- 不实现执行引擎（不拉起 agent、不跑节点、不过门、不做溯源图）。
- 不做可视化 DAG 画布；v1 工作流为线性，节点用有序列表表达。
- 不做工作流的版本历史 / 多设备合并冲突解决（仅遵循 YAML 文件级写入，云同步留后续）。
- 不改动语言设置、侧边栏、项目导入/多仓既有行为。

## Decisions

### 决策 1：工作流 = 一个「包目录」（YAML + skill 文件），库即 `workflows/` 下的包集合
- **选择**：`userData/workflows/<id>/`，内含 `workflow.yaml`（定义）与被 `file` 驱动指令引用的 skill markdown（相对包路径）；库 = 扫描该目录下的各包。**包是存储/克隆/删除/导入/导出与将来云同步的整体单位**。
- **理由**：用户要求 `file` 引用相对工作流自身、且「整个工作流随云同步搬走」。把工作流做成自包含的包，引用永不断链、同步搬整包即可；YAML 仍是开放定义格式。每包一目录也避免单一大文件的并发写冲突，契合后续按包/字段粒度的同步合并。
- **备选**：每工作流一份扁平 YAML（无伴随文件）——放弃，无法承载 `file` 形态的 skill 随包搬运；塞进 `settings.json` / 单个 `workflows.json`——放弃，不开放、不利分享、写放大。

### 决策 2：引入 `yaml` 库（latest 2.9.0）做序列化
- **选择**：新增依赖 `yaml@^2.9.0`（main 进程用）。
- **理由**：往返保真、错误可读、纯 JS 无原生编译，适配 electron 打包。`js-yaml` 亦可，但 `yaml` 的 AST/往返能力更适合未来保留注释与字段级 diff。
- **备选**：手写 JSON↔YAML——放弃，重复造轮子且易出错。

### 决策 3：激活工作流 id 挂在 `Project` 上
- **选择**：`Project` 增加可选字段 `activeWorkflowId?: string | null`，随注册表持久化、按项目身份关联。
- **理由**：归属项目（project-goals「工作流属项目层」），随身份不断链；切换=改这一个指针，删除工作流=清理所有指向它的指针。
- **备选**：单独存 `project-workflows.json`——放弃，徒增一处状态与一致性负担，激活态本就是项目属性。

### 决策 4：校验集中在 main 的库服务，复用于保存/导入/编辑保存
- **选择**：一个纯函数 `validateWorkflow(def): {ok} | {ok:false, reason}`，被新建/导入/编辑保存共用；路径约束（相对、禁绝对、禁 `..`）与节点「恰一个执行者」在此判定。
- **理由**：单一真相、可测（针对公共 API 完整覆盖）；渲染层只消费结果与原因文案。
- **备选**：渲染层各自校验——放弃，易漂移、难测。

### 决策 5：编辑器用 @dnd-kit 做节点排序（CLAUDE.md 指定拖拽库）
- **选择**：新增 `@dnd-kit/core@^6.3.1` + `@dnd-kit/sortable@^10.0.0`，用 `SortableContext` 做节点有序列表的拖拽重排；其余字段为受控输入控件（文本/下拉/路径）。
- **理由**：CLAUDE.md 已把 @dnd-kit 定为拖拽库；线性工作流只需「列表内排序」这一最简用法。
- **备选**：HTML5 原生 drag——放弃，跨平台与可访问性差，且与项目既定栈不一致。

### 决策 7：路径字段用相对路径校验输入框，非 OS 文件选择器
- **选择**：产出路径 / 可写范围渲染为带相对路径校验的文本输入（禁绝对、禁 `..`），不接 OS 文件选择对话框。
- **理由**：工作流是可导出/分享的可移植数据，路径是「相对分支目录」语义；OS 选择器返回绝对路径会把定义绑死到某台机器，且工作流存于全局库、编辑时未必绑定项目，没有唯一仓根可供相对化。校验输入框保证可移植、可测。
- **备选**：以「当前激活项目仓根」为基准的点选器并存相对值——更友好但需处理多成员仓「选哪个仓」，留作后续增强。

### 决策 9：agent 驱动指令用判别联合（inline / file），file 路径相对工作流包、文件随包
- **选择**：`agent.drivingInstruction` 为 `{ kind: 'inline'; text } | { kind: 'file'; path }`。inline 内联文本；file 的 `path` **相对工作流包目录**，被引用文件**物理位于包内**——新建即写入包、导入即拷入包（不原地引用外部）。编辑器「手写 / 使用文件」切换对应两种 kind，「使用文件」下提供新建/导入两路。
- **理由**：project-goals 的 agent 驱动指令本就是「prompt / skill.md」二选一；判别联合让两种形态都可表达、可校验、可往返。把 file 锁定为「包内相对路径」契合决策 1 的包模型，保证自包含与可同步。
- **范围**：本次只存储/校验/落盘（含拷贝与新建 skill 文件），保证引用落在包内；**执行期读取/解析文件内容交由后续引擎 change**。
- **备选**：原地引用外部文件路径——放弃，破坏自包含与云同步；裸字符串 + 约定前缀——放弃，弱类型难校验。

### 决策 8：默认工作流种子做成确定性 engine 操作链，兼作引擎 smoke fixture
- **选择**：默认种子的节点序列以 `engine` 执行者为主——建分支 → 开 worktree →〔将来插 agent 的占位〕→ 合并分支 → 删分支+删 worktree（「开 git」可选前置）；junction 解除归入「删 worktree」内部步骤、不单列节点。
- **理由**：engine 操作确定性、无需 agent/PTY，是后续引擎 change 最先能实现并写集成测试的部分；让默认种子直接成为第一个可跑用例，避免另造 fixture。本次 change 不执行它，种子现仅为数据。
- **备选**：种一条满 SDLC 的 agent 工作流骨架——放弃，现阶段跑不起来、也无法当确定性测试基准。

### 决策 6：IPC 契约扩展
- 在 `KlaritApi` 增加：`listWorkflows()`、`createWorkflow()`、`cloneWorkflow(id)`、`deleteWorkflow(id)`、`importWorkflow(filePath)`、`exportWorkflow(id, filePath)`、`getWorkflow(id)`、`saveWorkflow(def)`；以及 `getActiveWorkflow(projectId)`、`setActiveWorkflow(projectId, workflowId|null)`。
- 删除走「先解项目引用、再删整个包目录」的主进程事务式顺序，避免悬挂引用。

## Risks / Trade-offs

- **[工作流结构很重，表单字段多]** → v1 只保证「可表达、可保存、可往返」，编辑器按 project-goals 字段铺开但不追求执行语义的强约束（路径合规等关键约束仍校验）；执行期约束留给后续引擎 change。
- **[YAML 手改/导入产生非法定义]** → 读取损坏文件跳过且不崩；导入/保存前强制校验并回报可读原因。
- **[删除被激活工作流引发悬挂引用]** → 主进程内「先解引用后删包目录」，并有 spec 场景覆盖删除后无项目指向已删 id。
- **[默认种子覆盖用户数据]** → 仅在库为空时种入，已有工作流则不动。
- **[新依赖增加打包体积]** → `yaml` 与 `@dnd-kit` 均为成熟纯 JS 包，体积可接受；@dnd-kit 仅渲染层用。

## Migration Plan

- 纯增量：新增 `userData/workflows/` 目录与 `Project.activeWorkflowId` 可选字段；旧注册表无该字段时读为「未激活」，无需数据迁移。
- 首次进入工作流能力时若库为空则种入默认工作流（幂等）。
- 回滚：移除新增 IPC 与 UI 区即可；遗留的 `workflows/` 目录与 `activeWorkflowId` 字段对旧版本无害（被忽略）。

## Open Questions

- 默认 engine 操作链中各节点的精确操作 spec 字段（分支命名规则、worktree 落地目录约定等）在实现种子时定，受后续引擎 change 的 engine 操作契约影响；本次只保证节点类型与顺序合法。
- 云同步本身不在本次范围（项目尚无同步设施，project-goals 列为后续）；本次确立的「工作流包」存储模型即是为让将来同步「整包搬运」天然成立。
- 导入 id 冲突时「分配新 id」与「覆盖同 id」的取舍：v1 取分配新 id（更安全），如需覆盖留作后续选项。
