## Why

`add-document-registry` 已落，但它扫描时会把**计划类文档**也纳进登记表——例如把 `openspec/changes` 判成 dynamic 纳管文档。计划类文档是**任务作用域的、前瞻的产物**（要做什么的计划稿），不是**归档目标**（沉淀成果的项目文档）。

下一步的「归档」节点只该沉淀成果、就地更新或追加**归档目标**，绝不该去动计划稿。所以登记表得先收窄：**只识别归档时候该经手的文档，把计划类文档排除掉。**

规则很简单——**让 agent 自己判断某路径是不是计划类，是就不纳管**（和现在排除噪声/许可证同处理）。不堆信号清单、不硬编码路径，避免规则僵化与下游误读。

## What Changes

- **分类阶段排除计划类文档**：`document-registry` 的扫描分类中，**agent 语义路**在分组/分类时 MUST 判断每个候选路径是否属于计划类（任务作用域的计划/提案产物），是则**不列入登记表**（同噪声处理，不纳管）。
- **无 agent 兜底轻量排除**：启发式回落路对**明显的计划/提案容器**做轻量路径判断并排除；判不准的照旧走既有分类（用户可事后手动改判/移出）。
- **修正既有条文**：原分类与坍缩条文里「`openspec/changes` 作为纳管条目」的示例场景随之更新为「被排除」，消除与本 change 的矛盾。

## Capabilities

### Modified Capabilities
- `document-registry`: 扫描分类新增「排除计划类文档」——agent 判定计划类即不纳管；无 agent 兜底轻量排除计划/提案容器；相应更新原示例场景。

## Impact

- **代码**：`src/main/document-scan.ts`（agent 分类指令加一条"计划类不列入"；兜底路的轻量计划容器排除）、`src/shared/document-registry.ts`（若兜底启发式在此，则加计划容器判断）、相关测试。
- **兼容**：纯收窄，不改数据模型（`ManagedDoc`/`DocKind` 不动）。对已建登记表无强制迁移——用户重扫时生效；已纳管的计划稿用户可手动移出。
- **不在本 change**：归档节点本身（下一个 change）；计划期产出/计划节点（已确定不做）。
