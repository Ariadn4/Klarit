# 设计：把「Klarit 枚举、agent 解读」从文档推广到习惯

## 先量，别猜

`--add-dir 整个仓` + author 慢 + CPU 上万秒，这三件事同时成立，但因果没被验证过。两种可能：

- **A：`--add-dir` 本身贵** —— CLI 挂载目录时做索引/扫描，仓越大越贵，跟提问内容无关
- **B：agent 自己翻贵** —— 挂载便宜，但 author 拿到一整个项目就开始满仓 glob，一轮轮读文件

如果是 B，光换成小目录也有效（它没得翻了）；如果是 A，那更有效。但如果实际是「A 很便宜、B 才是大头，而且 author 就算给了 manifest 还是要自己翻」，那这个 change 的收益会打折。

所以第一步是**在一个大仓上测**：挂仓根但只问一句废话（隔离 A）vs 挂一个小目录问同样的 author 问题（隔离 B）。结论写回本文件再往下做。不做这步就是在赌。

**这步实际没测成**（实现是在无人值守环境里做的，起不了真实 agent CLI 跑大仓）。所以下面的实现是在没有 A/B 数字的前提下推进的——理由是 A、B 两种成因都被「换成一个小目录」削掉，差别只在收益大小。**收益仍未验证**，由 dogfood（tasks 6.3(a)：同一大仓对比改前改后的耗时与 CPU 累计）回填；若届时发现提速不明显，说明成本另有出处，需回头重议。

## 物化 ≠ 抽取

`workflow-onboarding` 现有的门控要求写得很硬：

> MUST NOT 读取、解析或预抽取痕迹内容喂给 agent（深读与解读是 author agent 自身职责）

这条不能违反，也不该违反——它防的是 Klarit 自作聪明地把 `CLAUDE.md` 摘要成三行然后喂给 author，那样 author 就在二手信息上做判断了。

物化**不触碰这条**，因为它是**逐字复制**：

```
Klarit 决定：哪些文件值得给      ← 枚举（确定性、廉价）
author 决定：这些文件说明什么     ← 解读（照旧，全量原文）
```

没有任何一个字被 Klarit 解析、摘要或裁剪。author 读到的 `CLAUDE.md` 和它自己去项目里读到的**逐字节相同**。所以既有门控需求原样保留，物化作为**并列**的新能力加进去——一个答「有没有」，一个答「在哪、内容是什么」。

实现上要真的做到逐字：整文件复制，不做行数截断、不做「只取前 N KB」。文件太大就整个不给并在 manifest 里标注「过大未收录」，而不是给半截——半截的 `CLAUDE.md` 比没有更容易让 author 误判。

## manifest 里放什么

包里的文件脱离了原语境，所以 manifest 至少要回答「这文件原来在哪」。多仓项目尤其重要：两个成员仓各有一个 `CLAUDE.md`，扁平复制过来就撞名了。所以包内目录结构按 `<成员仓名>/<原相对路径>` 组织，manifest 再显式列一遍真实绝对路径。

另外放**Klarit 预先跑好的廉价确定性摘要**——这些是 author 本来要自己起子进程去拿的东西，每拿一次烧一轮：

- `git log --oneline -n <N>`：推断提交习惯（Conventional Commits？中文还是英文？）
- 各成员仓 `package.json` 的 `scripts`：推断构建/测试/检查命令
- 成员仓清单

这几条的共同点：**确定性、一次跑完、结果就是原始输出**。同样不解析——原样贴进 manifest，author 自己看。

## 会漏，这是明知的取舍

最大的风险是 author 从此看不见项目其余部分。标记集（`.claude/`、`CLAUDE.md`、`.cursor/`、`AGENTS.md`、`.codex`、`.github/`）覆盖不到的习惯就漏了——比如某项目把规矩写在 `docs/CONTRIBUTING.md` 或 `Makefile` 注释里。

缓解不是「那就把仓根也挂上」（那等于没改），而是：

1. manifest 带一份**深度受限的项目目录清单**（只列路径、不读内容，`ls -R` 级别的成本），让 author 至少知道项目里有些什么、有没有明显该看但没给的东西
2. 标记集可扩展，dogfood 中发现漏的就加

**这是拿「可能漏一点」换「快一个数量级」。** 值不值得由 dogfood 说了算：如果实测发现 author 产出的工作流质量明显下降，说明它原来真的靠满仓翻找拿到了关键信息，那就得回到「挂仓根 + manifest 引导」的折中方案——代价是 CPU 可能治不好。这个回退路径要在实现时留着，别把仓根挂载的代码删干净。

## 生命周期

包是 **per-run** 的：一次 author 调用建一次，结束就删。

**绝不写进任何成员仓**——写进去会进 git，污染用户仓库。这也是为什么我们不能照搬「把简报写进 `CLAUDE.md`」那招：别人在隔离的 per-task 目录里写，我们的 agent 跑在用户仓的 worktree 里，写进去就是往用户项目里拉屎。

包建在应用自己的临时区，author 进程结束（正常或异常）都清理。

## 边界

- 不推广到执行期的 agent 节点。那些 agent 本来就该在 worktree 里跑真代码，看得见全项目是正确的。
- 不改 author 的产出契约。它照旧产整份定义、照旧过脚手架规整与两闸校验。
- 不动聊天写工作流那条路（本来就不挂项目）。
