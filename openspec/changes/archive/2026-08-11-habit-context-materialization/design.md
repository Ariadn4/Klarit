# 设计：把「Klarit 枚举、agent 解读」从文档推广到习惯

## 先量，别猜

`--add-dir 整个仓` + author 慢 + CPU 上万秒，这三件事同时成立，但因果没被验证过。两种可能：

- **A：`--add-dir` 本身贵** —— CLI 挂载目录时做索引/扫描，仓越大越贵，跟提问内容无关
- **B：agent 自己翻贵** —— 挂载便宜，但 author 拿到一整个项目就开始满仓 glob，一轮轮读文件

如果是 B，光换成小目录也有效（它没得翻了）；如果是 A，那更有效。但如果实际是「A 很便宜、B 才是大头，而且 author 就算给了 manifest 还是要自己翻」，那这个 change 的收益会打折。

所以第一步是**在一个大仓上测**：挂仓根但只问一句废话（隔离 A）vs 挂一个小目录问同样的 author 问题（隔离 B）。结论写回本文件再往下做。不做这步就是在赌。

### 已测（2026-08-31）：A 证伪，B 的提速**测不出来**

在 Klarit 自己的仓上（29k 文件含 node_modules）起真实 `claude` CLI 测得。argv 逐字复刻 `adapter.ts` 的
`claudeCommon()`，cwd 是空 scratch 目录（同无头 author），prompt 走 stdin，CPU 用 Job Object 量**整棵进程树**
（一次调用起 145~374 个进程，只读父进程会漏掉大半）。

**先说一个测量陷阱，别再踩：** 第一轮只喂了裸 intent（428 字节），量出「改后 CPU −46%」——**这个数是假的**。
生产喂给 author 的是 `buildOrchestratePrompt` 的完整产物（21.7 KB：全盘视野 + OPS_CONTRACT + 写工作流 skill +
intent），而那段 skill **本身就内联了完整 workflow schema**。裸 intent 下挂仓根的 agent 得跑去读
`src/shared/workflow.ts` 才知道字段名，那些翻找成本是工装制造的、生产里不存在。下面只列忠实 prompt 的复测结果。

**隔离 A —— 同一句废话问题（agent 零工具调用），只差挂不挂仓根**（不受 prompt 忠实度影响，故沿用首轮）：

| 挂载 | CPU 累计（3 次） | 均值 |
|---|---|---|
| 不挂 | 5.38 / 5.72 / 5.62 秒 | **5.57 秒** |
| 挂 29k 文件仓根 | 5.45 / 5.07 / 5.17 秒 | **5.23 秒** |

**A 不成立。** 挂载成本 ≈ 0（挂的那组还略低，差值在 ±5% 噪声内）。`--add-dir` 不做索引/扫描，只是把目录加进
权限白名单。原文「CLI 挂载目录时做索引/扫描，仓越大越贵」是错的。

**改前 vs 改后（忠实 prompt，各 2 次取均值）：**

| 口径 | 改前（挂仓根 29k） | 改后（挂习惯包 12 文件） | 变化 |
|---|---|---|---|
| 墙钟 | 108.9 秒 | 125.7 秒 | **+15%（更慢）** |
| CPU 累计 | 10.39 秒 | 9.87 秒 | −5%（噪声内） |
| 轮次 | 9.5 | 5.5 | −42%（更少） |
| 工具调用 | 8.5 | 4.5 | −47%（更少） |
| 缓存读 token | 190k | 174k | −8%（噪声内） |
| 输出 token | 7453 | 8576 | +15%（更多） |
| 成本 | $0.4714 | $0.5470 | **+16%（更贵）** |

**B 的成因成立（挂得少确实让 agent 少翻：轮次 −42%、工具调用 −47%），但省下的轮次被「每轮更大」吃回去了，
净提速为零、成本反而略升。** 也就是说：**这个 change 的提速收益测不出来。**

**质量那半（tasks 6.3(b)）：分不出高下。** 两边都被喂了 schema，产出**都是 0 个自造字段**、全用真实字段。
对照 CLAUDE.md 与仓内事实列 11 条习惯，改前命中 9 与 6、改后命中 6 与 7——改前自身的波动（6~9）就盖过了
组间差异，n=2 判不出退化，也判不出更好。**所以「会漏」这个明知的取舍，目前既无证据成立、也无证据被排除。**

**三条必须诚实记下的：**

1. **「快一个数量级」不成立**，本文后面那句已就地更正。实测是**没有可测的提速**。
2. **「CPU 累计上万秒」没能复现。** 本节开头那个前提是拿本仓测不出来的——改前也只有 10 CPU 秒。要么当初那次
   是在远大于本仓的项目上，要么它的成因根本不在这条链上。**该前提至今无证据**，别再当既定事实引用。
3. **按 tasks 0.3 的约定，这里本该「回来重议方案」**——收益确实有限。但实现已经落地归档，且它在轮次/工具调用
   上的收敛是真的、也没测出质量损失，所以不建议推翻重做；建议改为：**别再拿「提速」为它辩护**，它的实际价值
   是「让 author 少满仓乱翻、行为更收敛可预期」。若将来真在大仓上复现出 CPU 病态，再回来单独立 change 量。

**另有一条意外发现（首轮裸 intent 下测到，可信）：意图改写本身不贡献提速。** 同样挂习惯包，用改前意图与改后
意图的差异在噪声内。收益（如果有）来自挂载变小，不来自「告诉 agent 材料已备齐」。

## 物化 ≠ 抽取

`workflow-onboarding` 现有的门控要求写得很硬：

> MUST NOT 读取、解析或预抽取痕迹内容喂给 agent（深读与解读是 author agent 自身职责）

这条不能违反，也不该违反——它防的是 Klarit 自作聪明地把 `CLAUDE.md` 摘要成三行然后喂给 author，那样 author 就在二手信息上做判断了。

物化**不触碰这条**，因为它是**逐字复制**：

```
Klarit 决定：哪些文件值得给      ← 枚举（确定性、廉价）
author 决定：这些文件说明什么     ← 解读（照旧，全量原文）
```

没有任何一个字被 Klarit 解析、摘要或裁剪。author 读到的 `CLAUDE.md` 和它自己去项目里读到的**逐字节相同**。所以既有门控需求原样保留，物化作为**并列**的新能力加进去——一个答「有没有」，一个答「在哪、内容是什么」。

实现上要真的做到逐字：整文件复制，不做行数截断、不做「只取前 N KB」。文件太大就整个不给并在 manifest 里标注「过大未收录」，而不是给半截——半截的 `CLAUDE.md` 比没有更容易让 author 误判。

## manifest 里放什么

包里的文件脱离了原语境，所以 manifest 至少要回答「这文件原来在哪」。多仓项目尤其重要：两个成员仓各有一个 `CLAUDE.md`，扁平复制过来就撞名了。所以包内目录结构按 `<成员仓名>/<原相对路径>` 组织，manifest 再显式列一遍真实绝对路径。

另外放**Klarit 预先跑好的廉价确定性摘要**——这些是 author 本来要自己起子进程去拿的东西，每拿一次烧一轮：

- `git log --oneline -n <N>`：推断提交习惯（Conventional Commits？中文还是英文？）
- 各成员仓 `package.json` 的 `scripts`：推断构建/测试/检查命令
- 成员仓清单

这几条的共同点：**确定性、一次跑完、结果就是原始输出**。同样不解析——原样贴进 manifest，author 自己看。

## 会漏，这是明知的取舍

最大的风险是 author 从此看不见项目其余部分。标记集（`.claude/`、`CLAUDE.md`、`.cursor/`、`AGENTS.md`、`.codex`、`.github/`）覆盖不到的习惯就漏了——比如某项目把规矩写在 `docs/CONTRIBUTING.md` 或 `Makefile` 注释里。

缓解不是「那就把仓根也挂上」（那等于没改），而是：

1. manifest 带一份**深度受限的项目目录清单**（只列路径、不读内容，`ls -R` 级别的成本），让 author 至少知道项目里有些什么、有没有明显该看但没给的东西
2. 标记集可扩展，dogfood 中发现漏的就加

原本写的是「拿『可能漏一点』换『快一个数量级』」——**这个交换根本不成立**：实测（见「先量，别猜」）没有可测的提速，成本还略升。所以真实的取舍是「拿『可能漏一点』换『author 行为更收敛』」（轮次 −42%、工具调用 −47%），而不是换速度。

漏不漏也没测出来：n=2 下改前改后的习惯覆盖分不出高下，改前自身的波动就盖过了组间差异。**两边都还是猜。** 想判就得在真项目上多跑几轮比产出，不是再量 CPU。

回退路径已在实现里留着（`KLARIT_HABIT_MOUNT_REPO_ROOTS=1` → 包 + 仓根一起挂），别把仓根挂载的代码删干净——既然提速不是理由，一旦发现漏得厉害，回退的代价比原先设想的小得多（原以为要吐回 CPU，实测没有 CPU 可吐）。

## 生命周期

包是 **per-run** 的：一次 author 调用建一次，结束就删。

**绝不写进任何成员仓**——写进去会进 git，污染用户仓库。这也是为什么我们不能照搬「把简报写进 `CLAUDE.md`」那招：别人在隔离的 per-task 目录里写，我们的 agent 跑在用户仓的 worktree 里，写进去就是往用户项目里拉屎。

包建在应用自己的临时区，author 进程结束（正常或异常）都清理。

## 边界

- 不推广到执行期的 agent 节点。那些 agent 本来就该在 worktree 里跑真代码，看得见全项目是正确的。
- 不改 author 的产出契约。它照旧产整份定义、照旧过脚手架规整与两闸校验。
- 不动聊天写工作流那条路（本来就不挂项目）。
