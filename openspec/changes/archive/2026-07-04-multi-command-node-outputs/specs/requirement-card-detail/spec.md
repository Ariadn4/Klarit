## MODIFIED Requirements

### Requirement: 单卡决策在详情面板内呈现

当一张卡的关联运行处于 `waiting-decision` 时,系统 SHALL 在**该卡详情面板内**呈现其决策(对齐 `docs/project-goals.md`「单卡决策直接展示在需求卡详情面板内,跨卡决策单独弹窗」)。决策渲染 SHALL 复用统一决策结构的全部要素:`titleKey`(+ `titleParams`)翻译后的背景说明、`options`(各按 `labelKey` 翻译、`recommended` 高亮、`detailKey` 作提示)、可选 `input`(填空 + 提交)、`actions`(人工门动作按钮)、`reason`(用户可读失败原因)、`gateHistory`(重试历史)。`raw`(原始底层输出)MUST NOT 在正式 UI 渲染(仅 dev/test)。提交决策经引擎 `decide(runId, { optionId? | optionIds? | text? })`。文案随当前语言实时翻译。跨卡决策弹窗不在本能力范围。

**动作按钮为切换态、不推进运行**:`actions` 里的每个动作按钮触发的是一个**旁路进程**(如启动后端/前端 dev server),**不**提交决策、**不**推进运行(与前进式 `options` 正交——只有选 `option` / 提交 `input` 才续跑)。每个动作按钮 SHALL 据其**对应进程的运行态**在两态间切换:该动作**无活进程**时呈现为「启动」(点击触发,经引擎起一条独立后台进程,见 `engine-execution`);该动作**有活进程**时呈现为「中止」(点击停掉该进程)。动作运行态 MUST 由该运行**当前后台命令列表**按动作身份**派生**(不把易变的活进程态塞进持久决策),使切换态与真实进程一致。

#### Scenario: 等待决策时在详情内显示决策
- **WHEN** 一张卡的运行进入 `waiting-decision`
- **THEN** 该卡详情面板内显示其决策(背景说明 + 前进式选项),不弹独立窗口

#### Scenario: 经卡上红点跳转定位到决策
- **WHEN** 用户点击看板卡上的静止红点(等待决策)入口
- **THEN** 打开该卡详情面板并定位/滚动到决策区,使其可见可操作

#### Scenario: 选项/填空提交推进,动作按钮不推进
- **WHEN** 用户在详情内对决策选定某选项、或填入 input 提交
- **THEN** 经引擎 `decide` 提交,运行据回应续跑、决策清除;而点动作按钮**不**提交决策、只起/停其旁路进程,决策仍在

#### Scenario: 动作按钮据进程运行态在启动/中止间切换
- **WHEN** 用户点某动作按钮的「启动」起了对应进程,该进程仍在跑
- **THEN** 该按钮就地变为「中止」;点「中止」停掉该进程后又变回「启动」;各动作按钮各自独立切换、互不影响

#### Scenario: 原始输出不在正式 UI 渲染
- **WHEN** 一个决策携带 `raw` 字段
- **THEN** 正式 UI 不渲染 `raw`(仅 dev/test 可见),用户只看 `titleKey`/`reason` 等可读文案

#### Scenario: 决策文案随语言实时翻译
- **WHEN** 用户在决策展示期间切换界面语言
- **THEN** 决策的背景与选项文案据新语言实时翻译

### Requirement: 命令输出按前台/各后台任务分流且可回看

需求卡详情面板 SHALL 为该卡运行的命令输出提供**按条分流、可回看**的入口,而非把多条命令输出杂糅一处:

- **前台当前命令**:以运行圆点(呼吸蓝点)及其后方节点文案作为入口,点击后展示**当前运行命令**的输出。
- **各后台命令**:展示该运行的后台命令条目(每个 `bgId` 一行,带其节点/标签),每行可点入查看**该后台命令各自**的输出(可同时存在多个后台命令)。**人工门动作按钮触发的进程亦为后台命令**,同样各占一格独立展示其输出(以该动作文案为标签),MUST NOT 混入「前台当前命令」——两个动作(如启动后端、启动前端)的输出 SHALL 各自一格、绝不夹揉在同一处。

**后台命令终止后 MUST NOT 直接消失**:一个后台命令被用户中止 / 自行退出 / **超时被杀**时,其条目 SHALL **保留在详情面板并标注终态**(如「已中止」「已结束」「已超时中止」——尤其"计时中止"要显式可见,以免用户误以为是 bug),直到**用户点击「清除」**才移除该条目;运行中的后台命令则提供「中止」。终态条目的输出仍 SHALL 可回看。**但运行推进进入新节点时**,系统 SHALL **自动清掉**上个节点残留的**已终止**后台命令条目(避免跨节点攒一堆死窗口);**仍在运行**的转后台命令条目 MUST 保留。

输出 MUST **可回看**(不只在流过时即时显示):依赖引擎对命令输出按命令/后台任务分桶缓冲(见 `engine-execution`);**命令转后台后其后续输出归入该后台命令自己的桶**(不再混入前台节点桶)。关闭重开后,仍能回看运行期内已缓冲的输出。

#### Scenario: 经蓝点入口看前台命令输出
- **WHEN** 一张卡运行中其前台节点正在跑命令(呼吸蓝点),用户点击该点/文案入口
- **THEN** 展示当前命令的输出(可回看已产出的部分,非仅实时片段)

#### Scenario: 多个后台命令各自可点入查看
- **WHEN** 某运行有两个以上后台命令
- **THEN** 详情面板分别列出每个后台命令,各有独立入口查看其各自输出(转后台后的输出进各自的桶,不再是「暂无输出」)

#### Scenario: 两个动作进程输出各自一格不夹揉
- **WHEN** 用户在验收门先后点「启动后端」「启动前端」,两个动作进程同时在跑
- **THEN** 详情面板为两个进程各展示一格独立输出(以各自动作文案为标签),两条输出互不混入、也不进「前台当前命令」;可分别中止其一而不影响另一

#### Scenario: 后台命令超时中止后保留并标状态
- **WHEN** 一个带超时的后台命令到点被杀
- **THEN** 其条目保留在详情面板并标注「已超时中止」(不直接消失),并提供「清除」按钮;用户点「清除」后方移除该条目

#### Scenario: 进入新节点自动清掉已终止的后台窗口
- **WHEN** 运行推进进入新节点,而上个节点留有已终止(已中止/已结束/已超时)的后台命令条目,同时另有仍在运行的转后台命令
- **THEN** 已终止的条目被自动清掉(不再手动逐个「清除」),仍在运行的转后台命令条目保留

#### Scenario: 关重开后输出仍可回看
- **WHEN** 一个产生过命令输出的运行随应用关闭后重开并恢复
- **THEN** 用户仍可在详情面板回看运行期内已缓冲的命令输出
