## ADDED Requirements

### Requirement: 回退重入亦可被单需求 agent 干预发起

内容驱动回退的**重入执行**（重入不重置、前向修复，见「确认后重入执行」）此前只经**人工评审门驳回 → 判定 → 回退确认决策**这一条链路可达。系统 SHALL 使同一重入语义**亦可被单需求 agent 的干预直接发起**：单需求 agent 提议「倒回到节点 K（可带注入指令）」经用户确认后，经 `engine.reenter(runId, K, 指令)` 触发**同一重入**（拨回 K、重锚 K..N 基线、注入「修复前向」、前向重流；不 `git reset`、不撤下游）。两条发起路径 MUST 复用**同一重入实现**（不各造一套），且都 MUST 在破坏性执行前经用户确认。

#### Scenario: 单卡 agent 干预发起回退重入

- **WHEN** 用户在某卡单需求 agent 里确认「倒回到节点 K 并注入新指令」
- **THEN** 经 `engine.reenter` 触发与评审门驳回相同的重入前向修复，不 `git reset`、不撤下游代码/产出

#### Scenario: 两条发起路径复用同一重入

- **WHEN** 分别经「评审门驳回确认」与「单卡 agent 干预」发起回退到同一节点
- **THEN** 两者走同一重入实现，行为一致

### Requirement: 门自由输入的塑造需求分类前置

人工评审门驳回自由输入、以及失败决策自由输入里，用户可能冒出**塑造需求**（新增/扩范围/牵动别卡/新建）的意图。系统 SHALL 在**既有自由输入路由前加一道单需求 agent 分类**：把该卡的自由输入先交单需求 agent 分类——

- 判为**塑造需求** → **上抛** `orchestrate(intent, projectId)`，把 ops 提案呈现到该卡对话/审阅流，并 **MUST NOT 消费该决策**（门/失败决策仍 `pending`，用户随后另行 `pass`/真驳回或另作处置）；
- 判为**非塑造需求**（本卡执行/驳回/技术处置） → **原样直下**既有路由（人工评审门 → 只读回退判定；失败决策 → 处置 agent），行为不变。

此分类的**偏置与卡对话相反**：门语境默认「用户在评审本卡产出」，故**歧义 SHALL 留在本地（当驳回/处置）**，仅当明确是塑造需求才引流上抛——以免含糊的驳回意见被误当新需求、打乱既有「驳回→回退判定」闭环。既有回退判定/处置路径 MUST NOT 因本分类而回归。

#### Scenario: 门自由输入的塑造需求引流上抛且不消费门

- **WHEN** 用户在人工评审门自由输入里写「还要加个需求 X」，分类判为塑造需求
- **THEN** 系统上抛 `orchestrate` 出 ops 提案交审阅，评审门决策仍 `pending`（未过门、未触发回退），用户可随后另行 pass 或真驳回

#### Scenario: 明确驳回原样走回退判定

- **WHEN** 用户在评审门自由输入里写「这段 UI 太丑，重做」，分类判为非塑造需求
- **THEN** 原样进入既有只读回退判定 → 回退确认流，分类不改变其行为

#### Scenario: 门语境歧义留在本地

- **WHEN** 门自由输入在「驳回本卡」与「塑造新需求」间含糊
- **THEN** 分类保守判为本地（当驳回/处置），不上抛，以免打乱回退闭环

#### Scenario: 失败决策自由输入同样识别上抛

- **WHEN** 某失败决策的自由输入里冒出明确的塑造需求意图
- **THEN** 系统识别→上抛 `orchestrate`（不消费该失败决策），其余自由输入仍原样交处置 agent
