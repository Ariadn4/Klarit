# 设计：定时的自动排程，且绝不自作主张

## 形态直接抄 `auto-scheduler`

`todo-auto-scheduler` 已经把「主进程常驻回路自动拉起运行」这件事的坑趟完了，巡检是它的**按时间触发版**，形态照搬：

- `evaluate()` **串行化**：同一时刻至多一个评估在跑，评估间的新触发合并为一次补评估
- **永不抛**：单次评估异常不能让回路停摆
- **注入式依赖**：`listPatrols` / `getProject` / `isRunLive` / `startWorkflow` / `runCommand` / `scanDocuments` / `pushCandidates` / `pushInbox` 全部注入，纯逻辑（到期判定）放 `src/shared/patrol.ts`

唯一的结构差异：`auto-scheduler` 由事件触发（卡进待办 / 运行 done），巡检由**时钟**触发——一个低频 tick（分钟级）唤醒 `evaluate()`，比对每条巡检的 `lastRunAt` 与其触发周期。分钟级足够：巡检的场景是「每天凌晨扫一次文档」，不是秒级调度。

## 不用 cron 表达式

面向的是不读代码的 vibe coder。`0 3 * * 1` 在这个产品里出现就是设计事故。

所以触发只有三种形态，都能用下拉+时间选择器表达完：

```
{ everyHours: n }              每 n 小时
{ daily: 'HH:mm' }             每天几点
{ weekly: { day, time } }      每周几的几点
```

覆盖不了的场景（每月第一个工作日之类）**就是不支持**。真需要时用户可以建一条「每天」的巡检，让它的动作命令自己判断今天跑不跑——把复杂度留在用户自己的脚本里，不污染产品模型。

## 三类动作，零个新执行器

| 动作 | 复用 |
|---|---|
| 跑工作流 | `engine.start`（与自动排程同一条启动路径） |
| 跑命令 | `command-execution` 的可取消命令运行器 |
| 文档腐烂扫描 | `document-scan` |

一个新执行器都不加。这条约束是刻意的：巡检要是开始长自己的执行能力，它就会慢慢变成第二个引擎，然后两套失败处理、两套输出分桶、两套中止语义。

## 核心边界：发现问题，不解决问题

这是本设计最重要的一条，也是最容易在实现时被侵蚀的一条。

巡检**主动产出只有一个去处**：

```
发现了该改的东西 → 推成候选需求卡（submitDecomposedCandidates，止于审阅）
```

巡检 MUST NOT 直接改代码、直接合并、直接建活卡、直接排程。

### 为什么不是「进收件箱」

初稿写的是两个去处，第二个是「进决策收件箱」。这是错的——`decision-inbox` 的整个设计立在「**纯投影**、MUST NOT 独立于断点增删条目」上，巡检往里塞条目会直接摧毁那个不变量，然后收件箱就退回成一张需要各处同步的表。

而且根本不需要：巡检**跑工作流**时，如果那个工作流停在人工门上，它的运行本来就会置 `pendingDecision`，收件箱**自动**就投影到了。这条路巡检侧一行代码都不用写。

所以「巡检发现的事你会看到」有两条天然通路，都不需要新机制：停在门上的 → 收件箱自动显示；扫出来的问题 → 候选卡等你审。

理由不只是安全。用户对这个产品的信任建立在「**我管需求和优先级**」上——一个半夜自己改了代码的定时任务会直接摧毁这个前提。而且推成候选卡这条路本来就通：`submitDecomposedCandidates` 是外部 AI 推候选的既有接缝，候选卡止于审阅、由用户决定要不要落库，这个边界已经在 `requirement-decomposition` 里立好了，巡检**沿用而不是绕过**它。

于是巡检的定位很干净：**它是个巡逻的，不是修东西的。它把发现的问题变成需求，剩下的走你已经熟悉的那条路。**

## 并发槽共享

巡检启动的运行必须计入 `auto-scheduler` 的并发上限，否则两条回路会互相抢成员仓 worktree——`auto-scheduler` 现在的选取规则里有「与在跑不共享仓者优先」，这个规则的前提是它能看见所有在跑的运行。

所以口径统一为：**上限约束的是「系统自动发起的运行」，不管是排程发起还是巡检发起。** 手动启动仍不受约束（用户明确要跑，不该被拦）。

槽满时巡检**跳过本次，不排队**。排队会让定时任务堆积——软件开着一整天没槽，晚上突然攒了 8 个巡检一起冲进来。跳过更符合巡检的语义：它是周期性的，错过这次下次还会来。

## 软件没开就不跑

桌面应用的诚实边界，不粉饰。开机时的补跑口径：

- 某巡检自 `lastRunAt` 以来**错过了 ≥1 个窗口** → 只跑**一次**
- 错过 10 个窗口也只跑一次

逐个补跑毫无意义（补跑 10 次昨天的文档扫描能得到什么？）而且会在开机时瞬间打满并发槽。

`lastRunAt` 随巡检配置持久化。「跑了」的定义是**发起了动作**，不是动作成功——否则一个总是失败的巡检会在每个 tick 重试，变成死循环。

## 边界

- 不做 cron 表达式（见上）。
- 不做巡检历史报表/趋势图。巡检说了什么，去收件箱和候选卡里看。
- 不做跨项目巡检。巡检挂在项目上，跟着项目走。
- 不做后台常驻进程（软件关了也跑）。那是产品形态的决策，不是这个 change 能顺手带的。
- 不预置任何巡检。默认零条、完全静默——用户没建巡检时，本能力对系统行为的影响必须是**零**。
