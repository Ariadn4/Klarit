# Klarit 定位文档

## 一句话定位

**Klarit 是面向 vibe coder 的需求驱动项目管理应用——你只描述要什么，它接管从需求到交付的全过程，并让项目规模化后不腐烂。**

## 核心价值

**用户做的事情**：

1. 写需求
2. 排优先级
3. 对 AI 提出的问题/诉求进行决策
4. 查看 AI 生成的报告
5. 必要时进行验收
6. 可修改工作流

**Klarit 承接的事情**：

1. 可主动提出拆分大型需求 / 合并同类小需求的诉求，并维护需求卡间关系（层级 / 依赖 / 耦合）
2. 根据配置的工作流自动处理用户需求，并执行对应操作（包括编排 agent 执行）
3. 当对于需求或执行有疑问时，主动提出问题
4. 自动维护文档（动态文档与代码同步）
5. 当 agent 多次修改仍不满足需求时及时叫停，确认用户与 agent 对需求的理解一致——以防是需求理解偏差导致的反复返工
6. 当用户选择 `AI托管` 模式时，让 `全局agent` 代替用户，对 AI 提出的问题/诉求进行决策

## 范围边界

**做什么**：Klarit 承接的事情（见「核心价值」）+ 可独立开关的模块化能力（SDLC 引导、知识库维护、架构哨兵、Agent 编排、任务管理、发版管理、编程工具集成）。

**明确不做（v1 non-goals）**：
- 不写代码——交给智能编程工具
- 不做代码补全、提取、prompt 构建——交给智能编程工具
- 不做「一句话生成完整应用」——那是 Bolt / Lovable 的活
- 不做企业级权限 / SSO / 审计——不是这个阶段该考虑的
- 不做自有大模型——调用户的 Claude Code 订阅或第三方 API
- 不做规则包 marketplace——v2 再说，但导入格式 v1 必须开放

## 约束

- **复用用户的编程 AI，不自建模型通道**：调用户的 Claude Code 订阅或第三方 API；v1 默认 Claude Code CLI、经内嵌终端子进程通信。
- **平台形态**：桌面应用（内嵌终端 + 文档库 + 需求看板共存于窗口内，「能在窗口内查看 md」才能让用户查看报告。
- **不强推默认值**：目录、规则、版本号方案等由用户/导入定义，Klarit 提供默认规则包但不强制；既有约定优先。

## 四层产品结构

| 层 | 谁拥有 | 内容 |
|---|---|---|
| **引擎**（IP / 护城河）| Klarit | 扫描、违规检测、可视化、自动迁移、AI 持续维护、多 agent 追踪 |
| **规则包**（内容 / 数据）| 用户 / 社区 / Klarit 默认 | 文件夹结构、文档约束、架构约束等具体规范 |
| **工作流** | 用户 / 社区 / Klarit 默认 | 需求→交付的编排流程：阶段定义、各阶段调用的 agent 与操作、提问/决策节点、客观门校验点、分支与返工规则 |
| **执行端** | 第三方 | Claude Code / Codex / Cursor / Aider 等智能编程工具 |

引擎是核心 IP，规则只是数据，执行交给第三方——**边界极清晰**。

**规则包的实体形态**：一个规则包是命名的、可移植的包（`userData/rule-packs/<id>/`，开放 YAML 格式、不入 git），持有一组带类型条目——**宪法规则**（治理陈述，如「测试先行」）、**产出模板**（markdown 结构骨架）、**客观门校验**（CLI 命令，如 `openspec validate`）。两种消费方式：**宪法规则按项目套用**（应用设置·规则库编辑包内容；项目设置·宪法激活包并逐条 on/off，引擎把「激活包 − 关掉的」派生为该项目生效宪法、注入每个 agent 节点）；**产出模板/客观门校验被工作流节点引用**：产出模板**只从规则库引用**（内容统一住规则库、单一来源；编辑器的「手写新建」是把内容写进规则库再引用），客观门校验为「裸命令快捷 + 从规则库引用」。规则包与工作流是并列两层：工作流管编排、规则包管规范。

## 三层 Agent 结构

Klarit 内部的 AI 不是一个大杂烩，而是按「能看多大范围、能改不能改」分成三层，从外到内权限收窄、职责收紧。

| 层 | 权限 | 可多开 | 可见范围 | 干预能力 | 常用场景 |
|---|---|---|---|---|---|
| **全局 Agent** | 只读 | 可多开 | 项目目标、所有分支和 worktrees、全局所有需求的需求卡资料 | 可干预所有后台执行 Agent 的工作 | 用户咨询项目任意事宜；用户新建需求卡；`AI 托管`模式下代替用户决策 |
| **单需求 Agent** | 只读 | 不可多开（每张需求卡一个） | 仅指定需求的需求卡资料及其在各涉及成员仓的对应分支内容 | 可干预该需求卡的工作 | 用户咨询某需求实现进度；用户要求暂停 / 把需求退回指定节点 / 修改任务资料 |
| **后台执行 Agent** | 引擎按需分配读写权限 | —（由工作流编排，按需拉起） | 引擎指定的工作分支 | 自身即执行者 | 写代码、按指定格式写报告、完成具体工作 |

**为什么这么分**：

- **只读 vs 读写**——只有最内层的后台执行 Agent 才动文件，且权限由引擎按需分配、限定在指定分支；上面两层只读，咨询和决策不会误伤代码。
- **可见范围逐层收窄**——全局看全盘、单需求只看一卡一支、执行只看自己那条分支，越靠近代码暴露面越小。
- **干预自上而下**——全局能叫停 / 调度任意后台 Agent，单需求只能管自己那张卡，形成清晰的指挥链。

## 通信模型

引擎是唯一总线，Agent 之间不直连，一切通过引擎中转 + 共享产物。

**引擎 ↔ Agent**：

- 控制（引擎主动编排）：引擎用 node-pty 拉起 Agent，通过 PTY 的 stdin 注入指令 / 澄清 / 叫停；解析 Agent stdout 里约定的结构化哨兵块（需要决策、过门、完成某步），以及 Agent 写出的握手文件。
- 数据（共享产物，chokidar 监听变化）：需求卡、动态文档、git 分支 / worktree——每个需求**在其涉及的每个成员仓各开一条分支 / 一个 worktree**（单仓项目就是一条），后台 Agent 在对应 worktree 里干活，产出即各仓的分支差异。

**Agent ↔ Agent**（全部间接）：

- 全局 Agent 干预后台 Agent：向引擎发控制指令，引擎再操作目标 Agent（全局 → 引擎 → 后台）。
- 跨需求传递成果：靠合并后的分支 / 更新后的文档 / 需求卡的依赖边，不互相喊话。

**人 ↔ Agent**：用户与全局 / 单需求 Agent 的对话走 Electron IPC（renderer ↔ main）。完整链路：UI ↔ IPC ↔ 引擎 ↔ PTY / 文件 ↔ Agent。

## 项目与代码仓

一个 Klarit **项目**对应一组**代码仓**（git 仓库），可以是一个，也可以是多个——常见的多仓场景就是「前端仓 + 后端仓」当成同一个项目来管。

- **每个代码仓各有自己的持久身份**（`.klarit/project-id`，随该仓 git 走）；移动目录 / 换机器 / 多 worktree 都靠它不断链。
- **项目 = 一组代码仓的分组**。这层分组属 Klarit 管理数据，存 userData（不入 git，随云同步走）：它按成员仓的 project-id 记成员关系，换机器时各仓凭自己的 id 重新识别、分组随之复原。
- **单仓项目是「成员数为 1」的退化情形**，行为与单仓时代一致；多仓只是把同一套机制扩展到 N 个仓。
- 导入时若选中目录本身不是 git、其下却含多个子仓，Klarit 可提议把这些子仓组成一个多仓项目；也可随时往已有项目里增删成员仓。一旦某个目录查到 git 就立即给它绑身份。
- **需求与成员仓是多对多**：一张需求卡往往只动其中部分成员仓，卡片声明它涉及哪些仓，引擎只在这些仓里开分支 / worktree。

## 产物存储

Agent 产物分两类：

1. **项目文件**：直接改项目目录下的内容，有 git 就进 git，随分支版本化。
2. **需求卡关联信息**：Klarit 的管理状态（卡片、进度、关系、报告等），存在软件指定的用户数据目录（`app.getPath('userData')`，Windows 下默认在 C 盘），不进 git，未来云同步只同步这部分。

卡片状态跨分支、跨成员仓共享，不入 git——一个项目含多个仓、多个 worktree/分支时，它都是单一来源。

**工作流节点的产物路径**：每个节点可指定产物相对分支目录的路径；未指定则默认归入需求卡关联信息。该路径声明的是引擎要收集的交付物（如报告），不约束 Agent 直接编辑文件——代码改动由 git 自然捕获。路径必须落在分支目录内（禁绝对路径、禁 `..` 逃逸）。

**两类存储的绑定与一致性**：

- 卡片数据挂在**项目**（一组代码仓，见「项目与代码仓」）下，按各成员仓的 `.klarit/project-id` 关联，不靠路径——移动目录 / 换机器 / 多 worktree / 多成员仓都不断链；成员分组本身存 userData。
- 卡片元数据以 commit SHA / 分支名 / `路径@commit` 引用 git 产物；一次运行同时产出提交与卡片更新时，记下 SHA 以便检测漂移与修复。
- 卡片数据采用可按字段合并的格式（字段级 / 时间戳），为云同步的多设备并发改动做准备。

## 工作流与节点

### 阶段与节点

工作流分**阶段**（对应看板的列）；每个阶段含一或多个**节点**，默认线性，也可声明依赖做成 DAG（并行 / 条件）。

### 节点定义

```
节点 =
  所属阶段（看板列）
  执行者（四选一）:
    agent       —— prompt/skill、agent 层级、工作分支、可写范围、执行配置
    engine      —— 引擎内置结构化操作（建分支 / 开 worktree / 合并 / checkout），原生执行、结果可结构化追踪
    command     —— 在 CLI / 终端跑任意命令（测试 / 构建 / lint / 部署脚本），引擎只看退出码 + 捕获输出
    subworkflow —— 调用工作流 B（环检测 + 深度上限 + I/O 映射 + 默认折叠成一张卡）
  驱动指令       —— agent: prompt / skill.md（指导怎么干）；engine: 操作 spec（建哪条分支等）；command: 命令行
  产出[]         —— 0~N 个声明式交付物，每个 {目的地, 模板(可选), 必选|可选}；目的地 v1 为相对分支目录的 markdown 文件路径（文件名即标识、扩展名即格式，故不另设名称/格式字段），模板声明该文件的结构规范（必需标题/章节，对齐 OpenSpec）。卡片数据目的地（不填路径、归 userData，详见「产物存储」）待需求卡数据模型落地再开
  门             —— 有序门把序列（门把分自动校验 {校验命令, 校验目标(可选)} 与人工评审 {动作按钮[](可选)，各绑定一个命令} 两类）
  〔agent 节点〕 自动附加公共契约
```

规则：一个节点只有**一个执行者**，可有多个产出。要塞第二个执行者，就拆成下一个节点。

`产出[]` 只列**声明式交付物**。代码改动不算——它没有固定路径 / 格式，是**隐式产出**，由 git 自动捕获为本节点的提交，溯源图按 commit SHA + 改动文件记录（供内容驱动回退追溯）。

#### agent 执行者的「读写范围」

### agent 执行者的 「可读范围」

无需声明，默认可读所在节点的关联分支所有文件。

### agent 执行者的 「可写范围」

声明 agent 在本节点能改哪些文件，**与 `产出[]` 正交**——产出管"必须交付什么"，可写范围管"产出之外还能动什么"（典型就是改代码，代码是隐式产出、不进产出列表）。

- **默认 = 整条工作分支可写**。这覆盖了"写代码""维护本分支任意文档"这类节点——它们无需逐个声明产出，agent 直接知道分支内随便改。多仓项目里「工作分支」按成员仓计：节点声明它作用于哪个 / 哪些成员仓，可写范围与越界检测都在这些仓各自的工作分支内分别成立。
- 可收窄为分支内某子路径（给"只许动 `docs/`"这类受限节点用）；路径约束同产出（落在分支目录内、禁绝对路径、禁 `..` 逃逸）。
- **实际可写 = 可写范围 ∪ 所有产出路径**。声明一个产出就等于授权 agent 写它，所以产出路径**恒可写**，两者永不冲突，不存在"按谁算"。哪怕手动把可写范围收窄到比某产出路径还小，产出路径照样可写。
- **越界护栏（引擎强制）**：我们用 PTY 拉起第三方 CLI，没法逐路径沙箱化它的写操作，所以是**节点完成时后置检测**——引擎比对本节点 git 改动文件集与实际可写范围，越界即触发一道引擎自动加的基线门把（同「必选产出齐全」，无需配置）。处理：
  - 引擎把越界文件**还原到节点起始基线**（运行断点已记起始 commit SHA），确定性撤销、不靠 agent 自觉；范围内的合法改动**保留**——若它依赖被撤文件而残缺，会被后续测试 / 客观门自然挡下重做。
  - 带"哪些文件越界"详情喂回原节点重做，**限次**；超限抛决策，且选项必须含**「放宽可写范围」**——越界常因范围声明太窄（改代码必然要动 import 它的文件），缺这个选项会让硬撤硬返工陷入死循环。

#### agent 执行者的「执行配置」

可选地指定本节点用哪个编程工具、哪个模型：`{ 工具(adapter id，如 claude-code / codex / cursor)、模型、额外参数 }`。

- **声明式，不写裸启动命令**——工作流是拿来分享 / 复用的数据，裸命令会绑死某台机器的 CLI 路径与环境。引擎的「编程工具集成」模块当适配层，把 `工具 + 模型 + 参数` 翻译成实际的 node-pty 启动命令。裸命令只作高级逃生口（自定义 adapter），非默认路径。
- **级联就近覆盖**：`全局设置 < 节点声明`（两层；无「工作流默认」层）。
- **回退规则**：
  - *未声明* → 用级联下一级，最终落到软件全局模型，**静默**，属正常，不算失败。
  - *已声明但不可用*（模型不存在 / 工具没装 / 拉起即崩） → 显式意图落空，**默认抛决策**（用全局默认继续 / 去装那个模型 / 改声明），不静默降级以免悄悄拉低质量；可在工作流或全局设置里开「声明不可用时允许自动回退全局」让想省心的人打开。
  - 启动失败本身归"技术失败"（见失败矩阵）：模型回退即重启前的一次解析降级，作为重试策略的一环。

### 公共契约（仅 agent 节点）

除节点显式 I/O 外，引擎对每个 agent 节点自动注入：

- **公共输入**：宪法（＝该项目的**生效宪法**：激活规则包的宪法规则减去在该项目关掉的；详见四层结构「规则包的实体形态」）、引擎交互协议、对应需求卡活现状及关联文档。**本节点可写范围**（让 agent 明确知道这些文件可自由改动，而非靠分支内容自己猜）；续接 agent 额外注入会话历史。上游产出已固化在卡片活现状或分支里，节点无需声明。
- **公共输出**：必须更新对应需求卡的活现状。

数据全走公共输入，所以节点的「驱动指令」只管"怎么干"，不管"读什么"。

`engine` / `command` 节点不附加（确定性执行，无 agent）；`subworkflow` 通过内部 agent 节点继承。

### 门

门 = **有序门把序列**，逐道过，一道不过即短路。门把两类：

- **自动校验**：客观门 / 规则。基线门把（校验必选产出齐全且符合格式）由引擎自动加，无需配置；自定义门把可指定校验目标（某些产出 / 分支状态 / 测试），不指定则整体检查。
- **人工评审**：可选**动作按钮**：可声明零或多个，每个绑定一个 command（如验收时"启动 app"按钮跑 `npm start` 做真机验收）；声明会在抛出决策时渲染对应的按钮，不声明不渲染。

### 失败与中断

所有重试都**有限次数**，超限不静默挂起，一律以决策请求抛给用户（须交代每次重试的失败背景）。

| 类型 | 例子 | 处理 |
|---|---|---|
| 技术失败 | 卡住、断连、崩溃、超时 | 原节点重试 / 重启 → 超限抛决策 |
| 产出失败 | 必选产出缺失 / 格式不符 | 原节点带详情重做 → 超限抛决策 |
| 客观门失败 | 测试没过、违规命中 | 原节点带详情喂回重做 → 超限抛决策 |
| 越界写入 | 改了实际可写范围外的文件 | 引擎还原越界文件 + 带详情喂回重做 → 超限抛决策（含「放宽可写范围」选项） |
| 人工驳回 | "UI 重做""换实现方法" | 内容驱动回退（见下） |
| 外部抢占 | 上级 agent / 人临时变动、叫停 | 安全挂起（存活现状 + 会话历史）→ 重新调度 |

### 决策机制（统一）

人工门、agent 运行时提问、失败超限——三个来源走**同一个决策请求**：

- 形式：背景说明 + 选项 1/2/3… + 自由输入框；分**单选 / 多选**。
- 每个选项带：**名称**（标注是否推荐）+ **详细解释**（必要时含利弊分析 / 推荐理由）。
- 提交后返回给抛出者（原 agent）；若由引擎抛出且含自由输入，转交全局 agent 解读。
- **升级**：后台 agent 处理用户决策时，若涉及需求范围修改 / 跨需求联动 / 新建需求 / 调整其它需求，必须上抛全局 agent 处理，全局agent将其处理为跨卡决策。
- 单卡决策，就直接展示在需求卡详情面板内，跨卡决策单独弹窗处理。

### 内容驱动回退

人工驳回时不预先指定回退节点，也**不重置、不作废下游**——回退是**回到目标节点去修复**，不是推倒重来：

1. AI 解析反馈 → 命中的产物集合。
2. 引擎用**产物溯源图**反查生产该产物的节点。
3. 映射到多个产物 → 回到覆盖它们的**最早节点**（提名主选 + 备选，交用户确认）。
4. 回退前记录当前**最远进展节点**，让用户**确认目标节点**。
5. 重入目标节点：不重置分支、不撤下游代码——把「已推进到哪、出了什么问题、请在现有进展上修复」注入该节点的执行者，工作流带着修复**前向重流**回到评审门复审。沿途已建的分支 / worktree 由幂等引擎操作复用、下游产出复用，不重建。

新基建：**产物溯源图**——每个产物记录生产节点 + 下游依赖，供判定 agent 定位最早节点；声明式产出以路径归节点，代码这类隐式产出以节点起始→提交的 commit SHA 区间 + 改动文件归节点（复用「产物存储」的 SHA 关联）。它是**运行断点数据的派生视图**，不新建独立存储。

> 「回退 = 重置到节点起始态、下游作废重生」是另一种更重的模型，v1 不做；若日后需要，另起 change。

## 需求卡与关系图

### 看板节点：需求卡

看板上的节点是**需求卡**。卡片的「类型」是**用户可自定义**的（项目级：每个项目一套类型集），每个类型挂在一个引擎内置的**流动原型**上——原型只有两种、写死在引擎、不开放扩展：

- **`container`（容器）**：分组容器，旗下挂子卡；**不逐列流动**，停「待办」列作子卡入口，子卡全归档后从「待办」直达「归档」；可嵌套容器。
- **`leaf`（子叶）**：看板的**流通单位**，按项目激活工作流的阶段（看板列）逐列流动；是叶子、不挂子卡。提案与需求细化针对它编写。

类型本身只表达语义：`{ 名称, 描述（给分解 AI 的分类依据）, 原型, 徽章颜色 }`，**不带工作流**——流动由项目激活的单一工作流统一承载。开箱预置三个默认类型：`epic`(容器)、`feat`(子叶)、`bug`(子叶)，可改可删；工作流可声明「建议类型」，项目激活它时幂等播种进该项目类型集。卡片以 `typeId` 引用所属类型。

分解时把项目在册类型的「名称 + 描述」喂给分解 skill（自动生成，单一来源），AI 据此给候选卡选类型；候选用了不在册的类型则进审阅问题、不静默回落。

### 关系图：带类型的三种边

卡片之间的关系统一成一张**带类型的关系图**，三种边：

- **`parent` / `child`（层级）**：容器卡 ↔ 其子卡（只有 `container` 原型的卡能挂子卡）。承载分组、`3/3 完成` 汇总、展开第二入口、归属唯一。它**蕴含一条阻塞规则**——父卡归档 `blocked_by` 子卡全部归档；所以阻塞不是新机制，层级早在用它的特例。
- **`blocked_by` / `blocks`（依赖）**：跨卡先后序，A 没完 B 不能走。
- **`coupled_with`（耦合）**：两卡必须一起合并 / 一起被同一次发版纳入。验收时判断「分开发布会让体验退化」时打的标（详见「验收是反馈回路」）。

## 需求卡状态与恢复

### 卡片状态（生命周期）

未开始 → 进行中 → 已完成。另有两个非运行态：**已暂停**、**等待决策**（被决策请求阻塞）。

状态只表达"卡处于哪个阶段"，**当前在哪个节点单独记在运行断点里**，两者分开。

### 运行断点

为精确恢复，卡片在活现状里持久化一份运行断点（属卡片数据，存 userData）：

- 当前节点；
- 各声明产出的完成状态（已产出 / 未产出）；
- 门把进度（已过哪几道 / 停在哪道）；
- 代码隐式产出的最新 commit SHA。

恢复按断点续：产出未完成 → 重跑执行者；产出完成但门没过完 → 从下一道门把继续。

### 暂停与恢复

- 可手动暂停 / 恢复某张卡。
- 关闭软件自动暂停所有进行中的卡，重开自动恢复。
- 暂停即安全挂起（存活现状 + 会话历史）。
- agent 续接：优先用原生续接（如 Claude Code 的 `--resume`）直接接上对话；无原生能力的，用我们自存的对话历史重建上下文恢复。
