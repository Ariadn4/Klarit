# Klarit 失败与决策处理机制

这份文档是 Klarit 引擎「出问题时怎么办」的单一参考:每种失败什么时候触发、怎么归类、引擎怎么处理、用户会看到什么、以及所有转交给 AI 时**喂给 AI 的 prompt 由哪些部分组成**。用于日后查询错误处理机制,力求精确、不含糊。

> 术语:引擎跑一个工作流节点,分**执行阶段**(跑执行者)+ 随后的**门**(逐道客观校验 / 人工评审 / 外部门)。节点执行者四类:`engine`(内置 git 操作)、`command`(跑命令)、`agent`(叫编程 AI 干活)、`subworkflow`(暂跳过)。「主线」= 成员仓自己的基分支;「卡分支」= 该需求卡在成员仓里的同名工作分支;「工作区」= 卡分支的 worktree(独立工作目录)。

---

## 1. 处理模型总览

任何一个操作结果只会落到下面之一,**绝不停在看不见、没有出路的死结**:

| 归宿 | 什么意思 |
|---|---|
| **成功 / 已达成** | 达成目标,或探测发现已经达成(no-op),推进下一步 |
| **自动处理** | 瞬时抖动**有限次自动重试**(上限 2);某些环境性缺失**直接跳过**并记提示 |
| **agent 自愈** | 技术性失败(合并冲突、命令没过、客观门没过、越界写入)先**自动叫 AI 修**,修好继续;超限才转人工 |
| **人工决策** | 涉及**意图取舍 / 破坏性 / 凭据环境**的停顿,弹前进式决策请用户拍板 |

处理顺序:**先自动、再 agent、最后才打扰人**。两条关键分界:

- **技术性失败**(能靠改代码 / 解冲突消解、且「改哪儿」明确、能框在一个隔离工作区里)→ **先自动 agent 自愈**。
- **环境 / 凭据 / 意图 / 破坏性失败**(AI 决定不了、也修不了:配不了远端、决定不了丢不丢分支、抹不抹未提交改动)→ **直接人工决策**。

两个重试上限:

- **瞬时失败自动重试上限 = 2**。只有「目录 / 分支被占用」算瞬时。
- **agent 自愈重试上限 = 3**。超限回落到对应人工决策。

**重要**:无论哪种人工决策,都**恒带一个「转交 AI」的口子**(见 §2)——用户随时能就地问 AI 或把处置交给 AI,即便这个失败本身不走自动自愈。

## 2. 统一决策机制

**所有**询问用户的场合——失败超限、agent 运行时提问、人工评审门——都走**同一套决策结构**,并且**都带自由输入**。

### 2.1 决策的结构

一个决策含:

- **背景说明**:为什么停下(会随 AI 答疑而**向后追加**内容,见 §2.3)。
- **一组前进式选项**:每个都让流程继续(继续 / 跳过 / 重做 / 换法),各带名称(可标「推荐」)+ 可选详细解释;破坏性选项标 ⚠️。**没有「中止」这类死结选项**。
- **一个自由输入框**:恒在,可自由写想法 / 提问。**追问 AI 就是在这个框里打字提交**——不另设「继续问 AI」按钮。
- 单选或多选。

用户**选一个选项、和 / 或在自由输入框写内容,再点「提交」才正式生效**。光看不提交不改变任何状态。

### 2.2 提交后怎么处置

- **只选了内置前进式选项、没写自由输入** → 引擎按该选项语义直接续跑(跳过 / 重试 / 强推 / 先合并再删…),不牵涉 AI。
- **在自由输入框写了内容** → 内容连同上下文**转交一个 AI**处理,分两种:
  - **答疑**:AI 读懂问题后返回解释,**追加在背景说明之后**;原有选项**保留**,AI 还可**建议新增选项**并一并渲染;自由输入框仍在,用户可**继续在框里追问**,或最终选一项提交。
    - 例:开 worktree 失败,用户在自由框问「这是什么意思」→ 提交 → AI 解释路径被占的含义,追加到背景;选项仍为「删占位重建 / 递增尾号重建」(可能再加 AI 新增的建议),自由框仍在可继续追问。
  - **代办**:用户把处置交给 AI,AI 动手(改代码 / 调状态)或判定回退,收敛后引擎继续。

### 2.3 转交给哪个 AI(路由)

按**决策来自哪里**决定交给谁,以及那个 AI 有没有写权限:

| 决策来源 | 交给谁 | 权限 | 它干嘛 |
|---|---|---|---|
| **执行阶段**的失败 / agent 运行时提问,且**当前有 agent 在跑本节点** | **当前那个 agent** | 读写(它本就在写) | 把用户的意见经**续接**注入,让它据此继续(改代码 / 调整) |
| **执行阶段**的失败,且**当前没有 agent 在跑**(engine / command 节点) | **新起一个 agent** | **读写**,scope 到本卡分支工作区 | 就地处置:能改代码就改,不能就解释并把建议作为新选项交回用户 |
| **门类决策**(人工评审门 / 外部门的**驳回/打回**,如「这里不满意」「PR 要改」) | **新起一个 agent** | **只读** | **判定该回退到之前哪个节点**(内容驱动回退,见 §5.2/§5.3),**不**停在当前节点自行改;结论交用户确认 |

要点:

- **执行中的处置 agent 有写权限**——它要真去改。门类的判定 agent **只读**——它只负责「判断退回哪儿」,真正的重做由被退回节点的 agent(有写)去干。
- 这对齐三层 agent 结构:执行中的处置 = **后台执行 agent**(读写、限定分支);门类的只读判定 = **单需求 / 全局 agent**(只读、可要求把需求退回指定节点)。
- 技术性失败的**自动自愈**(§3.4 合并冲突、§4.1 命令没过)本质就是「执行阶段失败、当前没 agent → 新起读写 agent」这条路,只是**不等用户开口、引擎先自动跑一轮**;超限后落到的人工决策仍带 §2.1 的自由输入口子。

### 2.4 单卡 / 跨卡 与升级

- **单卡决策**直接展示在该需求卡的详情面板内;**跨卡决策**单独弹窗处理。
- **升级**:执行中的处置 agent 若发现用户意见涉及**需求范围修改 / 跨需求联动 / 新建需求 / 调整其它需求**,MUST 上抛**全局 agent**,由它处理成**跨卡决策**,而非自己在单卡内擅自处理。

## 3. 引擎操作节点(engine)的失败

引擎内置 9 个操作(平台预制节点),多数是**幂等调谐器**:先探测实际状态,已达成即 no-op,否则补齐。多仓时对每个涉及成员仓各跑一次、各自独立(某仓失败不阻断其余探测)。个别操作内部实现不同:`open-pr` 节点级委派一个 agent(能看到所有涉及仓)去各平台开 PR/MR。(「等平台把 PR 合并、合了才收尾」**不是**一个操作,而是一道**外部门**,见 §5.3。)

总览(每种失败的默认归宿):

| 操作 | 失败情形(底层归类) | 默认归宿 | 用户看到的决策(若到人工) |
|---|---|---|---|
| 建分支 create-branch | git 建分支异常(`error`) | 人工 | 「节点「X」未能完成,请重试或跳过」 |
| 开 worktree open-worktree | 路径被占 / 目录锁(`locked`) | 自动重试 2 次 → 人工 | 「worktree 路径被占用,无法创建」 |
| 关联环境 link-env | 目标目录不存在 / 链接失败 | **自动跳过** | (不弹) |
| 合并 merge-branch | **合并冲突**(`conflict`) | **agent 自愈**(§3.4)→ 超限人工 | 「合并遇到冲突」 |
| 合并 merge-branch | 其它合并异常(`error`) | 人工 | 「合并遇到冲突」 |
| 推送 push-branch | 非快进(`non-fast-forward`) | 人工 | 「推送被拒:远端已有比本地更新的提交」 |
| 推送 push-branch | 认证 / 权限(`auth`) | 人工 | 「推送失败:认证或权限不通过」 |
| 推送 push-branch | 没配远端(`no-remote`) | 人工(带填空) | 「尚未配置远端,无法推送」 |
| 删 worktree remove-worktree | 目录被占用(`locked`) | 自动重试 2 次 → 人工 | 「worktree 目录被占用,无法删除」 |
| 删 worktree remove-worktree | 内含未提交 / 未跟踪改动(`error`) | 人工(给强删) | 「worktree 目录被占用,无法删除」 |
| 删分支 delete-branch | 未合并到主干(`not-merged`) | 人工 | 「这个分支还有未合并到主干的改动,直接删会丢失」 |
| 删远端分支 delete-remote-branch | 不存在 / 无权限 | **自动跳过** | (不弹) |
| 开 PR open-pr | 无可用默认 agent(`no-agent`) | 人工 | 「要开 PR,但没有可用的 AI(默认 agent)」 |

### 3.1 建分支(create-branch)

- **在干嘛**:在成员仓建一条以卡 slug 命名的分支(基点是该仓自己的主线)。已存在即认领(noop)。
- **失败**:仅在 `git branch` 因罕见原因(基点引用不存在 / 仓库损坏)报错时,归 `error`。
- **决策**「节点「X」未能完成,请重试或跳过」:**重试** / **跳过该节点,流程继续**。
- 属 git / 环境层面,无代码可改,不走自愈。

### 3.2 开 worktree(open-worktree)

- **在干嘛**:给某分支在期望路径检出 worktree;残留半成品登记先 prune / 移除再重加。
- **失败**:路径被占或目录锁(`locked`),算瞬时,**先自动重试 2 次**。
- **决策**「worktree 路径被占用,无法创建」:
  - **删占位重建** ⚠️——会删掉该路径现有内容再建。
  - **递增尾号重建**——换带序号的新路径(`-2`/`-3`…),不动现有内容。
- 路径 / 环境问题,不走自愈(用户仍可经自由输入就地问 AI「这是什么意思」)。

### 3.3 关联环境(link-env)

- **在干嘛**:在 worktree 里建 junction 指向共享目录(如共用 `node_modules`),让 worktree 能完整跑验收;也用于把兄弟成员仓链进联调 hub。
- **失败**:目标目录不存在,或建链接失败。
- **归宿**:**自动跳过**并记提示——属「有更好、没有也不阻断交付」的辅助步骤,不打扰。

### 3.4 合并(merge-branch)+ 冲突自愈

- **在干嘛**:把卡分支合并回主线。先探测「卡分支是否已是主线祖先」(已并过就 noop),否则真合。
- **失败**:卡分支与主线改到同一处、git 无法自动合 = **合并冲突**(`conflict`)。
- **归宿:先自动 agent 自愈**。核心做法——**不在主线上解,在卡自己的分支上解**:冲突的本质是「卡分支的改动」和「主线的改动」撞在同一处,所以反过来把**主线并进卡分支**(在卡本来就隔离的工作区里做),让冲突显现在卡这边;临时 AI 在卡工作区解冲突;解完卡分支就消化了主线,**再合回主线就是干净快进、不再冲突**。这样主线全程没被碰过,AI 搞砸了大不了把卡分支重置回动手前。

  **流程**(多仓时**逐仓**各走一遍,哪个仓冲突就为哪个仓拉一个,各仓独立):
  1. 合并回主线时探到冲突。
  2. 未超限:在该成员仓卡工作区 `git merge <主线>`,**保留冲突态不 abort**。
  3. 拉起临时 heal agent(读写,cwd = 卡工作区),喂 §6.3 的 prompt。
  4. AI 解冲突、清干净标记(**不自己提交**)。
  5. 引擎校验无残留冲突标记后**确定性提交**这次合并 → 卡分支消化了主线。
  6. 把卡分支**快进合回主线** → 该仓过。
  7. **超限(3 次)**:卡分支**重置回动手前** + abort 在途合并 → 回落人工决策「合并遇到冲突」,唯一前进式选项 **放弃合并,跳过该节点,流程继续**(有损,但兜底不卡死)。该人工决策同样带自由输入口子。

### 3.5 推送(push-branch)

三种失败,**都留人工**(AI 配不了远端、决定不了覆不覆盖别人的提交):

- **非快进(`non-fast-forward`)**:远端已有比你新的提交。「推送被拒…」:
  - **拉取变基后重推**——本地变基到远端之上再推,**不覆盖**远端(推荐)。
  - **强推覆盖远端** ⚠️——覆盖远端比你新的提交。
  - **跳过推送,流程继续**。
- **认证 / 权限(`auth`)**:「推送失败:认证或权限不通过」:**我已配好凭据,重试** / **跳过推送**。
- **没配远端(`no-remote`)**:「尚未配置远端…」,带**填空框**(标签「远端仓库地址」,提示 `git@github.com:you/repo.git 或本地裸仓路径`):填地址 → 配好远端并重推;或**跳过推送**。

### 3.6 删 worktree(remove-worktree)

- **在干嘛**:确保某路径不再有 worktree。删前**无条件防御性解链**(解掉里面所有 junction、绝不递归进去,以免顺链误删目标)。
- **失败**:目录被占用(`locked`,瞬时、自动重试 2 次);或内含未提交 / 未跟踪改动(`error`)。
- **决策**「worktree 目录被占用,无法删除」:**我已关闭占用程序,重试** / **强制删除** ⚠️(可能丢未提交改动)/ **跳过,保留 worktree**。
- 破坏性(可能抹掉未提交工作),留人工——「绝不无脑 --force」红线。

### 3.7 删分支(delete-branch)

- **在干嘛**:确保某本地分支不存在,用**安全删**(未合并即拒)。分支仍被 worktree 检出则级联先清那个 worktree(worktree 若脏且非强制,会在这步冒泡成可见停点、保护未提交工作)。
- **失败**:分支还有未合并回主干的改动(`not-merged`)。
- **决策**「这个分支还有未合并到主干的改动,直接删会丢失」:**先合并再删**(并回主干再删,不丢工作,推荐)/ **直接删除丢弃** ⚠️(连未合并改动一起删)/ **保留分支,跳过该节点**。
- **丢不丢这条分支是意图取舍**,留人工。

### 3.8 删远端分支(delete-remote-branch)

- **在干嘛**:确保远端某分支不存在。
- **失败**:远端已无该分支 / 无权限。
- **归宿**:**自动跳过**(幂等 no-op 语义),不打扰。

## 4. 命令节点(command)的失败

命令节点在卡工作区里跑一或多条命令(测试 / 构建 / lint / 部署),引擎只看退出码 + 捕获输出。

| 失败情形 | 默认归宿 | 决策(若到人工) |
|---|---|---|
| **主命令非零退出**(测试 / 构建没过) | **agent 自愈**(§4.1)→ 超限人工 | 「命令「X」执行失败。请看下方原因后重试或跳过该节点」 |
| 主命令超时被中止 | 人工 | 「命令「X」运行超过 N 秒被中止。可重试或跳过该节点」 |
| 被暂停 / 手动打断(killed) | **不算失败**、不弹决策 | (无) |
| 前置检查 `check` 非零 | 正常跑主命令(非失败) | (无) |

### 4.1 主命令非零退出 + 自愈

- **触发**:命令退出码非 0(**不会被当瞬时失败自动重试**)。多命令节点里任一条非零,引擎杀掉本节点其余在跑命令,再处置这一条。
- **归宿:先自动 agent 自愈**。命令本就在卡的隔离工作区跑,天然沙箱,不用另搭隔间:
  1. 命令非零退出。
  2. 未超限:拉起临时 heal agent(读写,cwd = 命令的工作区),喂 §6.4 的 prompt。
  3. AI 改代码(**不自己提交**)。
  4. 引擎**提交**范围内改动,再**把那条命令重跑一遍**验证。
  5. 退出码 0 → 过;仍非零 → 计一次,重试或超限。
  6. **超限(3 次)** → 回落人工决策「命令「X」执行失败」,下方附**失败原因 = 命令输出**(不显示退出码):**重试** / **跳过该节点,流程继续**。

### 4.2 主命令超时

- **触发**:命令声明了超时且跑超,被杀整棵进程树。
- **归宿**:人工决策「命令「X」运行超过 N 秒被中止」——**重试** / **跳过该节点**。**不自愈**:超时可能是死循环、也可能只是机器慢,不好判定该不该 AI 修。

## 5. 门(gate)

门 = 有序门把序列,逐道过,一道不过即短路。三类:**客观校验**(跑校验命令看退出码)、**人工评审**、**外部门**(等一个 Klarit 控制不了的外部状态达成)。

### 5.1 客观校验门

| 挂在哪种节点 | 失败情形 | 归宿 |
|---|---|---|
| **agent** 节点 | 检查没过(非零) | agent 自愈:续接**原** agent、注入「哪道门为何没过」重做(§6.2);超限抛 agent 决策 |
| **command** 节点 | 检查报错(非零) | **agent 自愈**:同 §4.1(拉临时 heal agent 改代码,验证方式换成「重跑那道门」);超限人工 |
| **engine** 节点 | 检查报错(非零) | 人工(引擎操作没产出代码可改) |
| 任意 | 检查**超时** | **自动只重跑该检查 ≤3 次** → 仍超时才人工 |

- **人工决策(engine 节点门报错 / 各类超限)**「节点「X」的客观检查未通过…」,附**原因 = 检查命令输出**(不显示退出码):**重跑此检查**(推荐)/ **重跑本节点** / **跳过此检查,流程继续**。
- **超时升级**时决策文案变「…自动重跑 N 次仍未通过」,附重跑记录(每次是「超时→只重跑检查」还是「报错→重跑整节点」,不含退出码)。自动重跑次数**持久化进断点**(关软件重开不清零),门通过即清零。

### 5.2 人工评审门 + 驳回的内容驱动回退

- **触发**:节点声明了人工评审门,走到即停,弹「节点「X」需要人工评审」,选项 **通过**;并**打开自由输入框**供写驳回意见(评审门此前只发「通过」、不带自由框,驳回入口即由此开)。声明了产出文件的,决策附「可点开查看的产出链接」(如规划节点的 `PLAN.md`);声明了动作按钮(如「启动 app」)的,渲染按钮供真机验收。
- **驳回(用户在自由框写不满意的点,如「这里体验不对」)**:按 §2.3 门类路由,**新起一个只读 agent**,它:
  1. 解析用户反馈 → 命中的产物集合。
  2. 用**产物溯源图**(运行断点 SHA 的派生视图)反查生产这些产物的节点。
  3. 命中多个产物 → 定位到覆盖它们的**最早节点**,可给主选 + 备选。
  4. **回退前让用户确认**目标节点;引擎先记录当前**最远进展节点**。
- **回退 = 重入,不是重置**:确认后引擎把当前节点拨回目标节点,**不重置分支、不撤下游代码、不作废下游产出**。把「你之前已推进到节点 N、用户驳回意见是什么、请在现有进展上修复」注入目标节点执行者(有写),它在既有基础上改。工作流随后**前向重流**回评审门复审——沿途已建分支 / worktree 由幂等引擎操作(§3)复用,已跑过的合并把新的修复提交再前向合一次、不回撤主线。
- 这个只读 agent **只负责判定退到哪**、不自己改;真正的修复由被退回节点的执行者(有写)去干。

> 「回退 = 重置到节点起始态、作废下游重生」是另一种更重的模型,v1 不做;需要时另起 change。

### 5.3 外部门(等外部状态达成)

**第一个「等外界」的门**——它等的是一个 **Klarit 控制不了的外部状态**(v1:`verify: 'pr-merged'`,即 PR 已在托管平台合并)。典型挂在 `open-pr` 节点上,构成「真 PR」工作流的收尾关口。

- **过门条件 = 核查,不盲信**:进门跑一次平台无关的 git 合并核查(`fetch --prune` 后看分支是否已并入基分支 / 上游是否 `gone`,逐涉及仓、全达成才算)。达成 → 过门(前向到清理);未达成 → **挂起**,弹「PR 确认已合并后,点击以进行收尾工作」+ 前进式按钮 **「开始收尾」**。点「开始收尾」= **再核查一次**,真合了才过门,没合就再挂回来(点击不等于放行)。
- **将来接 webhook**:这个「再核查」现在由用户点触发,**将来可由平台 webhook 等外部信号触发**——所以过门判定是「核查外部状态」而非「用户断言」,同一判定可被外部信号复用。这也是它独立成一类门、而非并进人工评审门的原因。
- **打回 = 复用人工评审门那套内容驱动回退**(§5.2):在自由输入框写下不满意的点(如「PR 里这段要改」),即退回到之前节点改代码 → 前向重流经 `push` / `open-pr` / 本外部门**自然 re-push 更新平台 PR、再核查**——正好是「PR 被打回 → 改 → 更新 PR → 再等合并」的闭环。回退判不出 / 用户取消时,**重抛本外部门**(而非评审门)。
- **注意**:普通引擎失败决策(§3、§4)的自由输入**不**走回退——那类反馈有的就是本节点的活、该就地改(§2.3 处置 agent)。「打回到之前节点」是**门**(人工评审门 / 外部门)独有的语义。

## 6. 给 AI 的 prompt 组成

所有喂给 AI 的文本都在此列全(单一来源,精确到分节)。

### 6.1 agent 节点的完整 prompt

由纯函数按**固定层序**拼装(`# 回复语言 → # 宪法 → # 任务 → # 需求卡 → # 涉及的成员仓 → # 可写范围 → # 产出 → # 引擎交互协议`)。空层省略(宪法 / 涉及仓 / 产出),其余恒在:

- **`# 回复语言`**(恒在):按界面语言注入,如中文为「请始终用简体中文回复与产出(代码标识符等技术约定除外)。」
- **`# 宪法`**(空则省略):该项目**生效宪法**逐条 `- {规则名}：{规则正文}`(= 激活规则包的宪法规则 − 在该项目关掉的)。
- **`# 任务`**(恒在):节点驱动指令(inline prompt 或 skill.md 已读文本);读不出显「(无法读取 skill 文件内容)」、未填显「(未填写 prompt)」。
- **`# 需求卡`**(恒在):四个子标题 `## 标题` / `## 类型` / `## 描述` / `## 关系`,执行期填真实卡字段值,预览期用占位槽。
- **`# 涉及的成员仓`**(多仓才有):引导「本需求涉及以下代码仓,均已在你的工作范围内,请在各自目录里改对应文件:」+ 逐仓 `- {仓名}（{标签}）：{worktree 绝对路径}（当前工作目录 / 额外工作目录（--add-dir））`。
- **`# 可写范围`**(恒在):逐条列可写子路径;为空给默认「整条分支可写。」。
- **`# 产出`**(空则省略):引导「完成后需产出以下文件:」+ 每个 `## 产出文件：{路径}（必选 / 可选）` + 模板(有模板则用 ```` ```markdown ```` 围栏包住模板原文并提示「其中 `<!-- -->` 是写作指引,最终产出请删除」)。
- **`# 引擎交互协议`**(恒在,置末):教 AI 结构化交互——正文见 §6.5。

### 6.2 自愈 / 续接的注入(续接原 agent)

当引擎需要重新推进**同一个** agent 节点(自愈回喂 / 回答决策 / 崩溃恢复),按「就高不就低」阶梯:优先原生 `--resume <会话id>` 只注入下面这段增量;拿不到会话 id / 续接失败,则用「原完整 prompt + 历史记录块 + 这段增量」全新起。

**增量正文**(据情形拼)——固定开头:
```
# 续接说明
继续完成任务；你之前的改动已在 worktree 里，别重复已完成的部分。
```
若带**用户对提问的决定**,追加:
```
你此前请求了用户决策，用户的决定是：
{用户选定项或自由文本}
请据此继续。
```
若带**失败详情**(门没过 / 产出缺失 / 越界文件清单等),追加:
```
上一次未通过，失败详情：
{失败详情}
请据此在当前 worktree 修复后继续。
```
**历史记录块**(仅在无法原生续接、要全新起时垫在增量前):
```
# 你之前的执行记录（供参考，worktree 里已有对应改动，别重复已完成的）
{增量自存的会话记录尾部（约 8000 字）}
```

> 「用户对提问的决定」这一段,正是 §2.3 里「执行阶段决策 + 当前有 agent → 注入当前 agent」的落地:用户在决策里选的项 / 写的自由输入,原样填进 `{用户选定项或自由文本}`。

### 6.3 合并冲突自愈 prompt

公共输入复用 §6.1(生效宪法 + 需求卡 + 引擎交互协议),`# 任务` 段替换为:

```
仓库「{仓名}」里，这张卡的分支「{卡分支}」要合并回主线「{主线}」时发生冲突。
为方便你处理，主线已并入你当前分支，以下文件有冲突：
{冲突文件清单}
请解决全部冲突：两侧意图都要保留（既别丢本卡的改动，也别丢主线上他人的改动），
清理干净所有冲突标记。只需把这些文件改到无冲突即可，不要自己提交——引擎会提交并校验。
```

### 6.4 命令失败自愈 prompt

公共输入复用 §6.1,`# 任务` 段替换为(命令节点客观门失败共用此段,把「命令」换成「门校验命令」):

```
仓库「{仓名}」分支「{卡分支}」上，命令 `{命令}` 执行失败。失败输出：
{命令输出（截断）}
请修改代码让这条命令能通过。改完不要自己提交——引擎会提交并重跑该命令来验证是否修好。
若你判断这不是代码能修的问题（如缺依赖 / 环境不对），在握手文件里写清原因并请求决策（会转交人工）。
```

### 6.5 执行阶段无当前 agent、经自由输入新起读写 agent 的 prompt

当 engine / command 节点失败弹了人工决策、用户写了自由输入(§2.3 第二行),新起一个读写 agent,`# 任务` 段:

```
引擎在仓库「{仓名}」分支「{卡分支}」执行「{操作/命令}」时停下，背景：
{失败背景 + 原始输出}
用户对这个决策说：
{用户自由输入}
请帮用户处理：
- 若用户在提问，解释清楚并给出建议（可建议新增决策选项）；
- 若用户要你动手、且这是代码 / 工作区能解决的，就在当前工作区改（改完别自己提交，引擎会提交并重跑验证）；
- 若这不是代码能解决的（如路径被占、凭据、远端、需用户再拍板），在握手文件里说明，并把处置建议作为决策选项交回用户。
```

### 6.6 门驳回、只读回退判定 agent 的 prompt

人工评审门驳回时(§5.2),新起一个**只读** agent,`# 任务` 段(公共输入里**不**给可写范围 / 产出,强调只读):

```
你是本需求的只读顾问，不改任何文件、不写任何产出。
用户在「{节点}」的人工评审里驳回了，意见是：
{用户自由输入}
请对照本需求各节点的产出与它们的溯源关系，判断这条意见指向的问题最早在哪个节点产生、
该回到哪个节点去修复（给一个主选节点 + 若干备选）。把结论写进握手文件的决策里交用户确认：
目标回退节点、理由。回退是回到该节点在现有进展上修复，不重置、不作废下游。
不要自行修改代码或产出。
```

### 6.7 引擎交互协议正文(所有 agent 恒含)

置于每个 agent prompt 末尾,教它如何与引擎结构化交互(与握手文件合约同源):

```
你在引擎编排下工作。完成、需要用户决策、或无法继续时，MUST 把握手文件（JSON）写到这个
绝对路径：`{引擎运行时注入的绝对路径}`（它在代码仓之外，请勿写进 worktree）。写完即退出；
引擎在你退出时读它来决定下一步。
握手文件字段：
- status：done（已完成）/ need-decision（需用户拍板才能继续）/ failed（失败，附 detail）。
- decision（仅 need-decision）：{ title: 背景说明, options: [{ id, label, detail?, recommended? }],
  multi?: 是否多选, freeInput?: 是否允许用户自由输入 }。需要拍板时停下写它再退出，不要臆断。
- repos（可选）：本任务实际涉及的成员仓标识列表，供引擎给下游节点收窄目标仓。
- note（可选）：一句话小结，会写入需求卡活现状。
你的 stdout 只用于向用户实时展示进度，引擎不解析它来判断状态——结构化意图一律走握手文件。
```

> 握手 MUST 写到 worktree **之外**的引擎指定绝对路径,不落 worktree(否则会被越界检测 / 每节点提交误纳入、污染代码仓)。**握手缺失即乐观 `done`**:agent 退出却没写握手时,引擎按 `done` 继续,真未完成由客观门 / 越界检测兜底触发自愈。

## 7. 附:agent 节点执行的两道内置护栏

不属「失败决策」,但决定 agent 改动怎么被约束,一并记清:

- **可写范围越界后置检测**:agent 节点完成时,引擎对每个目标仓比对 git 改动集与**实际可写范围**(`可写范围 ∪ 所有产出路径`,可写范围为空 = 整条分支可写)。越界文件(改动落在范围外)被**确定性还原**到节点起始基线(还原到节点起始 commit),范围内改动保留。越界带「哪些文件越界」详情喂回自愈重做,限次;超限抛决策且选项**必含「放宽可写范围」**(越界常因范围声明过窄,缺此选项会死循环)。
- **每节点提交**:越界还原之后,引擎把该节点每个目标仓**实际可写范围内**的改动提交为一次 commit,记 commit SHA(代码隐式产出的溯源锚点 + 下一节点越界检测的起始基线);无范围内改动的仓跳过提交、不产生空 commit。

## 8. 观测与记录(排查用)

AI 是黑盒,出问题时必须能回看「喂了什么、它干了什么」。故:

- **prompt 随输出可见**:每个 agent 的实时输出框 MUST 同时展示**喂给它的完整 prompt**(§6 的拼装结果),供用户核对 prompt 是否靠谱——**包括**自愈续接注入、合并 / 命令临时 heal agent 的 prompt(临时 agent 也要能看到它收到的全文,不能是黑盒)。
- **所有 agent 全量留痕**:每一次 agent 运行——节点 agent、自愈续接、合并冲突 heal、命令失败 heal,以及将来的处置 / 只读判定 agent——MUST 各记一份可排查的运行记录,持久化、关软件重开仍可查,至少含:
  - 喂入的**完整 prompt**;
  - **增量自存的会话记录**(stdout/stderr 转写,边跑边落盘);
  - **握手文件内容**与最终 `status`;
  - **最终归宿**(done / need-decision / failed / 超限回落人工)与失败详情;
  - 所属**运行、节点、成员仓**,及每仓**起始 / 提交 SHA**;
  - 自愈的**第几次尝试**。
